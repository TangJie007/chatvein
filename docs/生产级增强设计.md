### 1. 目标与边界

**目标**：把现有「原型可用」的桌面 Agent 提升到「生产级可用」——在长对话、工具失败、进程重启、联网不稳、外部生态接入等真实条件下仍能给出稳定、可恢复、可观测的结果。

**本轮已确认的边界**（来自需求澄清）：

| 项 | 决定 | 说明 |
|---|---|---|
| 落地范围 | 全都要，分 3 批推进，从内核韧性开始 | 每批独立可交付、可回滚 |
| 交付形态 | **先出详细设计 → 评审 → 再改代码** | 本文档即评审物；评审通过后逐批实现 |
| 外置 MCP 客户端 | **允许引入** | stdio / SSE / Streamable HTTP 外部 server 接入；推翻 `Agent与功能.md`「刻意不做外置 MCP 子进程」一条，评审后同步修订该文档 |
| 容器级沙箱 | **不引入** | 保持进程内 + 路径约束 + 审批模型；第三批只做「加固」不做 OS 级隔离 |
| 语言/框架 | 不引入新的全局状态库、不引入 Alembic、不新增前端构建链 | 遵循 `AGENTS.md` 硬约定 |

**非目标**（本轮不做）：多用户/租户、服务端部署、SaaS 连接器内置、通用 `cmd.exe`、浏览器 RCE 工具。

#### 4.2 ContextVar 与线程约束（最容易踩的坑）

`AGENTS.md` 硬约定 9：trace / sandbox / turn 用 `ContextVar`，设置与读取必须同线程。现有 `_run_chat_heavy`（`main.py:403`）在 `asyncio.to_thread` 里 `bind_turn` → `recording` → `use_conversation_sandbox` → `run_pipeline`，全部同线程。

**新增能力的约束**：

- checkpointer、流式回调、HITL 断点都必须在这**同一个工作线程**内读取/写入；对应新增的 ContextVar（如 `stream_sink`、`interrupt_controller`）必须与现有三个一起在 `_run_chat_heavy` 里设置。
- 多 agent 并行（2.4）若用线程池，`copy_context()` 必须连同全部相关 ContextVar 一起传递；`pass_contextvars` 不得拆分。
- 真 MCP 客户端的异步事件循环不得阻塞该工作线程；用独立 asyncio loop + 线程安全队列桥接。

### 1.1 上下文工程：自动压缩 + token 预算

> **状态：已实现（2026-11-19）**。新增 `agents/token_budget.py` / `agents/context.py`，三张图接入，摘要缓存落会话库 `context_summaries`，trace 增 `context` 节点；开关 `CHATVEIN_CTX_COMPACT`（默认开）。

#### 现状（证据）

- `agents/memory.py::to_lc_messages()` 仅 `history[-limit:]`，`tool` 角色消息直接丢弃；limit 由 `main.py:285-295` 算 `clamp(role.memory*2, 0, 60)`，默认 24。
- 无摘要、无 token 计数、无相关性召回；长会话必然截断早期关键事实，且截断方式是把整条消息丢掉。
- `trace/recording.py` 记录了 `cached_tokens` 但只统计、不参与决策；`llm.py` 的 `max_tokens` 只限输出。

#### 目标

1. 当历史 token 逼近模型上下文窗口时，自动把**较早**的消息压缩成摘要，保留关键事实/决策/产物路径，而不是粗暴丢弃。
2. 引入 token 预算分配：system / history(含摘要) / 本轮输入 / 输出预留 四段预算可控，避免超窗报错。
3. 摘要可追溯：压缩事件写 trace，用户可在追踪窗看到「哪几轮被压缩成什么」。

#### 方案

**新增 `backend/agents/context.py`**（新模块，c 级）：

```python
# 对外唯一入口，取代 memory.to_lc_messages 在 pipeline / simple / medium / hard 的调用
def assemble_context(
    *,
    history: list[dict],
    message: str,
    system_prompt: str,
    model_id: str | None,
    role: dict | None,
    budget: ContextBudget,
) -> AssembledContext:  # .messages / .summary / .token_report / .compacted_turn_ids
    ...
```

处理流程（按顺序）：

1. **估算 token**：用 `tiktoken`（若模型是 OpenAI 系）按 `model_id` 选编码，否则用字符数 `/1.6` 的保守估算法。加 `backend/agents/token_budget.py` 封装 `count_tokens()`，只依赖 `tiktoken`（已在依赖中则直接用，否则走估算，不新增硬依赖）。
2. **预算计算**：`ContextBudget` 从角色/模型运行时读取 `context_window`（模型配置已有该字段），预留 `output_reserve`（默认 2048）+ system + 本轮输入，剩余给 history。
3. **分段裁剪**：
   - 保留最近 N 轮原文（`recent_turns`，默认 6，可配 `CHATVEIN_CTX_RECENT_TURNS`）不压缩。
   - 更早的消息按「对（user, assistant）」分组，若 history token 超预算，取最老的一组做摘要。
4. **摘要生成**：调用主模型一次（复用 `llm.invoke_structured`，输出 `SummaryDecision{summary, kept_facts[]}`），失败则降级为「抽取式摘要」——直接拼接各条消息前 200 字 + 关键词，绝不阻塞主流程。摘要作为一条 `SystemMessage(content="[历史摘要]\n…")` 置于历史最前。
5. **摘要缓存**：摘要结果写回会话库 `session.sqlite` 的 `context_summaries` 表（key = 压缩到 Message.id），下次同会话直接复用，避免重复付费。
6. **trace**：`note("context", detail={"compacted_ids": [...], "before_tokens":…, "after_tokens":…, "summary_chars":…})`；`_path` 新增 `context` 节点。

**降级路径**：任何异常（无模型、超窗估算失败）→ 回退到现有 `to_lc_messages(history[-limit:])`，行为与今天完全一致。

### 1.2 工具可靠性：结构化错误 + 重试/熔断 + 幂等

> **状态：已实现（2026-11-19）**。新增 `mcps/tool_result.py` / `mcps/resilience.py`，接入 ReAct（middleware）与离线 `invoke_tools`，`tool_scope` 按轮隔离状态；开关 `CHATVEIN_TOOL_RETRY`（默认开）。

#### 现状（证据）

- `registry.py::invoke_tools()` 每个工具 `try/except` 拼 `f"[{name}] 失败: {exc}"` 字符串；ReAct 层工具由 LangChain `ToolNode` 执行，失败以字符串回灌模型。
- `common.py::same_arg_tool_guard()` 阻止同参重复；`rate_limit_retry_middleware()` **只覆盖模型限流**，普通工具失败无重试、无熔断。
- `concise_failure()` 靠字符串匹配 `失败/离线模式/error` 挑失败工具名——脆弱。

#### 目标

1. 工具调用统一返回结构化结果（成功/失败/跳过 + code + 耗时 + 是否可重试），非空字符串。
2.  transient 失败（网络抖动、超时、5xx）自动重试（指数退避 + 抖动）；确定性失败（参数错误、权限拒绝）不重试。
3. 熔断：同一工具连续 N 次失败则本轮熔断，模型收到明确提示改用其他工具。
4. 幂等键：对有副作用的工具（写文件、支付类不存在但有 `write_file`/`delete_path`）用 `tool_call_id` 作为幂等键，防止重试重复写。

#### 方案

**新增 `backend/mcps/tool_result.py`**（c 级）：

```python
@dataclass
class ToolResult:
    ok: bool
    content: str                 # 给模型看的文本（原有字符串放这里）
    code: str = "TOOL_OK"        # 见「零、路线图与总纲」§4.3 code 域
    retryable: bool = False
    duration_ms: int = 0
    error_kind: str | None = None  # transient | deterministic | denied
```

**新增 `backend/mcps/resilience.py`**（c 级）：

- `classify_exception(exc) -> error_kind`：白名单 transient（`TimeoutError`、连接异常、HTTP 5xx/429）→ retryable；`ValueError`/参数校验/`ToolDenied` → deterministic。
- `with_retry(tool, args, *, max_attempts=3, base=0.5, jitter=True, cancel_check)`：使用 `agents.cancellation.raise_if_cancelled()` 作为等待中的取消检查点；每次重试前记 trace。
- `CircuitBreaker`：本轮内 `fails[name]`，连续 `CHATVEIN_TOOL_CB_THRESHOLD`（默认 3）次失败 → 后续该工具调用直接返回 `TOOL_CIRCUIT_OPEN` 提示，不再执行。按 turn 隔离（ContextVar 或 middleware 局部状态）。

**接入方式**（关键：不改工具实现，在 middleware 层包裹）：

- `common.py::build_react_graph()` 的 middleware 列表新增 `resilient_tool_middleware()`：用 `wrap_tool_call` 拦截 `handler(request)`，包一层重试 + 熔断 + 结构化返回（仍以 `ToolMessage` 回灌，content 用 `ToolResult.content`，保证对 LangChain 透明）。
- `registry.py::invoke_tools()` 离线路径同步用 `with_retry`，输出格式兼容旧 `f"[{name}] …"`（展示不变）。
- `concise_failure()` 改为读 `ToolResult.error_kind` / `code`（保留旧字符串匹配作为兼容分支）。

**幂等**：`wrap_tool_call` 的 `request.tool_call.id` 作为幂等键；`resilience.py` 维护 `seen_idempotency: dict[str, ToolResult]`；重试命中相同 id 直接返回缓存结果。对 `write_file`/`edit_file`/`delete_path` 强制启用（工具名集合常量 `IDEMPOTENT_TOOLS`）。

#### 改动文件

| 文件 | 等级 | 改动 |
|---|---|---|
| `backend/mcps/tool_result.py` / `resilience.py` | c | 新建 |
| `backend/agents/graphs/common.py` | a | middleware 加 resilient_tool；`concise_failure` 兼容新错误模型 |
| `backend/mcps/registry.py` | b | 离线 `invoke_tools` 接 retry |
| `backend/agents/cancellation.py` | b | `raise_if_cancelled` 暴露给 `resilience.wait` |
| `backend/tests/test_tool_resilience.py` | — | 新测试：retry 次数、熔断触发、幂等命中、取消打断退避 |
| 前端 `insightData.ts` | c | 工具失败展示 code（若有） |

#### 验收

### 1.3 断点续跑：LangGraph checkpointer + 状态持久化

> 本能力是 2.2 统一 HITL 的前置。**评审已确认（2026-11-19）：「崩溃/重启后续跑」与「用户点停止后保留现场可恢复」两者都做。** 下文按此范围实现。
>
> **状态：后端已实现（2026-11-19）**。新增 `agents/checkpoint.py::SqliteCheckpointer`，`run_pipeline(thread_id=..., resume=...)` 接入；`GET /api/conversations/{id}/resumable`、`POST /api/conversations/{id}/resume`（continue/discard）；开关 `CHATVEIN_CHECKPOINT`（默认开）。前端「继续 / 放弃」入口已随 2.1 接线（`useChatSession.resumable` + `ChatPanel` 提示条）。

#### 现状（证据）

- `pipeline.py:149`、`medium.py:197`、`hard.py:479`、`simple.py:32` 全部 `graph.compile(name=...)`，**无 `checkpointer=`**；`compile` 结果只在进程内缓存。
- `ChatState`（`graphs/state.py`）只在单次 invoke 内存流转；进程重启即丢。
- `cancellation.py` 的取消是协作式：检查点抛 `TurnCancelled` 后整轮结束，无现场保存。

#### 目标

1. 每完成一个图节点（understand / plan / select_tools / react / verify）持久化一次 `ChatState`。
2. 进程崩溃/重启后，用户打开同一会话可「继续上次」，从最后一个成功节点恢复，不重复已执行的工具。
3. 用户点停止时**可选**保留现场（默认保留），提供「继续生成」按钮而非丢弃整轮。

#### 方案

**checkpointer 实现**：不引入额外依赖，实现 LangGraph `BaseCheckpointSaver` 的轻量 SQLite 版本。

**新增 `backend/agents/checkpoint.py`**（b 级）：

```python
class SqliteCheckpointer(BaseCheckpointSaver):
    """会话库 logs/session.sqlite 内 agent_checkpoints 表。
    thread_id = f"{conversation_id}:{turn_id}"；按 (thread, checkpoint_id) 读写。"""
    def put(self, config, checkpoint, metadata, new_versions) -> None: ...
    def get(self, config) -> Checkpoint | None: ...
    def list(self, config, *, limit=1) -> list[CheckpointTuple]: ...
    ...
```

- 表结构（会话库）：`agent_checkpoints(thread_id, checkpoint_id, parent_id, state_json, metadata_json, created_at)`，索引 `(thread_id, created_at DESC)`。
- 状态序列化：`ChatState` 全字段 JSON；`role` 是 dict 可序列化；`history` 已是 dict 列表；无不可序列化对象（若发现 `BaseMessage` 对象则改在 state 里只存 dict，与现状一致）。
- 挂载：`build_pipeline()` / `build_react_graph()` 的 `compile(..., checkpointer=get_checkpointer())`；checkpointer 由 `use_conversation_sandbox` 同一 ContextVar 提供（保证指向本会话库），在 `_run_chat_heavy` 内设置。
- `config` 需带 `{"configurable": {"thread_id": …}}`：`runnable_config()`（`trace/recording.py`）已有 config 注入点，扩展它把 `thread_id` 带进去，避免改每张图的调用签名。

**续跑入口**：

- 新接口 `POST /api/conversations/{id}/resume`（`conversations/controller.py` + `module.py` + `main.py include_router`），body `{turn_id, action: "continue"|"discard"}`。
- service 层：按 thread_id 取最新 checkpoint → 调 `build_pipeline().invoke(None, config={...,"thread_id":…})`（LangGraph 从 checkpoint 恢复，从中断节点继续）→ 复用现有 `save_exchange` 落库；`action=discard` 则清 checkpoint 并按现有 `deleteLastTurn` 逻辑撤回乐观气泡。
- 前端：`useChatSession` 在会话加载时查 `GET /api/conversations/{id}/resumable`（新接口，返回未完成的 turn_id 列表）；有则显示「继续生成 / 放弃」提示；停止时不清 checkpoint。

**取消语义调整**（关键，避免与现有冲突）：

- `raise_if_cancelled()` 抛 `TurnCancelled` 时**不再清 checkpoint**；`main.py::chat` 捕获 `TurnCancelled` 返回的 `_aborted_payload` 增加 `resumable_turn_id=turn_id`。
- `bind_turn/clear_turn` 保持现状（只清取消标记，不清 checkpoint）。checkpoint 的 TTL（默认 24h）由 checkpointer 自身管理，独立取消 TTL（30min）。
- `save_exchange` 只在正常完成 / 用户「放弃」时写；取消保留现场时跳过（沿用现有 `request.is_disconnected()` 跳落库逻辑，不产生幽灵消息）。

**hard 回环注意**：verify 未通过回 `select_tools` 时会覆盖 checkpoint 分支；list() 按 parent 链保存，续跑取最新即可，不丢分支。

### 1.4 长期记忆：事实/偏好抽取 + 巩固 + 召回

> **状态：已实现（2026-11-20）**。新增 `backend/memory/`（`store.py` + `service.py` + `controller.py` + `module.py` + `entity/dto.py`），独立库 `memory.sqlite`；召回注入 role prompt 的**副本**，抽取在落库之后 daemon 线程异步执行；trace 增 `memory` 节点。开关：`CHATVEIN_MEMORY`（默认开）、`CHATVEIN_MEMORY_AUTO_ACCEPT`（默认关，候选制）、`CHATVEIN_MEMORY_EXTRACT_TURN_INTERVAL`（默认 1）。

#### 现状（证据）

- Agent 框架内无自动长期记忆；只有工具驱动的 `mcps/tools/kb.py`（`kb_add_note` / `kb_search`）和按 `actor_id` 隔离的短期记忆。
- `kb.sqlite` 已具备向量 + 关键词检索能力，可复用为召回后端，但需与「自动记忆」分离（避免污染用户手动知识库）。

#### 目标

1. 跨会话自动抽取事实/偏好（如「用户偏好中文回复」「项目用 Python 3.11」），经用户确认后写入。
2. 记忆有作用域（全局 / 角色 / 会话）、置信度、来源 turn、时间；支持巩固（合并重复）、遗忘（TTL / 用户删除）。
3. 每轮对话前召回相关记忆注入 system，不喧宾夺主（条数/token 上限）。

#### 方案

**新库 `backend/memory/`**（模块，b 级）：`module.py`（`/api/memories`）+ `controller.py` + `service.py` + `repository.py` + `entity/{entity,dto}.py`。

**存储**：`<data>/memory.sqlite`（独立，跨会话），表 `memories(id, scope, scope_id, kind, content, facts_json, confidence, source_turn_id, created_at, updated_at, expires_at)`；sqlite-vec 映射表复用 `kb_vec_map` 模式（可选，向量模型就绪才用）。

**写入流程（抽取 → 确认 → 落库）**：

1. 每轮正常完成后（在 `_chat_turn` 落库之后，异步 fire-and-forget，不阻塞用户）调用 `memory.service.extract(turn_id, user_msg, assistant_msg)`。
2. `extract` 用主模型 `invoke_structured` 输出 `MemoryCandidate{items:[{kind, content, confidence}]}`，`kind ∈ {preference, fact, project, person}`。
3. **可发现 + 可确认**：候选不直接生效，标记 `status=pending`；前端设置页/侧栏提供「记忆管理」抽屉，用户确认/编辑/删除（可配置为自动确认 `CHATVEIN_MEMORY_AUTO_ACCEPT=1`，默认关闭以护隐私）。
4. 巩固：`service.consolidate()` 定期合并高相似候选（向量/关键词），提升 confidence 或合并内容；TTL 到期软删除。

**召回流程**：

- 在 `main.py::_chat_turn` 取 history 后、`assemble_context` 前，调用 `memory.service.recall(query=req.message, scope_ids=[role_id, conversation_id], limit=8, max_tokens=512)`。
- 召回结果注入 `role_runtime["prompt"]` 的 `# Memory` 段（与技能目录注入同位置，`main.py:296-321` 附近），或作为 `ChatState.extras["memories"]` 传给 `assemble_context`（推荐后者，避免污染角色定义）。
- trace 记 `note("memory", detail={"recalled_ids": [...], "tokens":…})`，`_path` 加 `memory` 节点。

**脱敏**：`extract` 前用正则过滤疑似密钥/token/手机号/邮箱（复用 `models/crypto.py` 的敏感字段识别思路），命中的片段不写入。

1. **不做 `extras["memories"]`**：`role_runtime` 是跨轮缓存的，改写它会串记忆。实现改为 `recall_into_role()` 返回浅拷贝后只改副本的 `prompt`，因此 `agents/context.py`、`graphs/state.py` 未改动（次数比评审稿少动 2 个 b 级文件）。

### 2.1 token 级流式（SSE）

> **状态：已实现（2026-11-19）**。新增 `agents/streaming.py`（ContextVar 事件桥 + `StreamSink`）、`POST /api/chat/stream`；直答走 `model.stream()`，ReAct 走 `stream_mode=["values","messages"]` 只推纯文本增量；工具进度/阶段事件由中间件与图节点上报。前端 `backendStream`（`client.ts`）+ `sendChatStream`；拿不到可读流 / 后端 409 时自动回落旧接口。开关 `CHATVEIN_STREAM`（默认开）。

#### 现状（证据）

- 全仓无 `StreamingResponse`；`sendChat`（`src/api/conversations.ts:118`）是一次性 POST，靠 `turn_id` 轮询 `GET /traces/{turn}` 看进度。
- `invoke_react`（`graphs/common.py:339`）已用 `agent.stream(..., stream_mode="values")`，但只在内部迭代取最后一份状态，未对外推流。
- 前端 `useChatSession` 用乐观气泡 + 轮询补齐，**没有 token 级增量渲染**。

#### 目标

1. 助手回复逐 token（或小 chunk）推送到前端，边生成边显示，首次可见时间显著缩短。
2. 流式与现有 trace 轮询共存：流式是「加速体验」，trace 是「权威记录」，二者不互相替代。
3. 取消、工具调用、审批打断时流能正确收尾（发 `done`/`cancelled`/`error` 终止事件）。

#### 方案

**协议**：新增 `POST /api/chat/stream`，`text/event-stream`。事件类型：

```text
event: token      data: {"turn_id","text":"增量文本"}
event: tool       data: {"name","status","tool_call_id"}     # 工具开始/结束
event: approval   data: {"request_id","kind","command"}      # 需要 HITL 审批（见 2.2）
event: trace      data: {"node":"understand|plan|react|verify"}  # 阶段切换
event: done       data: {"reply","tokens","duration_ms",...完整旧响应字段}
event: error      data: {"code","message","retryable"}        # 见 总纲 §4.3
event: cancelled  data: {"turn_id","resumable":true}
```

**后端**：

- `main.py` 新增 `@app.post("/api/chat/stream")` → 一个 `async def` 用 `StreamingResponse(generator)`。generator 内部仍需把重活放到工作线程，但**流 sink 必须是线程安全的队列**：
  - 新增 ContextVar `stream_sink`（`backend/agents/streaming.py`），在 `_run_chat_heavy` 与 `bind_turn` 一起设置。
  - `sink.push(event)` 把事件写入 `queue.Queue`，异步 generator 侧 `await asyncio.to_thread(queue.get)` 取出 yield（不阻塞事件循环）。
- **token 来源**：LangChain 模型用 `astream_events(version="v2")` 或在 `create_agent` 层加 `stream_messages` 回调拿 token chunk。最小侵入方案：在 `build_react_graph` 的 middleware 里挂一个 `after_model` 钩子，从 `AIMessage.content` 的增量文本推 `token` 事件（内容块级，非严格逐 token，但足够「边生成边显示」）。若模型 SDK 原生支持 token chunk，用 `astream_events` 的 `on_chat_model_stream` 事件升级为逐 token。
- `simple.py` 的 `model.invoke` 改 `model.stream()`，逐块推 `token`。
- `done` 事件携带与现有 `/api/chat` **完全相同**的响应体（`run_pipeline` 结果 + 落库后的消息），前端拿到后走与今天一致的收尾逻辑。
- 落库时机不变（仍在 `_chat_turn` 末尾、`request.is_disconnected()` 判断之后）；流结束前必须先发 `done`，再关闭 generator。
- **降级**：`CHATVEIN_STREAM=0` 或客户端不接受 SSE → 走旧 `/api/chat`。

**前端**：

- `src/api/client.ts` 新增 `backendStream(endpoint, body, {signal, onEvent})`：复用 `getBackendUrl` / token 注入 / AbortController 语义，用 `@tauri-apps/plugin-http` 的 `fetch` 拿 `ReadableStream`，按 `\n\n` 切 SSE 帧解析。
- `src/api/conversations.ts` 新增 `sendChatStream(...)`，参数与 `sendChat` 对齐，多传 `onEvent`。
- `useChatSession`：优先走 stream，把 `token` 事件 append 到助手气泡；`done` 事件替换成权威消息；`error`/`cancelled` 走现有失败/停止清理路径。轮询 trace 保留但降频（仅拿结构化阶段信息）。
- 停止：现有 `cancelChat` + AbortController 双管齐下不变；收到 `cancelled` 事件后按 1.3 保留现场。

#### 改动文件

| 文件 | 等级 | 改动 |
|---|---|---|
| `backend/agents/streaming.py` | b | 新建：stream_sink ContextVar + 事件模型 + 队列桥 |
| `backend/main.py` | a | 新增 `/api/chat/stream` 路由；`_run_chat_heavy` 设置 sink |
| `backend/agents/graphs/common.py` / `simple.py` | a | middleware / 直答节点推 token 事件 |

#### 风险与回滚

- **Tauri HTTP 插件的 SSE 兼容性**：设计评审阶段先做 spike（小 demo 验证 `plugin-http` 能逐块读流）；若不稳，保留 `EventSource` 不可用的回退 = 现有轮询，功能不阻断。

### 2.2 统一 HITL 审批（interrupt 断点）

> **状态：已实现（2026-11-19）**，实现位置与评审稿有出入（见末节「实现纪要」）：审批设施落在**工具层**（`backend/mcps/approval.py`），而不是图内 `approval_node` + `Command(resume)`；图内 interrupt 留给 2.3 外部 MCP 危险工具时再补。开关 `CHATVEIN_UNIFIED_APPROVAL`（默认开，设 0 回退旧 `bash_approval`）；超时 `CHATVEIN_APPROVAL_TIMEOUT`（默认 120s）。

#### 现状（证据）

- 审批在工具执行层：`bash_approval.create_pending()` / `wait_decision()`（`mcps/bash_approval.py`），内存 dict + 120s 超时；`path_access.py` 会话外访问复用同一确认弹窗。
- 图里**没有** `interrupt()`（全仓 `graph.compile()` 无 checkpointer，彻底查无中断）；`Agent与功能.md` 明确写「HITL 审批节点不在图内」。
- 前端 `BashApproval.tsx` 监听审批事件并回传 decision。

#### 目标

1. 把「Bash / 文件越界 / 外部 MCP 危险工具 / 长期记忆写入」等所有需人工确认的动作，统一到一个 `interrupt` 断点设施。
2. 审批状态可持久化（依赖 1.3 checkpointer）：进程重启后未决审批不丢；用户可稍后从其他入口批准。
3. 保留现有工具层审批作为兼容路径，逐步迁移。

#### 方案

**设施**：基于 1.3 的 checkpointer + LangGraph `interrupt()`（需 `interrupt` 挂 checkpointer，正好具备）。

**新增 `backend/agents/approval.py`**（b 级）：

```python
@dataclass
class ApprovalRequest:
    request_id: str
    kind: str            # bash | path | mcp_tool | memory_write
    title: str           # 人话标题
    detail: str          # 命令 / 路径 / 工具名 + 参数
    risk: str            # low | medium | high
    tool_call_id: str | None

def request_approval(req: ApprovalRequest) -> ApprovalDecision: ...
```

- 在 ReAct 图的工具调用前插入一个 `approval_node`：检查工具名/参数是否命中审批策略 → 命中则 `interrupt(req)` 暂停图，把 request 推到 `stream_sink` 的 `approval` 事件（2.1）→ 等待前端通过新接口 `POST /api/approvals/{id}/decision` 提交 → `Command(resume=decision)` 恢复图。
- **审批策略集中化**：新增 `backend/mcps/approval_policy.py`，合并现有 `bash_policy.classify` / `path_access` / 外部 MCP 工具风险等级，返回 `allow | ask | deny` + `ApprovalRequest`。现有策略函数保留作底层判定。
- **持久化**：审批请求与决定写会话库 `approvals(request_id, turn_id, kind, payload_json, status, decision, created_at, decided_at)`；未决请求在会话加载时可查询/恢复。
- **超时**：默认 120s（`CHATVEIN_APPROVAL_TIMEOUT`），超时按「拒绝」处理并推事件；超时线程里也要 `raise_if_cancelled` 可打断。
- **兼容**：`bash_approval.wait_decision` 保留；迁移期两套并存，`CHATVEIN_INTERRUPT_APPROVAL=1` 时走新路径。

**前端**：`BashApproval.tsx` 扩展为通用 `ApprovalDialog`，识别 `kind` 渲染不同详情（命令 / 路径 / 工具 + 参数 / 记忆内容）；新增 `src/api/approvals.ts` 提交决定；`useChatSession` 收到 `approval` 事件弹窗。

### 2.3 真 MCP 协议客户端（stdio / SSE / Streamable HTTP）

> **本能力推翻 `Agent与功能.md` 既有边界**：由「刻意不做外置 MCP 子进程」改为「内置工具优先，外置 MCP 按需 opt-in」。评审通过后须同步修订 `Agent与功能.md` §「刻意不做」与 `Agent与功能.md`。
>
> **状态：已实现（2026-11-19）**。`Agent与功能.md` 与 `Agent与功能.md` 已同步修订。开关 `CHATVEIN_MCP_EXTERNAL=0`（默认开）；`mcp` SDK 缺失时全量降级，内置工具不受影响。实现与评审稿的差异见末节「实现纪要」。

#### 现状（证据）

- 全仓搜 `mcp.client|stdio_client|sse_client|ClientSession|FastMCP|import mcp` = 0；依赖中无 MCP SDK。
- `mcp-http` 仅前端占位（`McpSection.tsx`）；`web.py` 的 Claw Search 是普通 HTTP API，不是 MCP 会话。
- 工具注册表 `registry.py` 静态汇总 `tools/__init__.py::build_tool_groups()`，无动态发现。

#### 目标

1. 用户可在设置页配置外部 MCP server（命令启动 stdio / SSE URL / Streamable HTTP URL），动态发现其工具并纳入现有工具注册表。
2. 外部工具与内置工具**同等待遇**：参与选型、角色白名单、trace、审批策略、结构化错误。
3. 连接失败/超时不拖垮会话，降级为「该 server 不可用」并在目录标注。

#### 方案

**依赖**：引入官方 `mcp` Python SDK（提供 `ClientSession` + `stdio_client` / `sse_client` / `streamablehttp_client`）。为控制打包体积，做**可选依赖 + 延迟导入**：未配置任何外部 server 时不 import。

**新增 `backend/mcps/external/`**（b 级）：

- `config.py`：server 配置模型（name / transport / command|url / env / headers / enabled / allow_tools），存主库新表 `mcp_servers`（迁移 v14）+ 前端设置页 CRUD。凭据走 `models/crypto.py` 加密，不明文落库/日志。
- `client.py`：`McpClientManager` 单例，维护每个 server 的连接会话。
  - stdio：`async with stdio_client(...)` 启动子进程；生命周期由管理器持有，后端退出时统一 close（对齐 Rust 监督逻辑，避免孤儿进程）。
  - SSE / Streamable HTTP：`sse_client` / `streamablehttp_client`，带 header token。
  - **线程桥接**：LangGraph 在工作线程跑，MCP 客户端是 asyncio；用每条 server 一个后台事件循环线程 + `asyncio.run_coroutine_threadsafe` 调 `session.list_tools()` / `call_tool()`，超时由 `concurrent.futures` 控制。
- `adapter.py`：把 MCP 工具适配成 LangChain `BaseTool`（name 加前缀 `mcp__<server>__<tool>` 防冲突；`args_schema` 由 MCP `inputSchema` 转 Pydantic；`_run` 调 `call_tool`），异常映射为 1.2 的 `ToolResult` code（`MCP_SERVER_DOWN` / `TOOL_TIMEOUT`）。

**注册表接入**（`registry.py` / `tools/__init__.py`）：

- `refresh_tool_groups()` 末尾 merge 外部工具分组 `mcp-ext::<server>`；`tool_catalog` / `tool_groups` 自动包含。
- 角色白名单 `expand_allowlist` 支持 `mcp-ext::<server>` 分组 id 与 `mcp__<server>__<tool>` 工具名。
- 外部工具加入 `ALWAYS_ON_TOOLS` 之外，仍走选型；风险等级高的外部工具默认进审批策略（2.2）。
- 热重载：`PUT /api/mcp-servers` 后调 `refresh_tool_groups()` 重建；前端目录即时刷新。

**降级**：`CHATVEIN_MCP_EXTERNAL=0` 完全不加载外部工具；SDK 缺失时导入失败只记 warning，不影响内置工具。

与评审稿的差异：

1. **不是「每条 server 一个事件循环」**，而是 **一个进程级后台 loop + 每条 server 一个常驻协程**。anyio 的取消作用域要求「进入与退出在同一个任务」，把 `AsyncExitStack` 拆到每次 `run_coroutine_threadsafe` 调用上会在关闭时抛 `cancel scope in a different task`。
2. **接口用 `PATCH` 而非 `PUT`**，且只在请求体里出现的键才覆盖：凭据没传 = 保留原密文，传 `{}` = 清空。否则「改个名称」会把 token 清掉。
3. **前端新建独立 `McpExternalSection.tsx`**，没有改动 `McpSection.tsx`（内置工具那块是只读展示，混在一起会让状态机变复杂）；`prefs.ts` 也不再需要外部分组元数据——分组从 `/api/mcps/catalog` 与 `/api/mcp-servers/` 直接读。
4. **连接时机**：`lifespan` 只起后台线程（`state.startup`），请求路径只读缓存。评审稿写的「PUT 后调 `refresh_tool_groups()`」改为 CRUD 后 `state.refresh(id)`，效果相同但不重建内置工具。
5. **SSRF 放宽**：远程地址只校验协议与云元数据主机，**放行 localhost / 内网**——本地 SSE server 是主流用法，且地址由用户手填；这与「模型能读到网页里的内网 URL」的场景不同。
6. **错误码**：`MCP_SERVER_DOWN` / `TOOL_TIMEOUT` / `TOOL_DENIED` 通过异常上的 `tool_code` 直达 `ToolResult.code`，不是塞进文案。
7. **测试策略**：用 `FastMCP` 起真子进程（stdio 全链路），而不是 mock `ClientSession`——后者测不出 `cancel scope` 与进程清理问题。

未做（与评审稿「风险与回滚」对应）：`tools/build_backend.ps1` 的冻结配置未改，`mcp` 已进 `backend/requirements.txt`，冻结时会随依赖一起打进去；若确认体积敏感，再改成 opt-in extras。

### 2.4 多 agent 并行编排（fan-out + 聚合）

> **状态：已实现（2026-11-19）**。开关 `CHATVEIN_PARALLEL_DELEGATE`（设 `0` 回退串行）、并行度 `CHATVEIN_DELEGATE_MAX_PARALLEL`（默认 4，上限 8）、整批上限 `CHATVEIN_DELEGATE_BATCH_TIMEOUT`（默认 420s）。实现与评审稿的差异见末节「实现纪要」。

#### 现状（证据）

- `delegation.py::delegate_to_agent` 是单一工具，主 agent 在 ReAct 里调用；成员用自己模型/工具/独立记忆，**同步串行**等待返回。
- 无并行 fan-out、无共享任务板、无专用聚合器；花名册经 `ContextVar` 注入，防递归（成员不挂 delegate）。

#### 目标

1. 主 agent 能把一个任务拆成多个子任务**并行**派给多个成员（`fan-out`），而不是一个个等。
2. 有共享任务板记录子任务状态，结果由专用聚合步骤汇总后交回主 agent，减少主 ReAct 负担。
3. 保持对现有「@ 指派单个成员」链路的兼容；不引入嵌套派发。

#### 方案

**新增 `backend/agents/orchestration.py`**（b 级）：

- `parallel_delegate` 工具（替代/增强 `delegate_to_agent`）：入参 `{tasks: [{role_id, task, instruction}]}`。
- 并行执行：用 `ThreadPoolExecutor(max_workers=CHATVEIN_DELEGATE_MAX_PARALLEL=4)` 并发调用现有 `delegation.py::_run_member`（每个成员仍独立模型/工具/记忆/ContextVar）。
  - **ContextVar 传递**：`copy_context().run(_run_member, …)` 每个任务复制主线程的 trace/sandbox/turn 上下文；成员写 trace 用派生 span，避免串台（现有 `delegation` 已按 actor_id 隔离记忆，这里补 trace 隔离）。
- **任务板**：会话库 `agent_tasks(turn_id, task_id, role_id, status, result_json, error_code, created_at, updated_at)`；每个子任务开始/结束更新状态，trace 可见。
- **聚合**：`aggregate(results)` 复用主模型做一次结构化汇总（`AggregateDecision{synthesis, conflicts[]}`），失败则退化为拼接各成员回复（带「成员 X 认为…」前缀）。
- **与主 ReAct 的衔接**：`parallel_delegate` 返回聚合文本作为 ToolMessage 回灌，主 agent 继续其 ReAct；`snapshot`/`delegate` 工具与现有 `@` 指派不变。
- **限额**：并行度上限、单成员超时（沿用 medium 的 300s）、总墙钟超时；取消时 `raise_if_cancelled` 在等待 `future.result()` 时也能打断（轮询 future + cancel check）。
- **开关**：`CHATVEIN_PARALLEL_DELEGATE=0` 回退到现有串行 `delegate_to_agent`。

#### 风险与回滚

- **ContextVar 串台**：每任务 `copy_context()` + 独立 span；测试断言成员 A 的工具不写到成员 B 的 workspace。
- **资源放大**：并行度 + 单成员次数上限 + 总超时三重约束；成员上限沿用现有 medium 级。
- **结果冲突**：聚合输出 `conflicts[]` 提示主 agent，不强行裁决；由用户/主模型判断。
- **回滚**：开关关闭回到同步串行，现有 @ 指派链路不变。

#### 验收

- 3 成员并行子任务，墙钟耗时 < 串行之和；任务板 3 条状态齐全；聚合结果进入主 agent 最终回复。
- 1 成员失败不影响其他成员，trace 标 `error_code`。
- 关闭开关后团队模式行为与当前一致。

#### 实现纪要（2026-11-19）

先说结论：**并行只能由工具内部开线程池**。LangGraph 对同一条 AIMessage 里的多个 `tool_call`
是顺序执行的，让模型「连发多次 delegate」不会并行；因此新增 `parallel_delegate`，模型侧只表达
「一次派发 N 条子任务」。

与评审稿的差异（按影响从大到小）：

1. **trace 隔离不是「派生 recorder」**，而是共享 recorder + 锁 + 显式父节点。
   派生 recorder 会让 SSE 的 `on_change` 收到两份快照，前端还得合并；共享 + `RLock` 只是在
   并行成员之间串行化几十微秒的记账，更简单也更容易保证事件顺序。
2. **取消不改 `cancellation.py`**：`_fan_out` 用 `concurrent.futures.wait(..., timeout=0.2)` 循环，
   每轮调一次 `raise_if_cancelled`，命中就 `future.cancel()` + 抛出；`executor.shutdown(wait=False)`
   不等待在跑的成员（成员内部每个节点都会检查取消位，会自行退出）。
3. **聚合没有 `conflicts[]` 结构化输出**：ToolMessage 只回文本，多一层 JSON 只会多一个解析失败面；
   改在聚合 system prompt 里要求「有冲突时指出分歧」。模型不可用 / 调用失败时退化为
   「### 成员名 + 回复」拼接，不丢内容。
4. **单成员异常按失败隔离**：`run_member_task` 自身不吞异常（保持串行语义），由 `_fan_out`
   在每个 future 外围捕获（`TurnCancelled` 除外，它必须向上冒泡结束整轮）。
5. **任务板字段简化**：`result` 存纯文本（不是 `result_json`），`finished_at` 代替 `updated_at`；
   状态 `running/done/failed/cancelled`。前端只提供 `listAgentTasks` 封装，**未新增任务板 UI** ——
   trace 树里已有 `delegate:成员` 子树，任务板定位为排查/自动化接口。
6. **开启时两个工具都挂**：`parallel_delegate` 负责无依赖的多路任务，`delegate_to_agent` 留给
   「必须拿到上一步结果」的串行场景；`CHATVEIN_PARALLEL_DELEGATE=0` 或并行度=1 时只挂后者，
   与「关闭开关回到当前行为」一致。
7. **上限**：单次最多 8 条子任务（超出丢弃并在结果里说明），整批 420s；单成员仍用
   `delegation.py` 的 300s deadline 与步数上限，不额外放大。

### 3.1 沙箱加固（不做容器）

> **状态：已实现（2026-11-20）**。新增 `backend/mcps/sandbox_guard.py` + `backend/mcps/audit.py`；沙箱 / bash / powershell 统一走 `run_limited()`（env 清洗 + 限额 + 黑洞代理），`sandbox_run_python` 额外注入 `sitecustomize` 网络钩子；`ALWAYS_ON_TOOLS` 改为 `always_on_tools(role)`。
> 开关：`CHATVEIN_SANDBOX_GUARD=0`（整体回退）、`CHATVEIN_SANDBOX_LIMITS=0`、`CHATVEIN_SANDBOX_NETWORK=1`、`CHATVEIN_SANDBOX_CPU_SECONDS` / `_MEMORY_MB` / `_FILE_MB`、`CHATVEIN_SANDBOX_ENV_PASSTHROUGH`、`CHATVEIN_PIP_INDEX_URL`、`CHATVEIN_AUDIT=0`。

#### 现状（证据）

- `sandbox.py::sandbox_run_python`（L186-227）用 `env = os.environ.copy()` 继承**完整宿主环境**（可能含 API Key / `CHATVEIN_TOKEN`）；`shell=False`、超时 ≤120s，但无网络出口限制、无内存/CPU/磁盘配额。
- `sandbox_pip_install` 包名正则校验、≤8 个/次，但可拉任意 PyPI 包（供应链风险）；无镜像审计。
- `bash.py` / `powershell.py` 是普通子进程，可联网、可读环境变量；审批只发生在工具入口，Python 自身 I/O 可绕过路径策略。
- `ALWAYS_ON_TOOLS`（`common.py:94`）含 `sandbox_run_python`，**绕过角色白名单**无条件挂载。

#### 目标

1. 执行子进程时默认不继承敏感环境变量（token / API Key / 凭据），需要白名单才能透传。
2. 限制沙箱进程的网络出口与资源（CPU 时间 / 内存 / 磁盘写入 / 进程数），用平台原生机制，不引入容器。
3. `pip install` 支持镜像白名单 + 可选离线锁文件；常驻代码工具可禁用。
4. 所有加固可被工具层感知并给模型可读提示（不静默失败）。

#### 方案

**新增 `backend/mcps/sandbox_guard.py`**（c 级）：

- `sanitize_env(base: dict) -> dict`：从 `os.environ` 去掉敏感键（正则 `KEY|TOKEN|SECRET|PASSWORD|CREDENTIAL|CHATVEIN_TOKEN|API`），只保留白名单（`PATH`/`SYSTEMROOT`/`LANG`/`PYTHONIOENCODING`/`VIRTUAL_ENV` 等）。`sandbox_run_python` / bash / powershell 统一调用。敏感键命中记 trace（只记键名，不记值）。
- **资源限制**：
  - Python：用 `resource.setrlimit` 在 POSIX 设 `RLIMIT_CPU` / `RLIMIT_AS` / `RLIMIT_FSIZE`；Windows 无 `resource`，用 `subprocess.CREATE_JOB_OBJECT` + `JobObjectLimit`（Windows API via ctypes），限额 CPU/内存/进程数。封装 `apply_limits(process) -> cleanup`，跨平台。
  - 复用现有 `timeout` 作为最后兜底。
- **网络出口**：**评审确认（2026-11-19）：按最容易的方式实现**，不引入容器 / 防火墙规则 / 管理员权限：
  - 唯一开关 `CHATVEIN_SANDBOX_NETWORK=0`（默认禁用网络）控制；只用「Python `sitecustomize` hook + 黑洞代理环境变量」两层软隔离，跨平台一致。
  - **层 1（脚本进程）**：在会话 `runs/.venv` 里预置一份 `sitecustomize.py`（Python 启动时自动 import），在脚本代码执行前 patch `socket.socket` 的 `connect` / `connect_ex` / `create_connection`：对非本地地址（白名单 `127.0.0.1` / `::1` / `localhost`）直接抛错。仅影响走该 venv 的 `sandbox_run_python`，实现简单、无需管理员权限。用户脚本若显式 `del`/重绑 `socket` 可绕过 → 明确标注为**软隔离、非安全硬边界**。
  - **层 2（Shell / 子进程）**：对 bash / powershell / 沙箱进程统一注入黑洞代理环境变量（`HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` = `http://127.0.0.1:9`），让依赖代理的 HTTP 客户端默认连不通；不依赖代理的直连 socket 不受限，同样只作软约束。
  - 需要在沙箱内联网时：`CHATVEIN_SANDBOX_NETWORK=1` 关闭两层限制，联网需求优先引导用 `web_search` / `web_fetch`（它们不受沙箱网络开关影响，且自带 SSRF 防护）。
  - 工具层：给模型提示「当前沙箱网络已禁用，联网请用 web_search / web_fetch」，并在 trace / 审计记录实际生效模式。
- **pip 加固**：`sandbox_pip_install` 从 `CHATVEIN_PIP_INDEX_URL`（默认官方镜像）取源，禁止 `file://` / 本地路径 / `--trusted-host` 任意值；支持 `requirements.lock`（会话内）固定版本。
- **常驻工具可禁用**：`ALWAYS_ON_TOOLS` 改为函数 `always_on_tools(role)`：若角色 `tools` 显式不含 `sandbox_run_python`（或新增 `deny_tools` 字段），则不挂载。修正「空列表=不限制」与「常驻绕过」的冲突语义——默认仍常驻保证体验，只有显式拒绝才移除。
- **审计**：沙箱进程启动/结束/超限写 `audit.sqlite`（见 3.2）；输出截断沿用 `clip()`，但超限写入审计而非丢弃。

与评审稿的差异：

1. **env 清洗用「按类别黑名单」而非纯白名单**：白名单会把 `JAVA_HOME` / `GOPATH` / 自定义 `NPM_CONFIG_*` 一起砍掉，脚本会莫名跑不起来。现在只删敏感类别（`KEY/TOKEN/SECRET/PASSWORD/CREDENTIAL/AUTH/COOKIE/SESSION/API`）与全部 `CHATVEIN_*`，验收要求（打印 `os.environ` 不含 token/key）仍然成立。
2. **`sitecustomize` 不放 `site-packages`**：实测宿主只要设了 `PYTHONPATH`（IDE / 启动脚本很常见），`import sitecustomize` 会先命中宿主那份，venv 里的钩子根本不生效。改为写 `runs/.chatvein-guard/sitecustomize.py` 并**前置**到子进程 `PYTHONPATH`，同时把钩子注入 bash / powershell（shell 里起的 python 也受控）。
3. **`apply_limits(process)` 改为 `run_limited(cmd, ...)`**：Windows Job Object 必须在 spawn 之后立刻拿到 pid/句柄，而 `subprocess.run` 不暴露进程对象，包一层执行器才能跨平台一致。
4. **bash / powershell 与沙箱共用同一执行器**：评审稿只要求「沙箱进程」限额，但 shell 才是最容易跑飞的入口；统一后 `shell.exec` 也有了审计记录（限额仍宽松，可用 `CHATVEIN_SANDBOX_LIMITS=0` 回退）。
5. **`deny_tools` 不落库**：用角色 `tools` 里的 `!工具名` / `-工具名` 表达显式拒绝（运行时也认 `deny_tools` 键，留给 3.2 的权限模型接管），因此没有迁移、没有改角色 DTO / 前端表单。
6. **pip 未做 `requirements.lock`**：只固定源（`CHATVEIN_PIP_INDEX_URL`，强制 http(s)）与包名白名单；锁文件固定版本的价值等到 3.2 配额 / 供应链策略一起做。
7. **审计粒度**：一次执行写一条 `sandbox.exec`（带 `duration_ms` + `result_code`：`OK` / `FAILED` / `TIMEOUT` / `SIGNAL` / `SPAWN_FAILED`），env 清洗另写一条 `sandbox.env`（只含被移除的键名）。启动/结束拆两条会让事件数翻倍，回放价值不变。

### 3.2 细粒度权限 + 审计日志

> **状态：已实现（2026-11-20）**。规则 DSL 落成扁平字段（路径 / URL / 只读 SQL），`deny_tools` 不落库（继续用角色 `tools` 的 `!` / `-` 前缀），审计沿用 `audit.sqlite`，配额为进程内计数。实现细节与偏差见文末「实现纪要」「与评审稿的差异」。

#### 现状（证据）

- 权限是角色级粗粒度白名单（`tools` 分组 id / 工具名），`registry.resolve_tools/invoke_tools/catalog` 无工具级鉴权；无配额、无安全审计（trace 是功能追踪，非审计）。
- 审批态仅内存 dict（`bash_approval.py`），无持久化/审计；3 个常驻工具绕过白名单（3.1 处理）。

#### 目标

1. 权限从「工具名/分组」细化到「参数级 / 路径级 / 数据级」，用声明式策略表达。
2. 全量工具调用（含内置/外部/MCP）写不可篡改语义的审计日志，支持查询与回放。
3. 配额：按会话/工具限制调用次数与频率，超限自动拒绝并提示。

#### 方案

**新增 `backend/mcps/permissions.py`**（b 级）：

- 策略模型 `PermissionRule(scope, effect, tool, conditions)`，`conditions` 支持：
  - 参数约束：`{"tool":"web_fetch","url_host_in":[...]}`、`{"tool":"sqlite_query","read_only":true}`；
  - 路径约束：`{"tool":"read_text_file","path_prefix":"session:output/**"}`（复用 `path_access` 解析）；
  - 数据约束：外部 MCP 工具的字段白名单。
- 决策 `check(tool_name, args, ctx) -> allow|ask|deny + reason`：与 2.2 `approval_policy` 合并——`ask` 直接产 `ApprovalRequest`；`deny` 由 1.2 结构化错误返回 `TOOL_DENIED`。
- **默认最小权限**：未知工具默认 `ask`；全局默认策略随分发，`CHATVEIN_PERMISSION_MODE=strict|normal`（默认 `normal` 保持体验，`strict` 为最小权限）。
- 配置：策略存 `<data>/permissions.json`（用户可编辑）+ 主库索引；设置页提供可视化编辑（简单模式：工具勾选；高级模式：JSON）。

**审计 `backend/mcps/audit.py`**（e 级）：

- 库 `<data>/audit.sqlite`，表 `audit_events(seq INTEGER PRIMARY KEY AUTOINCREMENT, ts, actor, scope, action, tool, args_redacted_json, result_code, duration_ms, decision, decision_by)`。
- 只追加（应用无 UPDATE/DELETE 路径）；敏感字段脱敏后写（复用 3.1 sanitize 思路）。
- 接入点：1.2 的 `resilient_tool_middleware`（每次工具调用、`ToolResult.code`）+ 2.2 审批决定 + 3.1 沙箱事件。
- 新接口 `GET /api/audit/events?tool=&since=&limit=`（main.py + audit controller），设置页「审计日志」只读视图。

**配额**：`permissions.py::QuotaGuard` 按 `(conversation_id, tool)` 计数，规则来自配置（默认宽松）；与现有 `ToolCallLimitMiddleware`（按次数）互补——这里是**用户可配**的运营级配额。超限返回 `TOOL_DENIED(code=QUOTA_EXCEEDED)`。

行为要点：

- **判定顺序**：`permissions.json` 的 `rules` 按列表顺序取第一条命中；未命中时 `strict` → `ask`、`normal` → `allow`（空策略 = 3.2 之前的老行为，删文件即可回滚）。
- **拦截位置**：ReAct 中间件最外层，先于「同参去重 / 熔断」。否则模型看到的是「重复调用」而不是「权限被拒绝」，会无意义重试。
- **`ask`**：复用 `approval.py::request_approval`，审批 id 仍是 `(turn_id, tool_call_id)` 确定性哈希，续跑复用历史决定；用户拒绝 / 超时归为 deny 并写 `tool.deny`。
- **`deny`**：返回 `ToolMessage` + `tool_result.code=TOOL_DENIED`，正文提示「换工具/参数或请用户改规则」。
- **配额**：`(会话, 工具)` 与本轮总调用两个上限，默认 0（不限），进程内计数、重启清零。
- **配置容错**：解析失败退回空配置 + normal，`/api/permissions` 暴露 `error`，并按文件版本只写一条 `permission.config` 审计；判定函数自身异常兜底 `allow`（权限设施坏了不能锁死应用）。
- **开关**：`CHATVEIN_PERMISSION_MODE=strict|normal`（环境变量优先于文件）、`CHATVEIN_PERMISSIONS_PATH`、`CHATVEIN_AUDIT=0`。

1. **规则 DSL 是扁平的，不是 `(scope, tool, conditions)` 嵌套**：`effect` + `tool` 通配 + `path_prefix` / `path_not_prefix` / `url_host_in` / `read_only`（同时给出即 AND）；OR 语义拆多条规则。评审稿的「外部 MCP 字段白名单」未实现——字段级约束要等真实 server schema 稳定，先靠 `url_host_in` + `tool` 通配覆盖。
2. **`deny_tools` 不落库、没有 v15 迁移**：角色 `tools` 里的 `!` / `-` 前缀（3.1 起）已能表达显式拒绝，参数级 / 路径级拒绝交给 `permissions.json`；策略不进主库，唯一事实来源就是那个 JSON 文件。
3. **审计不写「判定 + 结果」两条**：`allow` 只写一条 `tool.call`（带 `result_code` + `duration_ms`），`deny` / 用户拒绝 / 超时写一条 `tool.deny`，`decision_by` 记录是规则、模式还是用户。事件数减半，回放信息不丢。
4. **配额默认关闭且进程内计数**：这是运营级「防跑飞」阀，不是计费；落库会引入清理与漂移问题，重启清零可接受。
5. **离线直调 `ask` 按拒绝**：`invoke_tools` 没有弹窗通道，`ask` 会跳过并说明原因（安全优先，绝不静默放行）。
6. **权限设施异常兜底 `allow`**：`check()` 抛异常返回 allow + 原因（`by="fallback"`），`static_deny` 异常返回 `None`；但配置语法错误不静默（见上）。
7. **没有审计「回放 UI」**：接口返回脱敏后的 `args`，设置页只读表格 + 工具/判定过滤。播放器对安全排查没有增量价值。
8. **前端只做 JSON 编辑 + 模板，没做可视化勾选**：条件组合空间用表单表达会失真；模板 + 摘要列表比半吊子表单可靠。

### 3.3 eval 闭环 + OTel 可观测

> **状态：已实现（2026-11-20）**。eval 在 `backend/eval/`（用例 `backend/eval/cases/`），judge 默认关闭（`--judge` 才开），规则断言必跑；OTel 只在 `CHATVEIN_OTEL=1` 时启用且 SDK 不进安装包；指标是查询时聚合的 JSON，没有 `trace_metrics` 表。详见文末「实现纪要」「与评审稿的差异」。

#### 现状（证据）

- 有完整自研 trace（span / LLM / 工具 / token，落 `session.sqlite.turn_traces`），但无离线 eval 集、无 LLM-as-judge、无质量指标回归；`hard.verify` 是唯一运行期自检。
- 无结构化事件导出（OTel）、无指标告警。

#### 目标

1. 建立可回归的 eval 集与运行器：给定 case 输入 → 跑管线 → LLM-as-judge 打分 → 出报告，纳入 CI/发版门禁。
2. 把现有 trace 桥接到 OTel（可选导出）：span / LLM 调用 / 工具 / token 以标准语义输出，便于接入外部 APM。
3. 从 trace 聚合质量指标（成功率、重试率、取消率、平均 token/耗时），设置告警阈值。

#### 方案

**eval 模块 `backend/eval/`**（c 级）：

- Case 格式 `evals/cases/*.json`：`{id, message, difficulty, expect_tools[], expect_substring[], rubric}`。
- `runner.py`：批量跑 `run_pipeline`（离线/直连模式，不依赖桌面壳）→ 收集 `reply/tool_trace/trace`。
- `judge.py`：`LLM-as-judge` 结构化打分（`relevance/correctness/tool_use/format`，0-5），可关（关闭时只用规则断言：`expect_substring` / `expect_tools`）。
- 命令 `tools/run_eval.ps1` → `python -m eval.runner --report eval-report.json`；CI 门禁：规则断言通过率 100%、judge 均分 ≥ 阈值（阈值评审确认）。
- 与 prompt registry（总纲 §4.4）联动：报告带 `prompt_version`，可对比不同 prompt 版本质量。

**OTel 桥接 `backend/trace/otel.py`**（c 级）：

- 可选依赖 `opentelemetry-sdk` + 导出器（OTLP HTTP / console）；未安装或 `CHATVEIN_OTEL=0` 时 no-op。
- `OtelBridge` 作为 trace callbacks 的附加 handler：把 `trace.recording` 的 span 事件映射到 OTel Span（属性：turn_id / difficulty / tool / tokens / duration / error_code），父子关系沿用现有 span 树。
- 不替换现有落库 trace（桌面端离线可用），两者并行；OTel 只是可选导出。

**指标聚合 `backend/trace/metrics.py`**（c 级）：

- 从 `turn_traces` 聚合：按天/角色的成功率、取消率、工具失败率、平均 tokens/耗时、P95 延迟；写 `trace_metrics` 表或生成 JSON 报告。
- 前端「洞察」页可展示趋势；告警阈值超限时在设置页提示（本地告警，不外发）。

- **LLM-as-judge 成本**：默认规则断言必跑、judge 可选（`--no-judge`）；CI 用便宜模型或本地规则。

- 开 `CHATVEIN_OTEL=1` 配 console 导出，追踪窗与 OTel 输出节点一致。

行为要点：

- **硬门槛与软评分分离**：`check_rules`（工具是否被调用、回复是否含关键 / 禁用片段、回复非空）必跑；`--judge` 只影响「分数」不影响「能不能跑」，避免模型抖动把评测本身弄坏。
- **临时会话沙箱**：每条用例 `create_conversation_dir()` + `use_conversation_sandbox()` + `bind_turn()`，跑完 `remove_conversation_dir()`——工具的文件 / 命令落在一次性目录，不污染用户工作区，也不会因为没有沙箱直接失败。
- **退出码**：`0` 全通过；`1` 有 fail / error / 预算跳过；`2` 用例文件不合法或没有可用模型。接 CI 只需要执行这一步。
- **时间预算而非硬超时**：`--max-seconds` 到点就不再开新用例；单条硬超时会留下无法安全终止的线程与在途请求，宁可标记跳过。
- **OTel 时间轴**：`base = now - elapsed_ms`，每步 `start = base + start_ms`、`end = start + elapsed_ms`，所以外部 APM 的瀑布图和追踪窗一致；导出放在 `tracing` 的 `finally`，取消与报错也留痕。
- **指标口径**：轮次指标来自 `turn_traces` 摘要并按 `days` 过滤；工具失败率来自最近 `scan`（默认 100）轮 payload 扫描——两者分母不同，报告里分开列出，前端只展示失败次数。
- **告警门槛**：窗口内 ≥5 轮才判定（错误率 ≥20% warn / ≥40% critical，取消率 ≥30% warn，工具失败率 ≥50% warn），少量样本不报警。

与评审稿的差异：

1. **用例目录 `evals/cases/` → `backend/eval/cases/`**：跟着包走，后端冻结/打包时不用再补一条资源路径。
2. **`--no-judge`（评审稿）→ `--judge`（实现）**：默认就是关，不需要反向开关；CI 只跑规则断言即可。
3. **没有 `trace_metrics` 表**：指标是查询时从追踪聚合出来的视图，落表会引入清理与口径漂移；`GET /api/conversations/{id}/metrics` 直接返回 JSON（带 `schema_version`）。
4. **`prompt_version` 联动未做**：prompt registry（§4.4）还没落地，报告先带 `role/model_id`；等 registry 有了再补版本字段，避免先造一个假字段。
5. **`OtelBridge` 不是 trace callbacks 的附加 handler**：回调拿到的是整棵树的快照，逐帧 diff 既容易错、也会丢父子关系；改为 `tracing()` 结束时一次性导出。实时性换成正确性，外部 APM 拿到的是完整瀑布图。
6. **OTel 依赖不进 `requirements.txt`**：桌面安装包不该为可选导出多背体积；`pip install opentelemetry-sdk`（要 OTLP 再加 `opentelemetry-exporter-otlp-proto-http`）即可，缺依赖静默跳过。
7. **前端指标条幅放在追踪窗侧栏**，不是「洞察」页：`InsightPanel` 是产物 / 线程视图，健康度属于追踪上下文，放一起才能「看到告警 → 点进某轮」。
8. **复查修正（2026-11-20）**：`otel.py` 两处缺陷——①父 span 原先用 `start_span(parent=...)` 传，真实 SDK 的 `Tracer` 只认 `context=`（`set_span_in_context`），会 TypeError 并被 `export_turn` 吞掉，导致整轮 span 全丢；现改为 `_parent_kwargs()` 按是否有 OTel 依赖走 `context` / `parent` 两条路。②根 span 收尾时没带 `elapsed_ms`，结束时间等于开始时间，瀑布图里父比子短；现补整轮耗时，并在测试里断言「根覆盖所有子 span」。
9. **可读性整理（2026-11-20，行为不变）**：`metrics.py` 的 `compute_metrics` 拆成 `_within / _overall / _day_rows / _difficulty_rows / _alerts` 五个分块，状态分桶与 `totals` 取值收敛成 helper（未知状态统一算 `error`，坏 `totals` 不再可能崩接口），阈值/窗口/回看轮数提成命名常量并由 service / controller / 前端共用；`otel.py` 建 span 与收尾抽成 `_start_span / _start_step_span / _set_root_attributes / _finish`，去掉隐式 kwargs 与伪 step 字典；`eval` 的规则字段、报告 schema、judge 阈值各留一处常量，`--dry-run` 不再手抄字段名；`trace/store.py` 三处 JSON 解码合并成 `_decode_payload`。指标口径已用「旧版 vs 新版同输入逐字段对照」验证，唯一差异是负值 token / 耗时统一按 0 计（旧版日/难度维度会显示负数）。
10. **用例暂不支持按例准备文件**（评审稿也没要求）：沙箱是空的，先只覆盖「不需要预置本地文件」的用例；要测文件类工具再加 `${case_dir}` 约定。
11. **没有 CI 门禁接线**：仓库当前没有 workflow 文件，先把退出码规范好（`0/1/2`），接入 CI 是纯配置动作，不阻塞能力交付。

### 4.3 统一错误模型（`AgentError`）

#### 现状（证据）

- **对外只有两种错误形状**，没有统一错误体：FastAPI 默认 `{"detail": "文字"}`，以及 SSE 的 `{"code","message","retryable","turn_id"}`。
- 对外错误面分散在 **12 个文件、65 处 `raise HTTPException`**（`main.py` 17 处 + 11 个 `controller.py` 共 48 处），全部走 FastAPI 默认 `{"detail": 文字}`；`detail` 质量参差：`main.py:243`（对话失败）走 `model_error_hint(exc) or f"对话失败：{exc}"`，其余多处直接 `str(exc)` 原样透出（`main.py:939` 工作区、`main.py:1059` db tables、`main.py:1072` db detail、`main.py:1091` db backup）。
- SSE `error` 事件（`main.py:626` 组帧、`main.py:671-682` 生产）：`code` 只有 `chat_failed` 一个值、`retryable` 硬编码 `true`、`message` 可能是 `null`（`llm.py:109-125` 的 `model_error_hint` 认不出就返回 `None`）。
- **后端错误码已存在，但只在工具层**：`mcps/tool_result.py:17-27` 定义 `TOOL_OK/TOOL_FAILED/TOOL_DENIED/TOOL_TRANSIENT_EXHAUSTED/TOOL_CIRCUIT_OPEN/TOOL_SKIPPED/TOOL_TIMEOUT/MCP_SERVER_DOWN`（模块级常量，不是 Enum）；`external/adapter.py:26` 的 `ExternalToolError.tool_code` 是唯一自带 code 的异常。
- **「可重试」靠字符串猜**，且分散三处：`llm.py:75-84` `is_rate_limit_error`（特征表 `llm.py:62-72`）；`mcps/resilience.py:124-151` `classify_exception`（isinstance + 字符串 + `status_code` + `errno`）；`graphs/common.py:451-468` `_failed_tool_names`（逐行正则 + 中文关键词），被 `concise_failure`（`common.py:471-493`）用来拼最终文案。
- **后端码到不了前端**：`ToolResult.code` 只出现在审计表（`src/api/audit.ts:12` `result_code`）。`src/api/client.ts:117-118` 的 `HttpError` **没有 code 字段、且未 export**；`backendStream`（`client.ts:320-323`）非 2xx 抛普通 `Error`；`httpErrorMessage`（`client.ts:234-247`）只认 `detail`/`message`。
- `useChatSession` 用**字符串匹配**判分支：流式回落（`useChatSession.ts:378-384` 判 `StreamUnsupportedError` 或 message 含「流式已关闭」）、`isAbortError`（`useChatSession.ts:94-99`）；SSE `error` 只取 `message`（`useChatSession.ts:371-374`），`code`/`retryable` 被丢弃。

#### 目标

1. **错误码单一来源**：一个模块定义全部 code + 人话文案 + 可重试性 + HTTP 映射，`tool_result.py` 的 `TOOL_*` 并入同一取值域（旧名字继续可用）。
2. **一处分类**：`classify(exc)` 是唯一「异常 → code」判定点；字符串特征匹配集中在该模块内，`is_rate_limit_error` / `classify_exception` / `_failed_tool_names` 改为复用而非自建规则。
3. **对外错误体统一**：REST 与 SSE 都带 `code/retryable/stage`，**同时保留顶层 `detail` 字符串**（不破坏既有前端与脚本）。
4. **前端按 code 决策**：`HttpError` 带 `code/retryable/detail` 并导出；`useChatSession` 依据 code 决定「可重试 / 去配置 / 丢弃断点 / 静默」。
5. **可观测**：code 进 trace（step 级 `error_code`、轮级 `error_code`），指标可按 code 聚合。

#### 方案

**（a）新建 `backend/errors.py`（d 级契约层）**：只依赖标准库，`agents/`、`mcps/`、`trace/` 都能 import 而不产生循环依赖（`mcps` 不能反向依赖 `agents`，这是放根目录的原因）。

```python
# 取值域：模块级常量（与 tool_result.py 现有风格一致，不用 Enum）
MODEL_AUTH / MODEL_CONFIG / MODEL_RATE_LIMIT / MODEL_TIMEOUT / MODEL_NOT_FOUND / MODEL_FAILED
TOOL_OK / TOOL_FAILED / TOOL_DENIED / TOOL_TRANSIENT_EXHAUSTED / TOOL_CIRCUIT_OPEN /
TOOL_SKIPPED / TOOL_TIMEOUT / MCP_SERVER_DOWN
SANDBOX_VIOLATION / CHECKPOINT_EXPIRED / CANCELLED / EVAL_CASE_INVALID / INTERNAL

@dataclass(slots=True)
class AgentError(Exception):
    code: str
    message: str                 # 人话，直接给用户看
    retryable: bool = False      # 默认来自 code 表，允许调用点覆盖
    stage: str = ""              # understand|context|react|tool|stream|resume|db
    detail: dict | None = None   # 仅内部/日志，默认不外发
    status_code: int = 500       # 取 HTTP_STATUS[code]
```

- `to_dict(with_detail=False)` → `{"code","message","retryable","stage"}`；`detail` 默认不外发（避免把底层 request_id / 路径漏给 UI）。
- `MESSAGES: dict[code, str]`：**唯一**人话表（例：`MODEL_RATE_LIMIT` →「模型供应商限流，自动重试后仍未通过：稍后再试，或在「模型」里换一条更宽松的线路」）。
- `HTTP_STATUS`：`MODEL_AUTH 502`、`MODEL_CONFIG 409`、`MODEL_RATE_LIMIT 429`、`MODEL_TIMEOUT 504`、`MODEL_FAILED 502`、`TOOL_DENIED 403`、`SANDBOX_VIOLATION 403`、`CHECKPOINT_EXPIRED 409`、`INTERNAL 500`。
- `classify(exc, *, stage="") -> AgentError` 判定顺序：①已是 `AgentError`（补 stage）②`getattr(exc,"tool_code")` ③`isinstance`（`TurnCancelled`→`CANCELLED`、`PermissionError`→`TOOL_DENIED`、`TimeoutError`→`MODEL_TIMEOUT`…）④`status_code`（401/403→`MODEL_AUTH`、404→`MODEL_NOT_FOUND`、429→`MODEL_RATE_LIMIT`、≥500→`MODEL_FAILED`）⑤字符串特征（`_RATE_LIMIT_MARKERS` / `_TIMEOUT_MARKERS` / `_CONNECT_MARKERS`）⑥`INTERNAL`。`model_error_hint` 的结果优先塞进 `message`（保留「供应商原话 + request_id」体验）。

#### 目标

1. 提示词的**身份、版本、渲染入口**集中一处：代码里出现提示词时能回答「这是哪个模板、第几版」。
2. 版本进 trace（轮级 `prompts`）与 eval 报告，让「改 prompt → 质量变化」可对比（补上 3.3 遗留的 `prompt_version` 缺口）。
3. 配置不新增第二套开关系统：本批新增开关统一走一个读取函数；旧开关不强制迁移，但默认值在 `docs/运维手册.md` 有唯一表格。

#### 方案

**（a）新建 `backend/agents/prompt_registry.py`（d 级）**

```python
@dataclass(frozen=True, slots=True)
class PromptSpec:
    name: str        # "router.understand" / "agent.medium" / "hard.plan" ...
    version: str     # 人工维护，如 "v3"
    template: str    # 原始文本（含 $var 占位）
    tags: tuple[str, ...] = ()

class PromptRegistry:
    def register(self, spec: PromptSpec) -> None   # 重名/重版本 → ValueError（导入期就炸）
    def get(self, name: str) -> PromptSpec
    def render(self, name: str, **vars) -> str     # string.Template.substitute
    def versions(self) -> dict[str, dict]          # {"router.understand": {"version":"v3","fingerprint":"ab12cd34"}}
```

- **占位用 `string.Template`（`$var`）而不是 f-string**：f-string 要求占位在定义处就存在，模板无法集中；`Template` 还能对未知变量报 `KeyError`，直接指出缺哪个变量。
- `fingerprint = sha1(template)[:8]`：防「改了文本忘了改版本号」。trace 与 eval 报告同时写 `version` 与 `fingerprint`，不一致即说明漂移。
- 注册点在**各模块导入期**调 `register()`，不是让 registry 反向 import：`prompt_registry` 只依赖 `string`/`hashlib`，避免被 `agents/*` 循环依赖。

**（b）本批只做「登记 + 版本 + 渲染入口」，不搬文本**

理由：把 12 处文本一次性搬进新模块，等于在同一个 PR 里同时改「治理设施 + 全部提示词」，质量回归无法归因（3.3 刚建立 eval 基线，正是为了能归因）。因此：

- 各模块保留自己的常量作为文本来源，导入期 `registry.register(PromptSpec(...))`；
- 已有拼装函数（`build_agent_system`、`judge._prompt` 等）改为从 registry 取 spec 再 `render`，**输出字符串逐字不变**（靠现有测试 + eval `--dry-run` 校验）；
- 后续新增提示词必须走 registry，禁止再写裸常量。

登记清单（11 个 spec）：`router.understand`、`tool.selector`、`agent.simple`、`agent.medium`、`agent.hard`、`hard.plan`、`hard.verify`、`orchestrate.aggregate`、`context.summary`、`memory.extract`、`eval.judge`。技能目录 / 记忆召回块属于**运行时数据**，不是模板，不登记。

**（c）trace 与 eval 联动**

- `TraceRecorder` 增 `prompt_versions`，`snapshot()` 输出 `prompts: {"agent.medium": {"version":"v3","fingerprint":"ab12cd34"}}`；**只记本轮真正用到的**（simple 轮不记 `agent.hard`），由各节点 `note()` 带 `used_prompts`、`tracing()` 结束时按 `difficulty` 取并集。
- `TraceWindow` 侧栏加一行「提示词」：显示本轮用到的 spec 版本与数量（只读，不做编辑器）。
- `eval/runner.py` 报告增 `prompts`（registry 快照）+ 每条结果的本轮 spec 版本，形成「改 prompt → 跑 eval → 比报告」闭环；`--dry-run` 额外校验 registry 完整性（未注册 / 重名 / 指纹与版本不一致 → 退出码 `2`）。

**（d）配置治理（轻量，本批不做全量迁移）**

- 新建 `docs/运维手册.md`：把附录 30+ 个 `CHATVEIN_*` 整理成「变量 | 默认值 | 文件:行 | 一句话」，作为唯一表格；后续新增开关必须同步此表。
- 新建 `backend/agents/config.py`（e 级）只提供 `flag(name, default) -> bool` 与 `number(name, default, lo, hi)`：**本批新增的开关全部走它**；旧调用点不强制迁移（避免一次性碰 20 个文件），在 `docs/运维手册.md` 标「待迁移」。
- 不做运行时改配置的 UI 与热加载：桌面端改开关需重启，避免同进程两套默认值。

#### 风险与回滚

- **「登记」把提示词变成启动期依赖**：注册失败（重名）会在 import 期抛错，等于后端起不来。缓解：`register()` 只做常量登记、不读文件不联网；重名属开发期错误，`test_prompt_registry.py` 先拦住。
- **渲染改动引入空白差异**：`Template.substitute` 与 f-string 对换行/尾随空格的差异会导致 prompt 文本变化 → eval 分数抖动。缓解：`render` 输出与旧常量逐字比对（单测里做 `assert render(...) == 旧常量`）。
- **版本号沦为形式**：只写 `version` 不更新等于没有。缓解：`fingerprint` 与 `version` 双写，eval `--dry-run` 与报告对不上就报错。
- **回滚**：`CHATVEIN_PROMPT_REGISTRY=0` 时 `render` 直接返回原常量（等价于不启用）；trace 不写 `prompts` 字段；eval 报告退回 3.3 的字段集。

#### 验收

- 同一轮对话的 trace 里能看到 `prompts` 及其 `version/fingerprint`；把 `agent.medium` 改一个字、不升版本 → eval `--dry-run` 退出码 `2` 并指出是哪个 spec。
- 改动前后 prompt 文本逐字一致（单测断言），eval 冒烟用例结果不变。
- `npm run build` + `npm test` + `pytest` 通过。

### 4.7 成本预算与模型 fallback（本批新增编号）

> 总纲 §2 横切行写的「token/成本预算、模型降级与 fallback」此前没有编号，本批补为 4.7。

#### 现状（证据）

- **有「窗口预算」，没有「成本预算」**：`agents/token_budget.py` 已有 `estimate_text_tokens`（:59）、`count_message_tokens`（:98）、`ContextBudget`（:114，四段窗口预算）、`resolve_budget`（:144，读 `context_window_k` / `max_tokens` / `CHATVEIN_CTX_WINDOW`）。它回答的是「这轮能不能塞进上下文」，**不回答「这轮花了多少钱、要不要收手」**。
- **没有 fallback**：`models/service.py:1-7` 明示「不再区分主/默认模型、不存在回退链」；实体字段（`models/entity/entity.py:20-47`）= `id,name,provider,model_id,base_url,api_key,temperature,max_tokens,presence_penalty,frequency_penalty,stream,json_mode,retries,context_window_k,enabled,description,created_at,updated_at`，无备用模型引用、无价格字段。
- 唯一客户端工厂 `agents/llm.py::get_chat_model`（:239，仅 `openai`/`deepseek` 两条线路，:227）：`model_id` 空 / `enabled=False` / key 空 → 返回 `None`（:254-261），**上层只能降级成「不调模型」**，没有「换另一个模型继续」的路径。
- 每次调用的用量已经落 trace：`totals`（`recording.py:472-484`）= `input_tokens/output_tokens/total_tokens/llm_calls/tool_calls/llm_ms/tool_ms`（+cached/reasoning）；`metrics.py` 已有均值与 P95。**数据齐了，缺的是判定与收敛**。
- 放大成本的地方：并行派发（`orchestration.parallel_delegate`，默认并行度 4、批次上限 420s）、hard 的 plan/verify、上下文摘要、judge。这些都没有总额约束。

#### 目标

1. 每轮有**可选的 token 预算**：到阈值不再继续调工具，强制基于现有信息收尾（不是硬中断、不留半截答案）。
2. 主模型不可用时**按配置降级到备用模型**，且只降级一次、只在「本轮还没有产出」时降级。
3. 成本与降级都进 trace，追踪窗能看出「这轮花了多少、有没有降级」。

#### 方案

**（a）预算 `backend/agents/cost.py`（c 级）**

```python
@dataclass(slots=True)
class TurnBudget:
    token_limit: int      # CHATVEIN_TURN_TOKEN_BUDGET，默认 0 = 关
    used_input: int = 0
    used_output: int = 0
    def exceeded(self) -> bool
    def note_usage(self, usage: dict) -> None      # 由 TraceHandler.on_llm_end 之后回灌

def resolve_budget() -> TurnBudget                 # 读 env + 模型 max_tokens，默认 0 表示不限
def turn_usage() -> TurnBudget                     # ContextVar，与 tool_scope 同生命周期
```

- 挂载点在 ReAct 循环的 `wrap_tool_call` 之前：超预算时**改走「收尾」而不是拒绝工具**——注入一条 `HumanMessage`（「已达到本轮预算，请基于已有信息给出结论」）并禁用后续工具调用，本轮正常收尾落盘。理由：硬砍会造成半截答案与幽灵气泡（2.1/1.3 的老坑）。
- 计数来源只用 trace 已经拿到的 `usage`（不额外估算、不重复调用分词器）；`note_usage` 在 `on_llm_end` 回调里顺手回灌，避免两套计量口径。
- 预算默认 **0（关闭）**：桌面端单轮几百 token 是常态，默认限死会误伤；开启是给重度用户/评测用的阀，不是计费。
- 成本（金额）本批**只做可选展示**：`models` 表若填了 `price_input`/`price_output`（每百万 token，追加列、可空）则 `cost.py` 估算金额，未填就只报 token。**不内置价格表**（供应商改价频繁，内置等于长期错误），也不做币种换算。

**（b）fallback**

- `models` 表追加 `fallback_config_id`（`db.py` 迁移 v15，追加列 + 幂等，`SCHEMA_VERSION=14 → 15`）；外键不建（模型可被删除，悬空引用按「无 fallback」处理）。
- `llm.py` 新增 `with_fallback(model, fallback)`：返回一个**轻量包装对象**，只实现 `invoke` / `with_structured_output().invoke`（即**结构化调用**：router / tool_selector / plan / verify / summary / memory / judge）——这些是单次调用，降级语义清晰。
- **流式主循环不包装**：中途换模型会把两种风格的增量混在一起（且已推给前端无法撤回）。主循环失败仍走 4.3 的 `MODEL_*` 错误 + 前端「再试一次」。
  > **实现修正（2026-11-20）**：`graphs/simple.py` 的直答路径在**尚未吐字**时也走一次降级（换备用模型 + 一次性 `invoke`），因为此时没有增量可混；已吐字则原样抛出。判定与取备统一收在 `llm.py::try_fallback`，不在调用点各写一套。
- 降级触发条件（全部满足才降）：①`classify(exc).retryable` 为真且 code ∈ {`MODEL_AUTH`, `MODEL_RATE_LIMIT`, `MODEL_TIMEOUT`, `MODEL_NOT_FOUND`, `MODEL_FAILED`}；②已配置且 `enabled=True` 的 `fallback_config_id`；③本轮**尚未因降级切换过**（每轮最多一次，防抖与防循环）；④不处于取消中。
- 降级留痕：`note("model_fallback", status="warn", from_config=..., to_config=..., code=...)`；`snapshot()` 加轮级 `model_fallback: {from, to, code}`；`TraceWindow` 顶部条幅提示「本轮已降级到 <name>」（用现有 `config_name` 字段展示）。
- `resolve_budget()` 与 fallback 的模型参数（温度、max_tokens）各自独立：备用模型用自己的配置，不继承主模型参数。

**（c）开关**

| 开关 | 默认 | 含义 |
|---|---|---|
| `CHATVEIN_TURN_TOKEN_BUDGET` | `0` | 单轮 token 上限；`0` = 不限（只统计不干预） |
| `CHATVEIN_MODEL_FALLBACK` | `1` | `0` 关闭降级（已配置的备用模型也不生效） |
| `CHATVEIN_PRICE_CURRENCY` | 空 | 仅展示用币种符号，不做换算 |

#### 风险与回滚

- **`db.py` 迁移是 a 级**：只追加可空列 + 幂等，`SCHEMA_VERSION=15`；回滚不需要改库（旧代码忽略新列），但**降级字段一旦被写入，旧版本会静默忽略**——所以回滚只回行为，不回数据。
- **降级掩盖真实故障**：连续降级会让用户以为主模型正常。缓解：降级必留 `model_fallback` note + 前端条幅，且不改变 `success_rate` 口径（指标里单列 `fallback` 计数）。
- **预算误伤长任务**：默认 `0`（关），只有显式设置才生效；超限是「收尾」不是「报错」，落盘与追踪照常。
- **金额口径**：价格由用户填、只做展示，避免内置价目表的长期错误；没有价格时只报 token。
- **回滚**：`CHATVEIN_TURN_TOKEN_BUDGET=0` + `CHATVEIN_MODEL_FALLBACK=0` 即回到今天的行为。

#### 验收

- 设 `CHATVEIN_TURN_TOKEN_BUDGET=5000` 跑一个多工具任务：轮次正常收尾、trace 里能看到预算命中、没有半截气泡。
- 配置一个错误 key 的主模型 + 一个正常备用模型：结构化步骤（路由/工具选择）自动降级，trace 有 `model_fallback`，UI 顶部提示降级目标。
- 迁移在既有库上重复执行两次无副作用；`pytest` 全绿。

#### 与原设计的偏差（有意为之）

1. **提示词不搬文本、也不在导入期 `register()`**：注册表用 `ast` 读源码字符串常量，避免把「提示词版本」变成启动期依赖与循环依赖；代价是 `verify()` 只能校验「源符号存在 / id 唯一 / 常量可读」，不能做 `Template.substitute` 渲染校验。`CHATVEIN_PROMPT_REGISTRY` 开关取消——没有需要回滚的运行时行为。
2. **fallback 不做成 `with_fallback(model, fallback)` 包装**：降级逻辑收在 `try_fallback` 一处（`invoke_structured` 与 `graphs/simple.py` 共用），调用点无需各自判断；模型实例构造时打 `_chatvein_config_id` / `_chatvein_config_name` 私有标记，分别用于找回备用配置与在追踪里显示可读名字。
3. **降级触发码收窄为 429 / 超时 / 5xx**：鉴权错（`MODEL_AUTH`）与「模型名不存在」不降级——多半是配置填错，备用模型往往同样失败，只会掩盖真因。
4. **金额只做展示**：单价由用户在模型表单填（每百万 token），未填只报 token；不内置价目表、不做币种换算（`CHATVEIN_PRICE_CURRENCY` 只影响符号）。
5. **配置口径统一到「新开关 + 本次触碰的开关」**：`mcps/resilience.py`、`agents/orchestration.py`、`token_budget.py` 的数值开关保留各自的钳位函数（有上下限、支持小数），已在 `docs/运维手册.md` 第 5 节标注。

### 已确认口径与遗留项

1. **`backend/errors.py` 放根目录而不是 `agents/`**：为了让 `mcps/` 也能 import 而不产生 `mcps → agents` 反向依赖。是否接受把「契约层」放在 `backend/` 根（与 `db.py` 同级）？
2. **错误体双写 `detail` + `error`**：保留 `detail` 是为了不破坏既有前端与外部脚本。是否同意长期保留（而不是计划内移除）？
3. **`TOOL_*` 常量迁到 `errors.py`**（`tool_result.py` 只 re-export）：会动一个被 `registry`/`common`/`resilience`/审计广泛引用的模块，但只是移动定义、旧路径可用。是否接受？
4. **4.4 不搬提示词文本**：本批只做登记 + 版本 + trace，文本留在原模块。是否同意「搬文本」拆到后续单独一批（便于 eval 归因）？
5. **配置治理只做文档 + 新开关入口**：旧的 30+ 处 `os.getenv` 不强制迁移。是否接受（否则本批会扩散到 20 个文件）？
6. **成本只做 token 预算，金额可选**：不内置价目表、不做币种换算，价格由用户在模型表单填。是否需要把价格换成「按模型 ID 内置默认价」？
7. **fallback 的覆盖面**（已按主流做法落地）：结构化调用全量 + 直答**尚未吐字**时换线重跑（此时无增量可混）；正文流中途不换模型，失败仍交前端「再试一次」。若要让正文流也换线，只能做成「失败后整轮重跑并撤回已推内容」，另开一项。
