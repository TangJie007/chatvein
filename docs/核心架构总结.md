# ChatVein 核心架构总结

> 面向面试：本文聚焦“真正干活的核心”——Agent 编排流水线、工具系统、工作区沙箱、双层持久化、可观测与请求编排。
> 设计决策见《设计架构总结》，取舍哲学见《实现思想总结》，图细节权威来源是 `docs/agent-graphs.md`。

---

## 1. 核心是什么：**LangGraph 驱动的“理解→路由→分档执行→核对”流水线**

整个应用的能力心脏在 `backend/agents/`。一次 `/api/chat` 的本质是：把用户原文送进一张**总图**，先“理解并判难度”，再按难度进入 **simple / medium / hard** 三张子图之一。全程默认走**主模型**；角色可覆盖模型与生成参数。

```text
用户原文
   │
   ▼
┌──────────────────────────────────────────────┐
│ chat_pipeline（agents/graphs/pipeline.py）     │
│  START → understand（改写 + 难度路由）          │
│           ├─ simple  → simple 子图  → END       │
│           ├─ medium  → medium 子图  → END       │
│           └─ hard    → hard 子图    → END       │
└──────────────────────────────────────────────┘
   │
   ▼
run_pipeline 组装 reply / difficulty / tool_trace / trace
   │
   ▼
HTTP 落库（主库 + 会话库）+ 工作区洞察
```

| 模块 | 文件 | 职责 |
| --- | --- | --- |
| 入口 | `agents/service.py` → `run_chat` | 对外唯一聊天入口 |
| 总图 | `agents/graphs/pipeline.py` | understand + 条件边分流 |
| 理解/路由 | `agents/router.py` | 主模型 structured：`rewritten` + `difficulty` |
| simple | `agents/graphs/simple.py` | 无工具单节点直答 |
| medium | `agents/graphs/medium.py` | 选型 → ReAct（`create_agent`） |
| hard | `agents/graphs/hard.py` | plan → 选型 → ReAct → verify（可回环） |
| 选型 | `agents/tool_selector.py` | 工具缩集 + 角色白名单展开（允许空集） |
| 状态 | `agents/graphs/state.py` | `ChatState` TypedDict |
| 记忆 | `agents/memory.py` | 历史 → LangChain messages |
| 共用 | `agents/graphs/common.py` | `last_text` / `build_react_graph` / `merge_tool_traces` |

## 2. 共享状态 `ChatState`（图的“数据总线”）

`ChatState` 是 TypedDict，节点间通过它传值。关键字段：

```text
message          用户原文（HTTP 传入）
rewritten        改写后意图（下游只用这个，原文不替换用户气泡）
difficulty       simple | medium | hard
route_reason     路由理由
history          短期记忆（不含本轮用户句）
role             RolesService 运行时（可为空）
selected_tools / candidate_tools / tool_plan_reason
reply / used_llm / tool_trace
# hard 专用
plan / plan_text / verify_passed / verify_reason / verify_focus / verify_round
```

- **条件边只读 `difficulty`**：`hard → hard 子图`，`medium → medium`，否则 `simple`。
- **角色提示叠加**：`_merged_system(role, BASE)` 把角色 prompt 叠在“挡位 system”之上，避免丢掉工作区/工具约定。

## 3. 三档子图详解

### 3.1 simple（直答，无工具）
```text
START → chat → END
```
单次 `model.invoke([SystemMessage, …history, HumanMessage(rewritten)])`。闲聊/单句知识问答走这里，成本最低。

### 3.2 medium（选型 → ReAct）
```text
START → select_tools → react → END
```
- `select_tools`：主模型从“已注册全量工具”里按改写文本选子集；`allowed` 经 `expand_allowlist`（分组 id 如 `mcp-web` 展开为组内工具名）；**允许空名单**（认为无需工具就直答，不强行塞默认工具）。
- `react`：`create_agent(model, tools, system)` 编译 agent⇄tools 循环，`recursion_limit = 2×n+10`（默认 34），抽最后文本为 `reply`，`extract_tool_trace` 记录工具调用。
- 适合“一两跳工具就能答”的任务；空转靠“工具/模型调用上限”收束。

### 3.3 hard（plan → 选型 → ReAct → verify，可回环）
```text
START → plan → select_tools → react → verify
                      ▲                    │
                      └── 未通过且未达上限 ──┘
```
- `plan`：结构化 `TaskPlan`（goal / steps / success_criteria / risks），生成给人看的【执行计划】块。
- `select_tools`：查询串拼上 `plan_text`（若有 `verify_focus` 追加“上一轮未通过，请优先补…”）。
- `react`：`recursion_limit` 默认 42（`2×16+10`），便于“改代码→跑→看 stderr→再改”。
- `verify`：结构化 `VerifyDecision`（passed / reason / missing / next_focus），对照计划与 tool_trace 核对。
  - `passed` → 结束；
  - 未过且 `verify_round < 2` → 写 `verify_focus` 回 `select_tools` 再执行；
  - 达 2 轮仍不过 → **强制视为通过并收束**（防无限循环）；
  - 离线 → 有非空 reply 即通过。
- `tool_trace` **跨轮累计**，整轮追踪更完整。

## 4. 工具系统（进程内“MCP”，而非外置子进程）

工具是 Agent 能力的“手脚”。设计要点：

- **进程内 LangChain `@tool`**：不另起 `npx @playwright/mcp` 之类 Node 子进程，直接在当前 Python 进程里调用，体积小、启动快、与 `builtin://` 设计对齐。
- **注册表 + 按名 invoke**：`mcps/registry.py` 维护“工具名 → 实现”；`tool_selector` 只缩名字集，`resolve_tools(names)` 解析成可调用对象（名字无效回落全量）。
- **分组（MCP id）对齐前端**：`mcp-fs` / `mcp-web` / `mcp-sqlite` / `mcp-kb` / `mcp-codesandbox` / `mcp-bash` / `mcp-powershell` / `mcp-browser` / `mcp-ip` / `mcp-ocr` / `core` / `mcp-http`，与设置页 `MCP_SERVERS` 对齐。
- **能力探测（运行时决定注册与否）**：Bash（按需下 MinGit，失败则降级 PowerShell）、PowerShell（仅 Windows）、Browser（本机有 Chromium 才注册）、OCR/Web/IP 有各自降级链。**未探测到运行时不注册该分组**——避免在 Agent 里调用不存在的能力。
- **人工确认（HITL）不在图里**：Bash/PowerShell 的危险或写盘命令在“工具执行路径”上挂起，等前端 `BashApproval` 弹窗批准/拒绝（`/api/bash/{approve,deny}`）。这是把“不确定的人审”放在图节点之外，避免把对话阻塞在图状态机里。

工具矩阵（节选，详见 `docs/agents.md`）：

| 分组 | 代表工具 | 说明 |
| --- | --- | --- |
| `core` | `get_current_time` / `calculator` / `get_system_info` | 时间/时区/计算/本机概况 |
| `mcp-fs` | `read_file` / `write_file` / `edit_file` / `list_directory` | 工作区文件读写（范围受限） |
| `mcp-web` | `web_search` / `web_fetch` | 多级降级搜索/抓取 |
| `mcp-sqlite` | `sqlite_tables` / `sqlite_query` | **只读**查主库 |
| `mcp-kb` | `kb_add_note` / `kb_search` | 笔记沉淀 + 向量/关键词召回 |
| `mcp-codesandbox` | `sandbox_run_python` | 会话 `runs/` 内 venv + 跑 Python |
| `mcp-bash` / `mcp-powershell` | `bash_run` / `powershell_run` | 限会话目录 + 危险拦截 + 确认 |
| `mcp-browser` | `browser_navigate` / `browser_click` / … | 进程内 Playwright |
| `mcp-ip` / `mcp-ocr` | `lookup_ip_region` / `ocr_image` | 免费降级链 |

## 5. 工作区沙箱（两层工作区，安全隔离的核心）

这是核心架构里最容易讲错、也最容易出彩的点。

```text
<主工作区 workspace_root>                （用户配置/容器，非真正沙箱）
  └─ <YYYYMMDD-HHMMSS-xxxxx>/             （会话工作区 = 真正的沙箱）
       output/       产物（用户需要的文件）
       logs/
         session.sqlite   本会话：短期记忆 / 工具返回 / 推理 / 追踪
       runs/        代码沙箱 .venv 与脚本（与产物隔离）
       uploads/     用户输入框拖入/选择的文件落盘处
       ocr_input/   OCR 图片落点
```

- **主工作区**：用户在设置页配置（或 `CHATVEIN_WORKSPACE`），落到 `CHATVEIN_DATA_DIR/workspace`。它是“容器”，Agent 不直接把它当沙箱。
- **会话工作区**：在主工作区下为每个会话生成 `YYYYMMDD-HHMMSS-xxxxx` 目录，才是 Agent 真正读写文件的**真正工作区**。
- **沙箱上下文**：`use_conversation_sandbox(workspace_dir)` 用 `contextvars` 把“当前会话目录”绑到线程上下文；此后 `current_sandbox()` / `resolve_in_sandbox()` 都相对会话目录。所以**工具实现无需知道会话 id**，只问“当前沙箱在哪”。
- **硬规则**：给 Agent 用的文件（上传图片/附件）必须落进**当前会话工作区**（带 `conversation_id` 调用 `/api/uploads`），否则新会话沙箱找不到它——“找不到图片”类报错的常见根源。
- **删除会话级联清工作区**：删除会话时一并删该 `YYYYMMDD-...` 目录，天然隔离、易清理。

## 6. 双层持久化（核心数据架构）

| 库 | 位置 | 内容 | 技术 |
| --- | --- | --- | --- |
| 主库 | `CHATVEIN_DATA_DIR/chatvein.db` | 会话、消息、模型、角色 | SQLModel（SQLAlchemy2 + Pydantic） |
| 向量 | 同主库 `vec0` 虚拟表 | embedding 检索 | sqlite-vec（逐连接加载） |
| 会话库 | `<会话工作区>/logs/session.sqlite` | 短期记忆、工具返回、推理、整轮 trace | 轻量手写 DDL（可控增量加列） |

- **主库**：`db.py` 单例引擎 + `session_scope()` 事务；`Conversation` 与 `Message` 用 `Relationship(cascade_delete)` 关联；`Message.route` 记难度档位；schema 版本 `PRAGMA user_version`（当前 v4），`_migrate` 用 `create_all` + 增量 `ALTER` 兼容旧库（幂等）。
- **向量同库**：不用 lancedb（省 ~380MB），`sqlite-vec` 加载失败只诊断不阻断——聊天主流程不依赖向量。
- **会话库即短期记忆**：`short_term_memory` 先读 `logs/session.sqlite`（近 N 轮），空则回落主库消息；注入 simple/medium/hard 图。工具轨迹与推理也写这里，前端“洞察面板”与“追踪窗”直接读。

## 7. 可观测性（Agent 应用的刚需）

非确定性系统必须有“回放/追踪”能力：

- **`trace` 模块**：`recording(turn_id)` 上下文里记录 span 树、每次 LLM 请求/响应、工具调用、token 用量；按 `turn_id` 落会话库。
- **展示路径 `_path(difficulty)`**：把图节点映射成给人看的 path——understand → route →（simple | plan→select_tools→react→verify）。
- **接口**：`GET /api/conversations/{id}/traces`（每轮摘要）、`GET /api/conversations/{id}/traces/{turnId}`（完整步骤：图路径、LLM 入参/出参、工具、token）。前端 `TraceWindow` 独立窗可视化。
- **价值（面试话术）**：Agent 行为非确定性、且会调工具改文件，没有逐轮追踪就“无法调试、无法向用户解释为什么这么做”。所以可观测是**一等公民**，不是事后补监控。

## 8. 一次请求的完整编排（把核心串起来）

```text
POST /api/chat { message, conversation_id?, role_id?, skills? }
   │
   ├─ open_for_chat → 确保会话 + workspace_dir（分配或复用会话工作区）
   ├─ short_term_memory(limit ≈ role.memory×2)   ← 读会话库
   ├─ RolesService.resolve_for_chat → 角色运行时（prompt/模型/工具/记忆）
   ├─ skill_prompt_blocks(skills) → 并入 role.prompt（SKILL.md 文本）
   ├─ use_conversation_sandbox(workspace_dir)     ← contextvars 绑定沙箱
   │
   ├─ run_chat → run_pipeline → LangGraph
   │     understand(改写+难度) → simple|medium|hard
   │       medium/hard: tool_selector 缩集 → create_agent ReAct
   │       hard: plan→…→verify（可回环）
   │     工具在沙箱内执行；Bash/PowerShell 危险命令挂起等人审
   │
   ├─ save_exchange  → 主库：用户消息 + 助手回复（同事务，route=difficulty）
   ├─ record_turn    → 会话库：消息 + 工具轨迹 + 推理（route_reason/tool_plan）
   ├─ trace 按 turn_id 落会话库
   │
   └─ 返回 reply, difficulty, rewritten, tool_trace, selected_tools,
             tokens, duration_ms, conversation_id, user/assistant_message, workspace
```

**两个易踩的不一致点（面试加分）**
1. **原文入库，改写不入库**：`rewritten` 只进 Agent，用户气泡仍是原话（避免“AI 替我改了我说的话”的体验问题）。
2. **同步请求 vs 异步落库**：`/api/chat` 同步返回，但 Agent 可能还在生成；前端“停止/撤回”用 `AbortController` 中止 HTTP 后，还要轮询 `deleteLastTurn` 直到后端真正落库并被清掉——这是“前端乐观 UI + 后端同步落库”的协调细节。

## 9. 核心架构“面试串讲”（45 秒版）

> 核心是一条 LangGraph 流水线：先 `understand` 用主模型把用户原话改写成清晰意图并判定难度（simple/medium/hard），再按难度进子图。simple 直接答；medium 先“工具选型缩集”再跑 ReAct；hard 还要先 plan、最后 verify，不通过可回环最多两轮。工具是进程内 LangChain @tool，按 MCP 分组注册、运行时能力探测决定注册与否，Bash/PowerShell 危险命令走人工确认（在图外挂起）。文件操作都在“会话工作区沙箱”里——主工作区下按日期生成的目录，用 contextvars 绑定当前会话，删会话级联清目录。持久化是双层 SQLite：主库存会话/消息/模型/角色（SQLModel，向量用 sqlite-vec 同库），每会话再有一份 session.sqlite 存短期记忆/工具轨迹/逐轮追踪。每轮都有 trace，前端有独立追踪窗——因为 Agent 非确定性，可观测是刚需。

## 10. 常见追问与应答

- **Q：为什么 medium/hard 要先“选型”再跑 Agent？** → 全量工具进 prompt 既占 token 又易误调；先缩集能降成本、提准确率，也让角色“工具白名单”有用武之地。
- **Q：hard 的 verify 会不会无限循环？** → 不会，`_MAX_VERIFY_ROUNDS=2`，到上限强制收束并注明“已达核对上限”。
- **Q：工具为什么不做成外置 MCP 子进程？** → 体积/打包成本、启动延迟；进程内调用更简单且与 `builtin://` 设计一致。Browser 用进程内 Playwright 对齐上游工具面，不另起 Node。
- **Q：两层 SQLite 不麻烦吗？** → 主库是“跨会话的业务状态”，会话库是“单会话的短期记忆与轨迹”，天然按会话隔离、删除即清；向量同主库省一份重依赖。
- **Q：没有 API Key 时系统还能用吗？** → 能。`router`/`tool_selector` 走启发式，`simple` 回离线文案，`medium/hard` 直接 `run_tools`——离线降级是设计目标之一。
