# ChatVein 设计架构总结

> 面向面试：讲清楚“系统的拓扑（谁连谁）、关键设计决策、为什么这么设计、请求怎么流转、构建与运行模型”。
> 本文偏**结构与决策**；核心算法/图细节见《核心架构总结》，取舍哲学见《实现思想总结》。

---

## 1. 总体拓扑：三层 + 一个“消息层”定位

```text
┌─────────────────────────────────────────────────────────────┐
│  React (Vite + TS)  —— UI 层                                 │
│    • 会话列表 / 消息流 / 洞察面板 / 设置 / 追踪窗            │
│    • api.ts：统一封装，经 Tauri plugin-http 的 fetch 直连后端 │
└───────────────▲─────────────────────────────────────────────┘
                │  invoke("backend_url") 拿地址；之后 fetch 直连 Python
                │  （不走 Rust 代理，Rust 只在启动时推 URL + 转发日志）
┌───────────────┴─────────────────────────────────────────────┐
│  Rust / Tauri  —— 消息层（编排者，不是代理）                  │
│    • 启动 Python 侧车进程（spawn_backend）                    │
│    • 端口/数据目录决策（dev 8420；release 动态 ≥3000）         │
│    • 就绪探测 + emit("backend-ready", url)                    │
│    • 转发后端 stdout/stderr 为事件；退出时 kill_backend        │
└───────────────▲─────────────────────────────────────────────┘
                │ 子进程：Python 监听 127.0.0.1:port
┌───────────────┴─────────────────────────────────────────────┐
│  Python / FastAPI  —— 后端（真实业务）                        │
│    • /api/chat：LangGraph 编排（理解→路由→分档执行）          │
│    • /api/conversations|models|roles|mcps|skills|workspace    │
│    • SQLite（主库 SQLModel + 每会话 session.sqlite）+ 向量     │
└─────────────────────────────────────────────────────────────┘
```

## 2. 最关键的设计决策：**Rust 是“消息层”而非“请求代理”**

这是整个架构的“题眼”，面试务必先抛出来：

- **传统做法**：前端 → Rust 代理 → Python（每条请求都过 Rust 一次）。
- **ChatVein 做法**：Rust 在**启动时**把“真实后端 URL（含动态端口）”通过 `backend_url` 命令 + `backend-ready` 事件交给前端；之后 React 用 `fetch` **直连** Python。
- **Rust 的角色收敛为三件事**：
  1. **进程生命周期管理**：拉起 / 杀掉 Python 子进程；
  2. **URL 与路径提供者**：决定端口、数据目录，并推给前端；
  3. **日志/事件桥接层**：把 Python 的 stdout/stderr 转成前端可订阅的事件（`backend-stdout` / `backend-stderr` / `backend-error`）。

**为什么这样设计（要点）**
- 避免每请求多一跳 Rust 转发带来的延迟与复杂度（Agent 流式/长任务更敏感）。
- 让 Rust 专注它擅长且安全的“编排”，把 LLM/工具这类重业务逻辑交给 Python 生态（LangChain、SQLModel、sqlite-vec 都是 Python 一等公民）。
- 前端用 Tauri 的 `plugin-http` 的 `fetch`，请求实际在 Rust 的 reqwest 里发，**天然绕过浏览器 CORS / CSP**，所以直连没有跨域问题。

**面试话术**：
> “我们没有让 Rust 当逐请求的反向代理，而是让它做‘启动编排者’：负责把 Python 进程拉起来、探测就绪、把真实 URL 推给前端，之后前端直连 Python。Rust 只做进程管理、地址/路径决策和日志事件桥接。这样既保留了 Tauri 小体积、安全的优势，又让 Python 全权处理 LLM 编排这类重型逻辑，且前端直连没有 CORS 之扰。”

## 3. 进程与运行模型

### 3.1 启动顺序
1. Tauri（Rust）`Builder.setup` 中调用 `backend::spawn_backend(app)`。
2. Rust 解析端口（`OnceLock`，仅一次）：debug → 8420；release → `find_free_port(3000)`。
3. 决定数据目录：`app.path().app_data_dir()` → 经 `CHATVEIN_DATA_DIR` 注入；并建立目录。
4. 选定可执行文件：
   - **dev**：仓库根 `.venv` 的 python + `backend/main.py`，并设 `CHATVEIN_RELOAD=1`（uvicorn 热重载）。
   - **release**：资源目录 `backend-runtime/backend(.exe)`（PyInstaller 冻结产物）。
5. 启动子进程，`stdout`/`stderr` 各起一个线程 drain → `app.emit(event, text)`。
6. `wait_for_backend` 用 TCP 连接探测（最多 20s）；成功 `emit("backend-ready", base_url)`，失败 `emit("backend-error", ...)`。
7. 前端 `App` 启动后轮询 `/api/health` 直到后端可达（超时 20s），缓存 URL 后开始正常请求。

### 3.2 退出模型
- Rust `run()` 返回后调用 `kill_backend()`：杀掉 `BACKEND_CHILD` 中的 Python 子进程。

## 4. 后端模块架构（FastAPI + 分层）

每个业务域是“模块”，统一由 `module.py` 组装并暴露单例 `service` 与 `APIRouter`：

```text
请求 → APIRouter(controller.py 的路由)
        → Service（业务规则、编排）
        → Repository（SQLModel 持久化）
        → Entity（SQLModel 表模型）
```

- **`main.py` 装配**：`lifespan` 里 `init_db()` + 各模块 `on_module_init`（角色/向量模型等懒加载）；`include_router` 挂上 models/roles/embeddings/conversations/trace/skills。
- **`/api/chat` 主流程**（设计上最值得讲）：
  1. `conversations_service.open_for_chat` 确保会话 + `workspace_dir`；
  2. 读短期记忆、解析角色运行时、注入技能提示；
  3. `use_conversation_sandbox(workspace_dir)` 把“当前会话沙箱”绑到 contextvars；
  4. `run_chat` → LangGraph；
  5. `save_exchange`（主库消息） + `record_turn`（会话库记忆/工具轨迹/推理） + trace 落库；
  6. 返回 `reply / difficulty / tool_trace / workspace / tokens ...`。
- **横切**：CORS 全开（本地进程内通信，无外网暴露）、统一异常回落、schema 版本 `PRAGMA user_version`。

## 5. 前端架构（React 视图 + 单一 API 层）

- **单一出口 `api.ts`**：所有领域请求都走 `backendRequest(endpoint, method, body, signal)`；它内部 `await waitForBackend()` 保证后端就绪，再用 Tauri `fetch` 直连。这把“等后端 + 直连 + 错误归一”收敛到一处。
- **视图切换**：`App` 用 `view` state 在 ChatView/ModelsView/RolesView/... 间切换；Sidebar 负责导航与计数。
- **核心状态在 `ChatView`**：会话列表、消息流、洞察（轨迹/产物）、发送/停止/撤回。关键设计：
  - 用 `AbortController` + `abortRef` 实现“停止生成”；
  - 乐观插入用户/助手气泡（`pendingRef` 记录 id 原文），便于精确撤回；
  - 后端是同步落库，停止 HTTP 后可能仍在生成 → 前端 `cleanupLastTurn` 轮询删除最近一轮（最多 ~6.4s），处理“异步落库 vs 同步请求”的不一致。
- **Trace 独立窗口**：`?view=trace&conversation=&turn=` 打开 `TraceShell`，与主界面解耦。

## 6. 持久化与数据架构

- **主库 SQLite（SQLModel）**：`Conversation` / `Message` / `LlmModel` / `Role`；`db.py` 单例引擎，`session_scope()` 管事务，`_migrate` 用 `create_all` + 增量 `ALTER` 兼容旧库；`PRAGMA user_version` 记录 schema 版本（当前 v4）。
- **向量同库**：`sqlite-vec` 扩展逐连接加载，`vec0` 虚拟表存 embedding，与业务数据同事务同备份（不用 lancedb 省 ~380MB）。加载失败不阻断启动，只诊断上报。
- **每会话 `logs/session.sqlite`**：短期记忆、工具返回、推理（route_reason/tool_plan）、整轮 trace JSON；`session_store.py` 手写轻量 DDL（比 SQLModel 更可控地做增量加列）。
- **路径所有权在 Rust**：`CHATVEIN_DATA_DIR` 注入；`CHATVEIN_DB_PATH` 可覆盖。

## 7. 构建与发布架构（为什么最终用户不用装 Python）

```text
dev:  tauri dev  → Rust 拉起 .venv + backend/main.py（--reload，端口 8420）
build: prepare:runtime (PyInstaller onedir) → dist-backend/
       tauri build → 把 dist-backend/ 作为资源 backend-runtime/ 打进安装包
       最终：backend-runtime/backend.exe + _internal/，用户机无需 Python
```

- **PyInstaller onedir**：把 Python 解释器 + 依赖冻结成 `backend.exe` + `_internal/`，Tauri 在 `bundle.resources` 里以 `backend-runtime/` 复制进去。
- **按需下载，不进包**：Chromium（Playwright）、MinGit、向量权重模型等体积大的资源**不进安装包**，首次使用时下载到 `CHATVEIN_DATA_DIR`。
- **端口策略**：dev 固定便于抓包调试；release 动态探测空闲端口避免与宿主机冲突——端口在进程内只解析一次并被启动/探测/前端共用。

## 8. 设计架构“面试串讲”（30 秒版）

> ChatVein 是 Tauri2 桌面 Agent，三层架构：React 做界面，Rust 做消息层（不是代理，而是进程编排者——启动时把 Python 的真实 URL 推给前端，之后前端经 Tauri 的 fetch 直连 Python，绕开 CORS），Python/FastAPI 做真实业务（LangGraph 编排 + 工具 + SQLite）。Rust 还负责端口/数据目录决策和日志事件桥接。后端按领域分层（controller/service/repository/entity），前端有单一 API 封装层。持久化用主库 + 每会话库两份 SQLite，向量走 sqlite-vec。打包时把 Python 用 PyInstaller 冻结成侧车塞进安装包，用户无需装 Python，浏览器/MinGit/向量权重按需下载。

## 9. 常见追问与应答

- **Q：前端直连 Python，安全吗？** → 都是本机 `127.0.0.1`，不暴露到外网；CORS 全开仅限本地进程内通信；Tauri 窗口与能力受 `capabilities` 约束。
- **Q：Rust 不做代理，那它还能管什么？** → 进程生命周期、端口/路径决策、把后端日志实时转成前端事件（可观测）、退出清理。
- **Q：为什么不直接用 Electron？** → Tauri 用系统 WebView + Rust，体积小、内存低、安全模型更现代；本项目的“Rust 只编排不代理”正好契合 Tauri 轻量定位。
- **Q：dev 与 release 后端差异怎么对齐？** → `cfg!(debug_assertions)` 在编译期区分：dev 用源码+热重载+固定端口，release 用冻结 exe+动态端口；同一份 `backend.rs` 逻辑覆盖两种形态。
