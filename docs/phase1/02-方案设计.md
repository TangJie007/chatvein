# Forge 第一期 · 方案设计（技术设计文档）

> 版本：v1.0 ｜ 日期：2026-09-03 ｜ 作者：唐杰
> 上位文档：仓库根目录 `PRD-Forge-v1.md`（产品需求）、[`01-第一期PRD.md`](./01-第一期PRD.md)（一期范围）
> 本文回答一个问题：**Forge 的全部能力放在哪里、以什么形态被调用。**

---

## 1 设计总纲

### 1.1 一句话架构

```
packages/chatvein/*  = Harness 全部能力（纯 Node 库，零 Electron 依赖）
        ▲                          ▲
        │ (import / IPC)           │ (import / IPC)
   app（Electron 控制台）     service（Node 无头运行器，CLI + sidecar）
   = 能力的调用者（GUI）        = 能力的调用者（headless）
```

- **`packages/chatvein/` 提供 harness 的全部能力**：需求编译、LangGraph 编排、工具层、模型网关、沙箱执行、验证闭环、上下文/Token 管理、Trace 可观测、配置、运行记录。全部是**纯 TypeScript / Node.js** 包，不 import `electron`。
- **`app/` 只是能力的调用者**：Electron + Vue 桌面控制台，负责窗口、可视化、人工干预入口；它通过 `@chatvein/core` 的编程接口（或 IPC 到 sidecar）驱动一次运行，自身不含任何 Agent 业务逻辑。
- **Node 服务也是调用者**：`packages/chatvein/service` 是一个独立的 Node 进程入口（CLI `forge` / sidecar），复用同一套能力包，提供无人值守运行、崩溃隔离、回归脚本与（未来的）远程/容器部署。
- 已有的 `@electrum/*`（NestJS 风格 Electron 框架：DI / 控制器 / IPC / 窗口）是 **app 壳的框架**，不属于 harness 能力；harness 能力不依赖它。

### 1.2 为什么这样切

| 决策 | 理由 |
|------|------|
| 能力全部在 `packages/chatvein/*`，且**零 Electron 依赖** | ① harness 可用 vitest 在纯 Node 下单测，跑得快、可 mock；② 同一份能力既能被 Electron 主进程 `import`，也能被独立 Node 进程 `import`，杜绝"GUI 能跑、CLI 跑不了"的双份逻辑；③ 未来迁 Docker/赛事沙箱时，能力包原样可用 |
| app 只做调用 | 满足 PRD"渲染进程崩溃不影响运行"——重活在独立 Node sidecar 或主进程的能力层，UI 重启可重连续看 |
| 单独 Node 服务（service） | ① **崩溃隔离**：Agent 子进程/模型流把进程拖垮时不带走 Electron；② **回归基线**（PRD 场景 5）需要纯命令行跑固定 seed；③ 赛事若要求"命令行可复现"，service 即交付物；④ sidecar 模式下 app 只是监视器 |
| 复用 `@electrum/*` 而非另起壳 | 现有 DI/`@Controller`/`@IpcHandle`/`@IpcEmit` 正好承担"控制台 ↔ 主进程"的双向通信，app 侧几乎零胶水 |

### 1.3 与 `@electrum/*` 的关系

| 维度 | `@electrum/*`（已有） | `@chatvein/*`（本期新建） |
|------|----------------------|--------------------------|
| 定位 | Electron 应用框架（壳） | Agent Harness 能力库（芯） |
| 运行环境 | Electron 主/预加载/渲染 | 纯 Node（Electron 主进程或独立 Node 进程均可） |
| 依赖 electron | 是（core/preload） | **否** |
| 关键抽象 | `@Module/@Controller/@IpcHandle`、DI、窗口 | `Harness`、`graph`、`tools`、`models`、`sandbox`、`trace` |
| 被谁用 | app 的壳（窗口、IPC、菜单） | app 主进程 + service 两个调用者 |

app 内部分层：`@electrum/core` 管壳（窗口/IPC 骨架），`@chatvein/*` 装芯（Agent 能力）。两者通过 app 自己的 `RunController`（electrum 控制器）桥接。

## 2 仓库与包结构

### 2.1 目标布局

```
chatvein/
├─ packages/
│  ├─ electrum/                 # 已有：Electron 壳框架（common/core/preload/client/testing/codegen）
│  └─ chatvein/                 # 【本期】Harness 能力，全部纯 Node
│     ├─ common/                # @chatvein/common   类型、错误、日志、配置 schema、结果类型
│     ├─ core/                  # @chatvein/core     Harness 门面 + 运行时装配（RunEngine 生命周期）
│     ├─ models/                # @chatvein/models   OpenAI 兼容网关、分级路由、降级链、计量、并发
│     ├─ tools/                 # @chatvein/tools    文件/shell/git/检索 工具 + 截断/超时/白名单
│     ├─ sandbox/               # @chatvein/sandbox  工作区隔离 + 子进程执行（P0）/Docker(P1)
│     ├─ compiler/              # @chatvein/compiler 需求文档 → 任务树（M2）
│     ├─ orchestrator/          # @chatvein/orchestrator LangGraph 状态机 + checkpoint + 护栏（M3）
│     ├─ context/               # @chatvein/context  截断、压缩、文件索引、Token 预算（M5）
│     ├─ verifier/              # @chatvein/verifier build/test/lint 解析 + 失败归因（M6）
│     ├─ observability/         # @chatvein/observability Trace JSONL、事件总线、报告导出（M9）
│     └─ service/               # @chatvein/service   Node 无头运行器：CLI + sidecar server（调用者）
├─ app/                         # 【改造】Electron 控制台 = 能力的 GUI 调用者
│  └─ src/main/forge/           #   RunController/RunService：把 UI 动作映射到 @chatvein/core
└─ docs/
```

### 2.2 包依赖原则

- **单向依赖、无环**：`service → core → {orchestrator, compiler, verifier, ...} → {models, tools, sandbox, context, observability} → common`。
- **能力包绝不 import `electron`**（CI 加一条断言脚本兜底）。
- `@chatvein/orchestrator` 依赖 `@langchain/langgraph`、`@langchain/core`、`@langchain/openai`；其余包尽量不直接依赖 LangChain，用 `@chatvein/common` 里的最小接口（`ChatModelLike`）解耦，便于绕开框架直连网关（见风险 R1）。
- 构建沿用 **tsup**（双 CJS/ESM + d.ts），测试 **vitest**，与 electrum 包一致。

### 2.3 两个调用者如何复用能力

```
┌──────────────────────────── app (Electron) ───────────────────────────┐
│ renderer (Vue) ──window.api──▶ preload ──ipcMain──▶ RunController       │
│                                          (@electrum @Controller)       │
│                                                         │              │
│                                              import @chatvein/core     │
└─────────────────────────────────────────────────────────┼──────────────┘
                                                          │ 两种运行模式
                          ┌───────────────────────────────┴───────────────┐
                          ▼                                                 ▼
              【模式 A：进程内】                          【模式 B：sidecar（默认/推荐）】
        Electron 主进程直接 new Harness()         主进程 spawn `node @chatvein/service`
        适合开发调试、轻量运行                      stdin/stdout JSON-RPC + 事件流
                                                  崩溃不带走 GUI；可独立 CLI/回归
                          │                                                 │
                          └──────────────▶ 同一套 @chatvein/* 能力 ◀─────────┘
                                        （纯 Node，无 electron import）
```

- **模式 A（in-process）**：app 主进程 `import { Harness } from '@chatvein/core'` 直接跑。开发期最简单。
- **模式 B（sidecar）**：app 拉起 `@chatvein/service` 子进程，用 JSON-RPC（行分隔 JSON over stdio，或本地 HTTP/WS）通信。运行事件实时回流 UI；service 崩溃可从 checkpoint 续跑，GUI 不受影响。**初赛默认用 B**（满足非功能需求"渲染/壳崩溃不影响运行"）。
- **纯 CLI**：`forge run requirement.md --config forge.config.ts`、`forge resume <run_id>`、`forge regression`，无需 Electron。

## 3 `@chatvein/core`：能力门面与运行时装配

core 是调用者唯一需要直接 import 的包。它把各能力包装配成一个可启动/可暂停/可恢复/可订阅的运行引擎。

### 3.1 门面 API（草案）

```ts
// @chatvein/core
export interface Harness {
  /** 预览任务树（只跑 compiler 的本地预处理 + 模型抽取，不启动编排） */
  preview(input: { requirementPath: string; config: ForgeConfig }): Promise<RunPlan>
  /** 启动一次运行；事件通过 onEvent 回流 */
  start(input: StartRunInput): Promise<RunHandle>
  /** 从 checkpoint 恢复 */
  resume(runId: string): Promise<RunHandle>
  /** 读取历史运行（tasks/trace/report） */
  loadRun(runId: string): Promise<RunRecord>
}

export interface RunHandle {
  runId: string
  pause(): Promise<void>
  abort(): Promise<void>
  /** 练习期人工干预：注入提示 / 标记已手改文件 */
  intervene(input: InterventionInput): Promise<void>
  /** 订阅运行事件（trace 事件的超集，含任务状态/预算/报告） */
  onEvent(listener: (e: RunEvent) => void): () => void
  /** 运行结束的 Promise */
  done: Promise<RunReport>
}
```

- `Harness` 由 `createHarness(deps?)` 创建，deps 可注入 mock 的模型/沙箱/时钟（测试与 `@chatvein/testing` 用）。生产默认装配真实实现。
- core 内部持有一个极简 DI/装配器（不引 NestJS；用工厂函数 + 接口注册即可），把 `models/tools/sandbox/compiler/orchestrator/verifier/context/observability` 接起来。

### 3.2 运行生命周期

```
preview → start → [plan → dispatch → implement ⇄ verify ⇄ diagnose → fix] → integrate → finalize
                   ▲                                                         │
                   └──────────── 失败/预算内循环 ◀────────────────────────────┘
   pause/abort/intervene 任意时刻可介入；每个节点后写 checkpoint
```

core 负责：加载/校验配置 → 准备沙箱工作区 → 初始化 trace（run_start）→ 装配并驱动 LangGraph → 透传事件 → 收尾写 report。

## 4 `@chatvein/orchestrator`：LangGraph 状态机（M3）

### 4.1 状态 Schema（`GraphState`）

与 PRD 5.3.3 对齐，落到 TS 类型（放 `@chatvein/common`，供 UI/service 共享）：

```ts
interface GraphState {
  run_id: string
  workspace_path: string
  requirement_path: string
  task_tree: Task[]
  current_task_ids: string[]
  file_index: Record<string, FileSummary>   // 路径 → 摘要/签名，避免重复读
  build_status: 'unknown' | 'pass' | 'fail'
  test_report?: TestReport                  // 结构化失败项
  root_cause?: string
  retry_count: number
  token_usage: TokenStat                    // 按模型分档累计
  budget: Budget
  status: 'running' | 'paused' | 'done' | 'aborted'
  checkpoint_id?: string
}
```

### 4.2 节点与模型档

| 节点 | 职责 | 模型档 | 说明 |
|------|------|--------|------|
| plan | 需求编译产出任务树 | 强 | 调 `@chatvein/compiler` |
| dispatch | 选下一批可并行任务 | 无 | 纯逻辑，拓扑 + 并行组 |
| implement | 写/改代码 | 强 | 工具调用循环 |
| verify | build + test + lint | 无 | 调 `@chatvein/verifier` |
| diagnose | 失败归因 | 中 | 输出责任文件 + 根因 |
| fix | 定向最小修复 | 强 | 只加载责任文件上下文 |
| integrate | 全量回归 + 汇总 | 中 | |
| finalize | 报告 + 提交检查 | 无 | 调 observability 出报告 |

边条件、护栏（Token 800 万 / 单任务 30 步 / 墙钟 6h / 连续失败 3 次）与 PRD 5.3.3 一致，护栏触发即 `finalize` 或暂停。

### 4.3 Checkpoint

- P0 用 **LangGraph 文件型 checkpointer**（`@langchain/langgraph` 的持久化 saver，落盘到 `runs/<run_id>/checkpoints/`）。决策点 5 倾向文件方案。
- 每个节点退出后写一次；`resume(runId)` 从最近 checkpoint 重建 `GraphState`。
- app 重启后扫描 `runs/`，发现未完成运行提示续跑（PRD 异常处理）。

### 4.4 P1 并行

一期默认**串行**（风险：并行烧 Token）。dispatch 预留 `parallel_group`，仅对低耦合任务开并发子图，且受预算护栏约束。

## 5 `@chatvein/models`：模型网关（M7）

```ts
interface ChatModelLike {            // 最小接口，隔离 LangChain
  invoke(messages, opts?): Promise<ModelResult>
  stream?(messages, opts?): AsyncIterable<ModelChunk>
}
interface ModelResult { content: string; usage: { prompt_tokens; completion_tokens }; model: string }
```

- **适配器**：`@langchain/openai` 的 `ChatOpenAI` 指向赛事网关 `baseURL`（OpenAI 兼容），Claude/GPT/Kimi/DeepSeek 均走该适配。
- **分级路由** `ModelRouter`：`strong | medium | weak` 三档，各绑一个模型 ID，配置可切。节点按 4.2 取档。
- **降级链**：超时/限流/5xx → 自动切备用模型，发 `model_fallback` 事件留痕，最多重试 3 次。
- **计量**：每次调用累加 `usage` 到 `token_usage`（按模型），并产出 trace 事件；预算由 `@chatvein/context` 的 BudgetGuard 判定。
- **并发控制**：每档信号量限流，防 429。
- **密钥**：从本地加密配置读取，绝不进 trace（PRD 安全要求）。

## 6 `@chatvein/tools`：工具层（M4）

- 工具以 LangChain `StructuredTool`（或最小 tool 接口）实现：`read_file / write_file / apply_patch / list_dir / glob_search / grep_search / exec_shell / git_op / start_service / smoke_check`。
- **横切三件套**（每个工具强制）：
  1. **超时**：按 PRD 表（5s/10s/300s…）；
  2. **输出截断**：进上下文前过 `@chatvein/context` 的截断器（头尾保留 + 中间折叠 + 标注省略行数）；
  3. **白名单**：`exec_shell` 仅允许 npm/pnpm/node/git/lint/构建/测试命令，其余拒绝；
  4. 每次调用写 `tool_call` trace（工具名、参数大小、返回大小、耗时、是否截断）。
- 工具不直接碰模型，只接收参数、返回结构化结果，便于单测。

---

## 7 `@chatvein/sandbox`：沙箱（M8）

- **P0 本地工作区隔离**：每次 run 在 `runs/<run_id>/workspace/` 从模板拷贝独立目录；命令在受限 `child_process` 执行，带超时、cwd 锁定、环境变量白名单（不继承宿主敏感 env）、允许 npm 源网络。
- **环境快照**：记录 node 版本、依赖版本、OS，写入 run 记录（可复现）。
- **P1 Docker/WSL2**：预留 `SandboxProvider` 接口（`local` | `docker`），与赛事沙箱对齐。

## 8 `@chatvein/compiler`：需求编译（M2）

- 本地预处理：切分 Markdown、建章节索引（零模型调用）。
- 模型抽取：按章节抽功能点 + 验收标准 → 结构化 JSON；JSON Schema 校验失败重试一次，仍失败则该章节降级为单任务。
- 大文档分批抽取再合并；产出 `Task[]`（字段同 PRD 5.3.2），拓扑排序 + 并行分组，落盘 `tasks.json`，供 UI 预览/微调。

---

## 9 `@chatvein/context`：上下文与 Token（M5）

- `truncate()`：头尾保留 + 中间折叠；`extractErrorFrames()`：只留报错栈/失败用例名/断言差异。
- `summarizeHistory()`：每完成一个任务把该任务历史压成摘要（弱模型）。
- `FileIndex`：上下文只放路径 + 摘要 + 函数签名，需要时精确读。
- `BudgetGuard`：累计 token/步数/墙钟，超阈值发 `budget` 事件并触发熔断。

---

## 10 `@chatvein/verifier`：验证闭环（M6）

- `build()` / `test()` / `lint()`：在沙箱执行，解析退出码与输出为结构化结果（`TestReport { passed, failed: FailedCase[] }`，失败用例含名/断言/堆栈关键帧）。
- 硬规则：**模型不得自述完成**，通过证据必须来自 verify 的结构化输出。
- 失败 → 交 orchestrator 的 diagnose；重试上限与降级策略由状态机控制。

---

## 11 `@chatvein/observability`：可观测（M9）

- **事件总线**：core/节点/工具/模型都往一个 `EventBus` 发 `RunEvent`；订阅者 = ① JSONL 落盘 ② UI（经 sidecar/IPC 推送）③ 预算/计量聚合。
- **落盘**：`runs/<run_id>/` 下 `trace.jsonl`（追加写）、`tasks.json`、`run.json`、`report.md`、`payloads/<event_id>.json`（大 payload 分片，上下文只存 `payload_ref`）。
- **事件字段**：`ts / run_id / node / type / name / input_tokens / output_tokens / duration_ms / payload_ref / status`（同 PRD 5.3.9）。
- **报告导出**：`report.md` 汇总三项指标、失败清单、耗时/Token 分布、环境与参数快照、prompt 模板版本。
- **节流**：UI 推送 100ms 批量、Token 数字 500ms 刷新（PRD 第 8 节）。

## 12 `@chatvein/service`：Node 无头运行器（调用者）

两种形态，同一入口包：

1. **CLI**：`forge run / resume / regression / preview`。`regression` 跑固定需求 + 固定 seed，输出三项指标对比表（PRD 场景 5）。
2. **sidecar server**：被 app `spawn`，stdio 上行分隔 JSON：
   - 请求：`{ id, method: 'start'|'pause'|'abort'|'intervene'|'resume'|'loadRun', params }`；
   - 事件：`{ event: 'run', data: RunEvent }` 实时流；
   - 响应：`{ id, result | error }`。
- service **只做参数解析/进程通信/退出码**，所有逻辑来自 `@chatvein/core`，保证 CLI 与 GUI 行为完全一致。

## 13 app：Electron 控制台（调用者，改造现有 example）

复用 `@electrum/*` 壳，新增 `src/main/forge/` 功能模块：

| electrum 构件 | 职责 |
|---------------|------|
| `ForgeModule` | `@Module` 聚合控制台能力 |
| `RunController` (`@Controller('run')`) | `start/pause/abort/resume/intervene/preview/loadRun` 的 `@IpcHandle`；持有 sidecar 进程或 in-process Harness |
| `RunEventBridge` | 订阅 `RunEvent`，用 `@IpcEmit('run:event')` 推送到渲染进程 |
| `ConfigController` (`@Controller('config')`) | 模型分级/并行度/预算/白名单的读写 |
| `RunsController` (`@Controller('runs')`) | 历史运行列表、trace、报告读取 |

- 渲染进程（Vue 3 + Element Plus，沿用现有栈与品牌色 #4BD8BA）：顶部工具条 / 左任务树 / 中 Trace 时间线 / 右诊断面板（Token、错误、预算）/ 底部日志。用 `createClient<IpcApi>()` 调 `run:*`、订阅 `run:event`。
- app 侧**不出现**任何 LangGraph/模型/工具逻辑——只做"调接口 + 画界面 + 发干预"。
- codegen：用 `@electrum/codegen` 从 `RunController` 等生成渲染端 `IpcApi` 类型，替换现在手写的 `ipc-api.ts`。

## 14 数据模型与目录

```
runs/<run_id>/
├─ run.json          # Run 元数据：需求 hash、参数快照、环境快照、状态、起止时间、总 token
├─ tasks.json        # Task[] 任务树
├─ trace.jsonl       # TraceEvent 追加写
├─ report.md         # 三项指标 + 失败清单 + 分布
├─ checkpoints/      # LangGraph 状态快照
├─ payloads/<event_id>.json   # 大模型输入输出原文分片
├─ workspace/       # 沙箱工作区（产物代码 + git 仓库）
└─ diff/            # 变更补丁
config/forge.config.ts       # 模型分级、并行度、预算、白名单、截断阈值
```

`Task / TestReport / TokenStat / Budget / TraceEvent / RunReport / ForgeConfig` 等类型统一定义在 `@chatvein/common`，app 与 service 共享。

## 15 关键技术风险与对策（设计层面）
