# ChatVein 项目目录总结

> 面向面试：能一句话说出“这是什么、由哪几块组成、每块里有什么、为什么这么放”。
> 適用版本：v2.0.x，三层架构（React / Rust-Tauri / Python-FastAPI）桌面 Agent 应用。

---

## 0. 一句话定位

ChatVein 是一个**基于 Tauri 2 的本地桌面 AI Agent（对话 + 工具 + 工作区）**。它不是“套壳网页”，而是用三种语言各司其职：

- **React + TypeScript（Vite）** 做界面与交互（UI 层）；
- **Rust（Tauri）** 做进程编排、端口/路径决策、日志与事件桥接（消息层）；
- **Python（FastAPI）** 做真正的业务逻辑：LLM 编排、工具、持久化（后端/侧车进程）。

## 2. 各层目录详解

### 2.1 `src/`（前端 / UI 层）

```text
src/
├── main.tsx             # React 挂载入口
├── App.tsx              # 应用壳：导航视图切换（chat/group/kb/skills/roles/models/settings）
│                       #    + 启动即拉模型/角色计数；trace 视图独立启动
├── api.ts              # 唯一后端访问封装：getBackendUrl / waitForBackend / backendRequest
│                       #   所有领域 API（会话/模型/角色/MCP/技能/工作区/trace）都在这里声明
├── styles.css          # 全局样式（Tailwind 4 + 设计 token）
├── types/
│   └── view.ts          # 前端视图类型（AppView、NavCounts 等）
├── lib/                # 前端工具（如 openTrace.ts 打开追踪窗、helpers）
└── components/
    ├── layout/         # TitleBar（自定义标题栏）、Sidebar（导航）
    ├── chat/           # ChatPanel / SessionList / Composer / InsightPanel / BashApproval
    ├── views/          # 各页面：ChatView、ModelsView、RolesView、SkillsView、
    │                   #   KnowledgeView、GroupView、SettingsView、TraceShell
    ├── models/         # 模型管理相关组件
    ├── settings/       # 设置页（偏好、MCP 状态、SQLite 信息）
    ├── skills/         # 技能市场组件
    ├── trace/          # 追踪窗（TraceWindow：path / LLM / 工具 / token 树）
    └── ui/             # 基础 UI（Radix 封装的 Button/Dialog/Tabs/Tooltip/Switch 等）
```

**前端设计要点（看目录就能问的点）**
- 所有后端请求集中在 `api.ts`，统一经过 Tauri 的 `plugin-http` 的 `fetch`——这样请求在 Rust 里发（reqwest），**不受浏览器 CORS 约束**，也无需 CSP `connect-src`。
- 视图切换是简单的 `view` state + 条件渲染；`ChatView` 是核心，负责会话列表、消息流、洞察面板、发送/停止/撤回。
- 组件按职责分层：`layout`（壳）/ `views`（页面）/ `chat`（聊天域）/ `ui`（原子组件），便于面试时讲“组件分层与状态上提”。

### 2.2 `src-tauri/src/`（Rust 消息层）

```text
src-tauri/src/
├── main.rs             # 标准 Tauri main：`chatvein_lib::run()`
├── lib.rs             # 关键：Builder 装配 + setup 里 spawn 后端 + 就绪后 emit 事件
├── backend.rs         # 侧车进程管理（本项目最“设计感”的 Rust 文件，详见下）
└── commands.rs        # 仅暴露一个 Tauri command：`backend_url()`（把真实后端 URL 给前端）
```

`backend.rs` 内部分工：
- `backend_port()`：端口只解析一次（`OnceLock`），dev=8420 固定，release 探测 `>=3000` 空闲端口。
- `spawn_backend(app)`：启动 Python 子进程（dev 用 `.venv`+`main.py`，release 用冻结的 `backend.exe`）；注入 `CHATVEIN_DATA_DIR` / `CHATVEIN_PORT` / `CHATVEIN_RELOAD` 等环境变量；把 stdout/stderr 转发成 `backend-stdout` / `backend-stderr` 事件给前端。
- `wait_for_backend(port, timeout)`：TCP 探测就绪（最多 20s）。
- `resolve_data_dir(app)`：**路径决策权在 Rust**——用 `app_data_dir()` 拿到每用户数据目录传给 Python（因为打包后资源目录只读）。
- `kill_backend()`：退出时杀掉子进程。

### 2.3 `backend/`（Python 后端）

后端采用 **“按领域分模块 + 每个模块内部四层”** 的结构（NestJS 风格移植到 Python）：

```text
backend/
├── main.py             # 应用入口：FastAPI 实例、CORS、router 挂载、/api/chat 主流程
├── db.py               # 连接层（引擎/会话/迁移/向量扩展）—— 不在这里写业务表
├── agents/             # ★ Agent 编排（LangGraph）
│   ├── service.py       # run_chat 入口
│   ├── router.py        # 理解+难度路由（主模型 structured：rewritten + difficulty）
│   ├── llm.py           # get_chat_model / invoke_structured（统一模型调用）
│   ├── memory.py        # 短期记忆 → LangChain messages
│   ├── tool_selector.py # 工具缩集（候选集 + 角色白名单展开）
│   └── graphs/          # LangGraph：pipeline（总图）+ simple/medium/hard 子图 + state/common
├── conversations/       # 会话/消息领域
│   ├── module.py         # 组装 APIRouter + 单例 service
│   ├── controller.py     # 路由（REST）
│   ├── service.py        # 业务逻辑（open_for_chat / save_exchange / record_turn / 洞察）
│   ├── repository.py     # SQLModel 持久化
│   ├── session_store.py  # 会话空间 logs/session.sqlite（短期记忆/工具轨迹/推理）
│   └── entity/           # SQLModel 实体 Conversation / Message
├── models/             # LLM 模型配置（entity/controller/service/repository/module 同构）
├── roles/              # 角色配置（人格/模型/工具/记忆）同构
├── mcps/               # 内置工具（进程内“MCP”）
│   ├── registry.py      # 工具注册表 + 工具名→实现
│   ├── workspace.py     # 主工作区解析
│   ├── sandbox.py       # 会话沙箱上下文（contextvars：current_sandbox）
│   ├── bash_runtime.py / bash_approval.py / bash_policy.py  # Bash 执行与人工确认
│   ├── powershell_policy.py / browser_runtime.py / ipwhois_runtime.py ...
│   └── tools/           # 各工具实现（fs / web / sqlite / kb / codesandbox / bash / browser / ip / ocr）
├── skills/             # SkillHub 浏览代理 + 本机安装（local_store）
├── embeddings/         # 向量模型加载 + sqlite-vec 检索（module + on_module_init）
├── trace/              # 追踪：recording / span / note，落会话库；module 暴露 /api/.../traces
├── chats/              # 预留目录
└── tests/              # pytest（agent 图、db、upload 等）
```

**目录层面最值得面试讲的设计**
1. **每个领域模块同构**：`entity / controller / service / repository / module`，职责清晰、易测、易扩展；新增领域（如曾经预留的 `chats`、`knowledge`）照抄即可。
2. **`db.py` 只做连接层**：业务表散落在各模块 `entity/`，`init_db()` 先 `register_entities()` 再 `create_all`——避免巨型 `models.py`。
3. **两层 SQLite**：主库（会话/消息/模型/角色，SQLModel）+ 每会话 `logs/session.sqlite`（短期记忆/工具轨迹/推理/追踪），读写分离、按会话隔离。
4. **`agents/` 是灵魂目录**：把“理解→路由→分档执行→核对”拆成图与节点，是整个 Agent 能力的承载。

## 3. 目录为什么这样组织（面试可用论点）

| 决策 | 原因 | 面试话术 |
| --- | --- | --- |
| 三语言分仓但同仓库 | 各语言生态不互通（npm/cargo/pip），但共享一个产品；monorepo 便于统一版本与打包 | “用各语言最擅长的部分：Rust 安全编排、Python 吃 LLM 生态、TS 做现代 UI” |
| 后端按领域分模块 | 业务复杂（会话/模型/角色/工具/技能各自演进），分层后变更互不污染 | “领域驱动 + 四层分层，controller 只管路由、service 管逻辑、repository 管持久化” |
| 连接层与业务表分离 | db.py 通用、可复用；迁移逻辑集中 | “连接/事务/向量扩展是横切关注点，单独抽出来” |
| 工具按分组（MCP id）放 | 与前端设置页 `MCP_SERVERS` 对齐、能力探测后决定是否注册 | “工具被设计成可插拔的分组，未探测到运行时不注册，避免调用不存在的能力” |
| 构建脚本独立在 `tools/` | 冻结后端、冒烟测试是发布流程的一部分 | “打包是把 PyInstaller 产物当资源塞进 Tauri，脚本化保证可重复” |

## 4. 面试时可能被追问的“目录问题”与应答

- **Q：前端怎么找到后端地址？** → `commands.rs` 暴露 `backend_url()`；`lib.rs` 在后端就绪后 `emit("backend-ready", url)`；`api.ts` 的 `getBackendUrl()` 缓存它，之后所有请求直连 Python。
- **Q：Python 进程怎么起来的？** → Rust `backend.rs::spawn_backend` 作为子进程拉起；dev 用 `.venv`+源码（带 `--reload`），release 用 PyInstaller 冻结的 `backend.exe`。
- **Q：数据库文件放哪？** → Rust 决定路径（`app_data_dir`），经 `CHATVEIN_DATA_DIR` 注入 Python；因为打包后的后端在只读资源目录，不能写库。
- **Q：新增一个业务接口要动几个地方？** → 后端加 FastAPI 路由（通常落在某模块 `controller.py`），前端在 `api.ts` 加一个 `backendRequest` 封装，视图里调用——**不用改 Rust**。
- **Q：新增一个工具要动几个地方？** → 在 `mcps/tools/` 写 `@tool` 实现，在 `registry.py`/分组里登记，必要时更新 `agents.md` 矩阵与前端 `MCP_SERVERS`。
