## 1 这个 Agent 和市面通用 Agent 的区别

市面通用 PC Agent（ChatGPT 桌面版、Claude Code、豆包等）的形态是：**一个对话框 + 一个全能 Agent + 一组工具**。

Forge/Chatvein 在具备这套**普通对话**能力的同时，有一个特殊能力：

> **可以"建立 Agent 角色"，给不同角色分配不同的 LLM，然后像企业微信一样"拉群"——把多个角色拉进一个群里，在群聊中讨论、分工、共同解决任务。**

因此产品有两种并存的交互形态：

| 形态 | 类比 | 参与方 | 适用 |
|------|------|--------|------|
| **普通对话** | 和 ChatGPT/Claude 单聊 | 用户 ↔ 1 个 Agent（可带工具） | 问答、单步任务、快速编码 |
| **群组协作** | 企业微信群里 @ 同事讨论 | 用户 + N 个**角色 Agent**（+ 主持人） | 需要多视角/多专长/辩论/评审的复杂任务 |

两种形态共用同一套底层能力（模型网关、工具、记忆、向量、可观测），区别只在**会话编排**。

## 2 核心概念模型

```
User
 │
 ├─ Conversation（普通对话会话）
 │     └─ Agent（单一运行体）
 │           ├─ persona / system prompt
 │           ├─ model（一个 LLM 绑定）
 │           ├─ tools（可用工具集）
 │           └─ memory（个人记忆）
 │
 └─ Group（群组会话，"拉群"）
       ├─ topic / 任务目标
       ├─ members: GroupMember[]（每个成员 = 一个 AgentRole 的实例）
       ├─ facilitator（主持人 Agent，可选：路由发言/收敛）
       ├─ messages: GroupMessage[]（群消息流，类企业微信）
       └─ groupMemory（群组共享记忆，见 05 文档）
```

### 2.1 AgentRole（角色模板）

"建立 Agent 角色"创建的是可复用模板：

```ts
interface AgentRole {
  id: string                       // 角色 id，如 'architect'
  name: string                     // 展示名，如 '架构师'
  avatar?: string
  persona: string                  // 人设/系统提示词（性格、专长、说话风格）
  expertise: string[]              // 专长标签，用于拉群推荐/路由
  model: {
    tier: 'strong' | 'medium' | 'weak'   // 模型档（复用 @chatvein/models 分级）
    modelId?: string               // 也可直接钉死某个具体模型
    temperature?: number
  }
  tools: string[]                  // 该角色允许使用的工具白名单（子集）
  memoryScope: 'personal' | 'group' | 'global'  // 记忆可见范围
  builtin?: boolean                // 内置角色（主持人/记录员）不可删
}
```

关键点：**角色 = 人设 + 模型绑定 + 工具权限 + 记忆范围**。不同角色可分配不同 LLM（架构师用强模型，记录员用弱模型省 token）。

### 2.2 Group / GroupMember / GroupMessage

```ts
interface Group {
  id: string
  name: string
  topic: string                    // 群议题/任务
  memberIds: string[]              // 角色 id 列表
  facilitatorId?: string           // 主持人角色 id
  mode: 'free' | 'facilitated' | 'vote'  // 讨论模式，见 02 文档
  status: 'active' | 'converged' | 'closed'
  createdAt: number
}

interface GroupMessage {
  id: string
  groupId: string
  senderId: string                 // role id / 'user' / 'system'
  kind: 'say' | 'tool_call' | 'tool_result' | 'decision' | 'vote' | 'summary'
  content: string
  mentions?: string[]              // @ 谁（@某个角色 → 触发其发言）
  replyTo?: string                 // 回复某条消息
  toolCalls?: ToolCallRef[]
  tokens?: { prompt: number; completion: number; model: string }
  ts: number
}
```

群消息流在 UI 上就是企业微信式的消息列表；`@角色` 决定下一个发言者，`decision/vote/summary` 是结构化的收敛产物。

## 3 与现有 `@chatvein/*` 架构的关系

现有 harness 包（见 [`../phase1/04-依赖选型.md`](../phase1/04-依赖选型.md)）大部分可直接复用，新增 3 个能力包：

| 包 | 状态 | 在本骨架中的职责 |
|----|------|------------------|
| `@chatvein/models` | 已有 | 扩展：从"强/中/弱分档"扩展为**角色级模型绑定**（每个 role 一个 model 实例 + 降级链 + 计量） |
| `@chatvein/tools` | 已有 | 扩展：**角色级工具权限**（role.tools 白名单过滤） |
| `@chatvein/sandbox` | 已有 | 群内代码/命令执行的隔离环境 |
| `@chatvein/observability` | 已有 | 群消息、模型调用、工具调用全部落 trace |
| `@chatvein/context` | 已有 | 上下文截断/预算；群聊多发言者的上下文装配 |
| `@chatvein/orchestrator` | 已有 | Forge 任务图（plan→implement→verify…），**任务型**编排 |
| **`@chatvein/agents`** | 🆕 新增 | **Agent 运行时**：单个 Agent 循环（ReAct 等）+ 角色加载 + 工具绑定；普通对话与群成员都由它驱动 |
| **`@chatvein/groups`** | 🆕 新增 | **群组会话**：建群/拉人、消息流、发言路由（主持人/@/轮转）、收敛投票；见 02、05 文档 |
| **`@chatvein/memory`** | 🆕 新增 | 分层记忆（个人/群组/全局）+ 读写管线；见 03 文档 |
| **`@chatvein/vector`** | 🆕 新增 | 嵌入 + PGlite/pgvector 向量存储与混合检索；见 04 文档 |

依赖方向仍然单向、无环，且全部纯 Node、零 electron：

```
models ─┐
tools ──┼─→ agents ─→ groups
context─┤      │        │
vector ─┼─→ memory ◀─────┘
observability（横切，被所有包写事件）
         ▲
         │ 全部作为 Cordis 插件挂到 @chatvein/core 的根 Context
```

**插件运行时**：统一使用 `@deepseek-ai/cordis`（见 [`06-插件运行时-Cordis.md`](./06-插件运行时-Cordis.md)）。  
`orchestrator`（Forge 任务图）与 `groups`（群聊）是两种编排范式，但都以 Cordis 插件形式挂载——前者内部跑 LangGraph，后者内部跑群路由。

> `orchestrator` 与 `groups`：前者适合自动写代码-测试-修复；后者适合讨论/评审。群结论可派单给 orchestrator（见 §7）。

## 4 角色系统设计

### 4.1 角色从哪来

1. **内置角色**：主持人（Facilitator）、记录员（Notary，弱模型，负责纪要）、可选的通用编码者。
2. **用户自建角色**：在控制台"新建角色"，填名称、人设、选模型档、勾选工具。存为本地角色库，可反复拉群。
3. **模板角色**：预置"架构师 / 前端 / 后端 / 测试 / 产品 / 安全评审"等，一键选用。

### 4.2 角色与模型的绑定（省 token 的关键）

角色不直接写死模型，而是绑定**模型档 + 可选覆盖**：

| 角色类型 | 建议档 | 理由 |
|----------|--------|------|
| 架构师 / 复杂编码 / 主持人 | strong | 推理质量 |
| 前端/后端执行 | medium | 成本均衡 |
| 记录员 / 摘要 / 检索改写 | weak | 机械任务省 token |

`@chatvein/models` 的 `ModelRouter` 增加 `routeForRole(role)`：返回该角色的模型（含降级链）。同一角色的多次调用复用同一连接与**前缀缓存**（见 03 文档）。

### 4.3 角色与工具的权限

每个角色的 `tools` 是全局工具集的**子集**。例如：记录员无 `exec_shell`；安全评审只读（read/grep/glob）；编码者有 write/patch/exec。工具调用经 `@chatvein/tools` 的统一超时/截断/白名单，再叠加角色权限校验。

## 5 "拉群"与群消息流（企业微信式）

### 5.1 建群流程

1. 用户点"新建群聊"，填议题（要解决的任务/问题）。
2. 系统按 `expertise` 推荐角色，用户勾选（或手动 @ 拉入）。
3. 可选指定主持人；不指定则用 `free` 模式（谁被 @ 谁说话）。
4. 群创建 → 主持人（或系统）发第一条"议题"消息 → 讨论开始。

### 5.2 发言路由（谁下一个说话）

三种模式（详见 [02-agent循环方案.md](./02-agent循环方案.md)）：

- **free（自由/@驱动）**：像微信群，用户或某 Agent `@另一角色` 触发其发言；无人被 @ 时主持人决定是否点名。
- **facilitated（主持人主持）**：每轮由主持人根据讨论进展指定下一个发言者（类 LangGraph supervisor）。
- **vote（辩论+投票）**：各角色独立给出方案 → 投票/打分 → 主持人宣布收敛结论。

### 5.3 收敛与产出

群聊不是无限讨论，需要收敛信号：

- 主持人检测到"意见一致/分歧已解决"→ 发 `decision` 消息；
- 或进入 `vote`：收集各角色方案 → 计票 → 胜出方案写成 `decision`；
- 记录员把结论写成 `summary` 存入**群组记忆**（见 05 文档）；
- 若结论是"要去执行某个编码任务"，可一键**派单**给 Forge orchestrator。

## 6 普通对话模式

普通对话就是 `groups` 的退化形态（群里只有 1 个 Agent + 用户）：

- 一个 `Conversation` 持有一个 Agent（默认角色"通用助手"，strong 档，全工具）。
- Agent 跑单 Agent 循环（ReAct，见 02 文档）。
- 记忆走个人记忆（03 文档），向量检索个人/全局知识库。
- UI 就是常规聊天框；可随时"把这个对话升级成群"（一键拉相关角色进来继续）。

这样**普通对话和群组是同一套消息/记忆/模型抽象**，不是两套系统。

## 7 运行时数据流

### 7.1 普通对话

```
用户消息
  → agents.Agent.handle(msg)
     → memory.recall(query)        # 个人+全局记忆，向量+BM25 混合检索
     → 组装上下文（缓存友好的前缀排序，见 03 文档）
     → models.routeForRole(role) → LLM（流式）
     → 若需工具：tools 调用（角色权限 → 超时/截断 → trace）
     → 循环直到产出
  → memory.write(新事实/摘要)
  → observability 落 trace
  → 流式回推 UI
```

### 7.2 群组讨论

```
用户/某角色发消息 → groups.appendMessage()
  → groups.router 决定下一个发言者（@ / 主持人 / 轮转）
  → 被选中的 agents.Agent.handle(群上下文)
       群上下文 = 群设定 + 该角色人设 +【群组记忆检索结果】+ 最近 N 条消息
  → 产出 GroupMessage（say / tool_call / decision / vote）
  → 广播到群（UI 实时 + trace）
  → 检查收敛 → 未收敛继续路由；收敛 → 记录员写 summary / 派单
```

### 7.3 群 ↔ Forge 任务图

群负责"想清楚/评审/定方案"，Forge orchestrator 负责"自动写代码-测试-修复"。群讨论出的 `decision` 可作为任务输入派给 orchestrator；执行结果再回到群里通报，形成"讨论 → 执行 → 复盘"闭环。

## 8 数据模型（落 PGlite，见 04 文档）

| 表 | 关键字段 |
|----|---------|
| `roles` | id, name, persona, expertise[], model_tier, model_id, tools[], memory_scope, builtin, created_at |
| `conversations` | id, title, role_id, created_at, last_at |

向量列：`memories.embedding vector(<dim>)`、消息/代码块同样可嵌入（04 文档）。

## 9 接口面（Electron / CLI）

复用 `@electrum/*` 的控制器模式，app 主进程新增（薄调用层，不含逻辑）：

| 控制器通道 | 方法 | 说明 |
|------------|------|------|
| `role:*` | list / create / update / remove | 角色库管理 |
| `chat:*` | send / stop / history | 普通对话（流式事件回推） |
| `group:*` | create / addMember / post / mention / vote / converge / history | 群组会话 |
| `memory:*` | search / list / forget | 记忆查看与管理 |

CLI（`@chatvein/service`）侧可加 `forge chat`（单聊）与 `forge group`（无头群跑，用于回归/评测）。所有逻辑在 `@chatvein/agents|groups|memory|vector`。
