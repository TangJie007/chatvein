# 本体向量存储方案与架构

> 版本：v0.2 ｜ 日期：2026-09-03
> 上位：[`03-记忆方案.md`](./03-记忆方案.md)、[`01-核心骨架.md`](./01-核心骨架.md)
> 排期：[`../phase1/03-开发计划书.md`](../phase1/03-开发计划书.md) **CP2**（`packages/chatvein/vector` / `@chatvein/vector`）
> "本体"指 Agent 自身的知识库/记忆底座（非外部数据库服务）。要求：**进程内、零外部服务、可持久化、可随 app/sidecar 分发**。

---

## 1 选型结论

用 **LanceDB**（`@lancedb/lancedb`）作为本体向量库 + **Transformers.js 本地 BGE-zh** 嵌入：

- `@lancedb/lancedb@0.38.x`：嵌入式向量库（本地目录持久化，ANN / cosine，零外部服务）。
- `@huggingface/transformers` + `onnx-community/bge-small-zh-v1.5-ONNX`：512 维中文嵌入。
- 全文/BM25：可后续用 LanceDB FTS；与 observability 的 PGlite（trace）分库。

为什么不用别的：

| 方案 | 结论 |
|------|------|
| 外部 Postgres + pgvector | 需要起服务，不符合"桌面/sidecar 零部署" |
| PGlite + pgvector | 可行，但向量检索不如专用向量库；已改为 LanceDB，PGlite 仅留 trace |
| embedded-postgres（真实二进制） | ~100MB 平台二进制、杀软/打包坑，否决 |
| 纯内存向量库（如 hnswlib-node） | 原生模块、无元数据/事务，运维分散 |
| sqlite-vec | 可行但生态弱于 LanceDB |
| Chroma 等 | 独立依赖重，桌面嵌入成本高 |

LanceDB 单机单用户足够；未来要云端可换 `db://` URI。

## 2 架构位置

```
@chatvein/vector（`packages/chatvein/vector`，纯 Node）
  ├─ EmbeddingProvider   # BgeZhEmbedder（Transformers.js）/ 可选网关
  ├─ VectorStore         # LanceDB：upsert / vectorSearch / filter
  └─ Indexer             # 写入管线：切分 → 嵌入 → 入库（批量、异步）
        ▲
        │ 被调用
@chatvein/memory、@chatvein/tools、@chatvein/groups
        │
        ▼
LanceDB 目录（dataDir，如 userData/forge/vector 或 ~/.chatvein/vector）
```

- 与 `@chatvein/observability` 的 **PGlite（trace）分库**，互不耦合。
- 放在 sidecar（系统 Node）运行；Electron 主进程 in-process 需 externalize 原生绑定。

## 3 表结构

```sql
CREATE EXTENSION IF NOT EXISTS vector;

-- 通用向量内容表（记忆、知识、代码块、消息片段统一存这，用 kind/scope 区分）
CREATE TABLE IF NOT EXISTS vectors (
  id           TEXT PRIMARY KEY,            -- 内容寻址 hash 或 uuid
  scope        TEXT NOT NULL,               -- 'personal'|'group'|'global'|'code'
  owner_id     TEXT NOT NULL DEFAULT 'global', -- roleId / groupId / repoId
  kind         TEXT NOT NULL,               -- 'memory'|'message'|'code'|'doc'|'decision'
  content      TEXT NOT NULL,               -- 原文（紧凑）
  summary      TEXT,                        -- 摘要（进上下文用）
  meta         JSONB NOT NULL DEFAULT '{}', -- 路径/符号/标签/importance/source 等
  embedding    halfvec(1024),               -- 半精度，省 ~50% 存储；维度按嵌入模型
  created_at   BIGINT NOT NULL,
  updated_at   BIGINT NOT NULL
);

-- 向量索引（HNSW，余弦）——halfvec 用 halfvec_cosine_ops
CREATE INDEX IF NOT EXISTS vectors_embedding_idx
  ON vectors USING hnsw (embedding halfvec_cosine_ops);

-- 元数据过滤索引
CREATE INDEX IF NOT EXISTS vectors_scope_idx ON vectors (scope, owner_id, kind);

-- 全文检索（P0 用内置 FTS）
ALTER TABLE vectors ADD COLUMN IF NOT EXISTS fts tsvector
  GENERATED ALWAYS AS (to_tsvector('simple', content)) STORED;
CREATE INDEX IF NOT EXISTS vectors_fts_idx ON vectors USING gin (fts);
```

要点：
- **`halfvec`**：16 位半精度浮点，存储减半、召回损失极小；维度按嵌入模型定（如 1024/1536/768）。`halfvec` 支持到 4000 维，足够。
- **scope/owner_id**：天然做多租户隔离（个人记忆、某个群的记忆、全局、代码库）。
- **meta JSONB**：存 importance、文件路径、符号、消息 id 等，检索时可结构化过滤。
- 内容去重：`id` 用内容 hash，upsert 幂等。

## 4 嵌入模型（EmbeddingProvider）

- **本地默认（已落地）**：`@huggingface/transformers` + `onnx-community/bge-small-zh-v1.5-ONNX`（512 维，中文检索友好；零网关 token）。见 `@chatvein/vector` 的 `createBgeZhEmbedder`。
- **云端备选**：赛事/OpenAI 兼容网关 embeddings（`@langchain/openai` / `/v1/embeddings`），维度须与本地索引隔离或重建。
- 维度与模型绑定后**不要中途换**（换模型 = 向量空间不兼容，需要重建索引）。在 `meta`/配置里记录 `embedding_model` 版本。
- 云端嵌入经 `@chatvein/models` 的计量与降级链；本地嵌入不走计量。

## 5 写入管线（Indexer）

```
原始内容（消息/记忆/代码文件/文档）
  → 切分 chunking：
       · 记忆/消息：按条目或语义段
       · 代码：按符号/函数/类（可复用 codegen 的 ts-morph 扫描），保留 path + symbol
  → 批量嵌入（攒批，弱依赖、异步，不阻塞主循环）
  → upsert vectors（id=hash，embedding=halfvec，meta 带 scope/owner/importance）
  → trace 记录写入条数/耗时/token
```

- 代码索引按需触发（建库、文件变更增量更新），不做无谓全量。
- 记忆写入与 [`03-记忆方案.md`](./03-记忆方案.md) 的写管线共用：提炼出 semantic 记忆时顺手嵌入。

## 6 检索：混合检索（向量 + 关键词）

纯向量对"精确符号/文件名/错误码"不敏感，必须混合：

```
search(query, { scope, ownerId, kind, k, budget })
  ├─ 向量召回：embed(query) → ORDER BY embedding <=> $q  LIMIT N（cosine）
  ├─ 关键词召回：plainto_tsquery('simple', query) → fts @@ q（P0）
  │             （P1 可换 pg_textsearch BM25，质量更好）
  ├─ 结构化过滤：scope/owner_id/kind/importance 可在 WHERE 中限定
  └─ 融合：RRF（Reciprocal Rank Fusion）合并两路排名 → 取 top-k
```

- RRF 无需调权重分数，工程上稳：`score = Σ 1/(k + rank_i)`。
- 返回的不是整段原文，而是 `{ summary, ref, score, meta }`；需要全文再按 ref 精确取（省上下文）。
- k 受 [`03-记忆方案.md`](./03-记忆方案.md) 的预算动态控制。

## 7 部署与持久化

- `dataDir`：放用户数据目录（如 `app.getPath('userData')/forge/pglite` 或 sidecar 的 `~/.chatvein/store`）。PGlite 直接持久化到文件系统。
- 单例：进程内一个 PGlite 实例，启动时 `CREATE EXTENSION vector` + 建表（幂等迁移）。
- 备份/导出：直接复制 dataDir；或导出 JSONL（与 trace 一起进 `runs/` 或用户库）。
- 版本升级：schema 用简单的 `CREATE TABLE IF NOT EXISTS` + 版本号表做迁移；嵌入模型变更 → 标记重建索引。

---

## 8 容量与性能预期（单机）

- PGlite/WASM 单进程，适合**个人 Agent 的记忆 + 单个/少量代码库**量级（数万~数十万 chunk）。HNSW 在此量级查询毫秒级。
- 内存：WASM + 索引占内存，大库用文件持久化 + 控制并发；避免一次加载超大结果集。
- 若未来要跨项目/超大代码库/服务化，把连接串从 PGlite 换成真实 Postgres（SQL/pgvector 不变）即可水平扩展。

---

## 9 验收要点

1. 建库幂等：重复启动不报错，扩展/表存在。
2. 写入后能按 cosine 召回相关条目，且 scope/owner 过滤生效（个人记忆不串群）。
3. 混合检索对"精确符号/文件名"能命中（关键词路），对"语义相近描述"也能命中（向量路）。
4. 换嵌入模型时能检测维度/版本不一致并提示重建。
5. 嵌入调用走计量、可降级；批量异步写入不阻塞对话。
6. 纯 Node（sidecar）可跑，无 electron 依赖。
