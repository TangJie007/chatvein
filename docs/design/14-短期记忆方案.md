## 1 要解决的问题

落地前，`ChatService.send()` 每轮把会话**全量历史**拼成数组喂给 ReAct Agent：

| 问题 | 后果 |
|------|------|
| 上下文随轮数线性增长 | token 线性膨胀，长会话必然撞上下文上限 |
| 无 token 预算 | 单条超长消息（工具输出/粘贴代码）可能一次打爆请求 |
| 无稳定前缀 | 历史每轮都变，prompt 缓存逐轮失效 |
| 无压缩 | 「前 50 轮说过什么」只能靠全量重放，贵且不治本 |

短期记忆的目标：**让进上下文的历史量恒定为 O(1)，同时不丢掉对当前轮有用的前文信息。**

---

## 2 方案总览

一个会话的历史被切成两段：

```
┌─ 稳定前缀（跨轮不变，缓存命中区） ────────────────────┐
│ 1. system prompt（人设 + 路由约束）                    │
│ 2. 摘要块 ShortTermState.summary（system 角色）        │ ← 只在摘要更新时才变
├─ 易变后缀（不指望缓存） ──────────────────────────────┤
│ 3. 近因窗口：最近 N 条 user/assistant（逐字）          │ ← 每轮滑动
│ 4. 本轮用户消息                                        │
└──────────────────────────────────────────────────────┘
        ↑ 被挤出窗口的旧消息 → 增量合并进 2（滚动摘要）
```

三个机制：

| 机制 | 作用 | 对应函数 |
|------|------|---------|
| **近因窗口 activeWindow** | 保证最近几轮逐字可见，指代/追问不失真 | `planShortTerm()` |
| **滚动摘要 rollingSummary** | 旧消息压缩成紧凑条目，增量合并、越老越粗 | `consolidateShortTerm()` |
| **token 预算护栏** | 摘要 + 窗口总估算不超上限，超了先缩窗口再折叠 | `planShortTerm()` + `truncateFolded()` |

## 3 数据结构

### 3.1 会话状态（落盘）

```ts
interface ShortTermState {
  version: 1
  /** 已并入摘要的最后一条消息 id（摘要游标） */
  summarizedThroughId: string | null
  /** 已并入摘要的消息条数（可观测） */
  summarizedCount: number
  /** 摘要正文（紧凑条目，非逐字原文） */
  summary: string
  updatedAt: number
}
```

- 游标用**消息 id**而非下标：retry 会截断消息数组，下标会错位；id 找不到时视为游标失效，重新累积（幂等、安全）。
- 摘要是**派生态**：随会话工作区删除，不进 SQLite `messages` 表，不参与历史重放。

### 3.2 配置（`DEFAULT_SHORT_TERM_CONFIG`）

| 项 | 默认 | 含义 |
|----|------|------|
| `activeMessages` | 8 | 近因窗口保留的 user+assistant 条数（约 4 轮） |
| `maxMessageTokens` | 1200 | 窗口内单条上限，超出走头尾折叠 |
| `maxContextTokens` | 6000 | 摘要 + 窗口的总预算（不含 system prompt 与本轮消息） |
| `maxSummaryTokens` | 1200 | 摘要块上限 |
| `summaryMaxChars` | 1500 | 摘要正文字符上限（弱模型输出约束 + 抽取式降级上限） |
| `summarizeEvery` | 6 | 窗口外累计多少条未摘要消息触发一次合并 |
| `summaryAsSystemPrefix` | true | 摘要块作为 system 消息前置（缓存友好） |

## 4 读路径：`planShortTerm()`

```
会话全量消息
  → 剔除 system / 失败占位气泡
  → 按摘要游标切分：已摘要 | pending（窗口外未摘要）| active（窗口内）
  → ① 摘要块超 maxSummaryTokens → 折叠
  → ② 窗口内单条超 maxMessageTokens → 折叠（头 60% + 尾 40% + 省略标注）
  → ③ 仍超总预算 → 从窗口最老一条往外挤（最少保留 2 条，即最近一问一答）
  → 输出 { summaryBlock?, active, pending, stats }
```

**预算收缩顺序是刻意的**：「宁可少召回，也不爆上下文」——先压摘要，再压单条，最后才牺牲窗口。

`stats` 直接进思考面板与 `llm_debug`，便于复盘：

| 字段 | 含义 |
|------|------|
| `activeCount` / `summarizedCount` / `pendingCount` | 三段各多少条 |
| `estimatedTokens` | 摘要 + 窗口的估算 token |
| `truncatedCount` | 本轮被折叠的消息数 |
| `cursorValid` | 摘要游标是否命中（false = 状态与消息不一致，按未摘要处理） |

## 5 写路径：`consolidateShortTerm()`

- **触发**：每轮回复落库后**异步**执行（不阻塞返回），按会话串行（`shortTermQueue`）。
- **条件**：窗口外的 `pending` 条数 ≥ `summarizeEvery`；不足则原样返回（幂等）。
- **合并**：把 `pending` 与已有摘要一起交给弱模型，产出**合并后的新摘要**并推进游标。
- **降级**：摘要器缺失 / 抛错 / 超时 / 返回空 → 走**抽取式摘要**（`extractiveDigest`：按句截断每条消息首段，拼紧凑条目，确定性输出）。关掉模型也能收敛。
- **成本**：weak 档模型、temperature=0、maxTokens=512、单条输入先按 400 字压缩；该调用**不计入**消息级 token 统计（属系统开销，通过 `llm_debug` 可见）。

摘要 prompt 的硬约束（见 `short-term/prompt.ts`）：只保留目标/约束/事实与数字/决定/待办/文件路径；丢弃寒暄、重复、推理过程与代码块全文；**不得新增对话中没出现的信息**；输出无标题的紧凑条目。

## 6 缓存友好性（对齐 03 文档 §5）

| 做法 | 效果 |
|------|------|
| 摘要块作为 **system 消息**放在窗口之前 | 与 system prompt 一起构成稳定前缀 |
| 摘要块内容只在摘要更新时变化，无变化时逐字节复用 | 连续多轮命中缓存 |
| 易变的近因窗口与本轮消息放最后 | 不击穿前缀 |
| `renderSummaryBlock` 标题固定、`clampChars` 确定性 | 同样输入 → 同样输出 |

## 7 落点与接线

| 能力 | 落点 |
|------|------|
| token 估算 / 头尾折叠截断 | `@chatvein/context`（`tokens.ts` / `truncate.ts`） |
| 窗口 + 摘要 + 预算（纯逻辑、零 IO） | `@chatvein/memory`（`short-term/**`） |
| 摘要 prompt | `@chatvein/memory`（`short-term/prompt.ts`） |
| 落盘 `{workspacePath}/memory/short-term.json` | app `chat/short-term.store.ts`（原子写：tmp + rename） |
| 组装 history / 触发压缩 / 弱模型摘要器 | app `chat/chat.service.ts` |
| 进 Agent（裁剪） | `invokeReactChatAgent({ history })` —— 摘要块是 `role:'system'` 元素，`toLangChainMessages` 原样转 SystemMessage |
| 进 Agent（存储） | `WorkspaceCheckpointer`（LangChain checkpointer，`node:sqlite` 落盘 `{workspacePath}/memory/checkpoints.db`）；`ChatService` 每轮先 `deleteThread(threadId)` 再 `invoke(完整 history, threadId)`，thread 每轮从压缩 history 重置，**回复行为完全不变** |

调用链（一轮 Chat）：

```
ChatService.send()
  → readShortTermState(workspace)          # 读摘要状态
  → buildShortTermHistory() → planShortTerm()  # 摘要块 + 窗口
  → L1/L2 路由 → 工具绑定
  → getCheckpointer(workspace).deleteThread(id)   # 重置 thread（保持行为不变）
  → invokeReactChatAgent({ message, history, threadId: id })  # 走 LangChain checkpointer 落盘轨迹
  → persistAssistant()                      # 落库 SQLite + 思考日志
  → scheduleShortTermConsolidation()        # 异步：pending ≥ 6 → 弱模型合并摘要 → 落盘
```

**裁剪 vs 存储的分层**：自研短期记忆（`@chatvein/memory`）主导「每轮喂给模型的 history」（按 token 预算做窗口/摘要/折叠），是**裁剪层**；`WorkspaceCheckpointer` 是 LangChain 官方的「对话状态持久化」抽象，把每轮 ReAct 的**完整消息轨迹（含 ToolMessage）**落盘到 `checkpoints.db`，是**存储层**。两者各管一段，互不直接耦合：`send()` 仍每轮用自研压缩结果组装 history，仅把 thread 状态交给 checkpointer 持久化，因此回复内容 / token 预算 / 摘要逻辑全部不变，只是多出一份可跨进程、可 thread resume 的 agent 工作记忆快照。

> 注：checkpointer 落的是 LangGraph 视角的消息轨迹（含工具调用中间步骤），与 SQLite `messages` 表（UI 展示用的全量对话）是**两份互补存储**：前者面向「agent 重新进入图 / 崩溃恢复」，后者面向「界面与历史重放」。

`retry()` → `regenerateAfterUser()` 走同一套（`dropLast: true`，因为会话末尾那条就是本轮输入）。

可观测性：
- 思考面板新增一行：`短期记忆：窗口 8 条 / 摘要覆盖 22 条 / 待摘要 0 条 / 约 601 tokens`
- `llm_debug`：`react:request.shortTerm`（本轮裁剪结果）、`memory:short-term`（压缩结果，含摘要正文）

## 8 验收要点

1. 进上下文的历史量恒定：30 条消息的会话，窗口恒为 8 条 + 摘要（实测 `estimatedTokens` ≈ 600，不随轮数线性增长）。
2. 无摘要、模型不可用时对话**照常可用**（抽取式降级）——对应单测「未注入摘要器也能收敛」。
3. 摘要器抛错不影响本轮回复（错误被 `consolidateShortTerm` 吞掉并降级）。
4. 连续触发幂等：第二次 `consolidateShortTerm` 返回 `consolidated=0`。
5. 摘要游标失效（消息被删）时重新累积，不会丢消息。
6. 会话删除时摘要文件随工作区一起清除。
7. LangChain checkpointer 把本轮 ReAct 轨迹（含 ToolMessage）落盘到 `checkpoints.db`：单测覆盖 `put / getTuple / putWrites / deleteThread` 的序列化往返，以及**真实 ReAct `invoke` 经 checkpointer 落盘、可跨实例读取**的端到端验证（`react-agent.spec.ts`）。

单测：`packages/chatvein/memory/src/__tests__/short-term.spec.ts`（16 例）、`packages/chatvein/context/src/__tests__/context.spec.ts`（7 例）、`packages/chatvein/agents/src/__tests__/workspace-checkpointer.spec.ts`（3 例）+ `react-agent.spec.ts`（4 例，含 checkpointer 端到端）。
