# 群组记忆架构设计（≥2 方案）

> 版本：v0.1 ｜ 日期：2026-09-03
> 上位：[`01-核心骨架.md`](./01-核心骨架.md)、[`03-记忆方案.md`](./03-记忆方案.md)、[`04-向量存储架构.md`](./04-向量存储架构.md)
> 目标：在"企业微信式多角色群聊"里，让每个角色既能协作共享知识，又**不把整段群历史塞进每个角色的上下文**（省 token、利于 prompt 缓存）。

---

## 1 问题定义

群聊里有 N 个角色 + 用户。若每人发言前都读**全部群消息**，会出现：

1. **Token 爆炸**：消息线性增长 × N 个发言者 = 平方级消耗。
2. **缓存失效**：每人的上下文前缀不断被新消息改写，prompt 缓存打不中。
3. **隐私/权限混乱**：记录员不该看代码 diff 细节；安全评审不该写文件；某角色的个人偏好不该泄漏给全群。
4. **噪声**：无关闲聊污染每个角色的决策。

因此需要一套**群组记忆架构**：决定"什么共享、什么私有、如何写入、如何召回、如何进上下文"。

---

## 2 共享的抽象（两个方案共用）

不论选哪个方案，先统一三类记忆归属（与 [`03-记忆方案.md`](./03-记忆方案.md) 的 `scope` 对齐）：

| scope | 归属 | 谁可读 | 谁可写 | 例子 |
|-------|------|--------|--------|------|
| `personal` | 某个角色自己 | 仅该角色 | 该角色（及其提炼器） | "我偏好先写测试"、个人笔记 |
| `group` | 某个群 | 群内成员 | 记录员/主持人/达成共识后写入 | 议题、决议、群共识事实 |
| `global` | 全局 | 所有会话 | 系统/用户显式沉淀 | 项目规范、长期技能 |

群消息全文落 **episodic**（PGlite + JSONL，可检索），但**默认不整段进上下文**；进上下文的是检索命中 + 群 digest。

## 3 方案 A：共享黑板（Shared Blackboard）

### 3.1 思路

群里维护一块**结构化黑板**（blackboard），所有角色读写的是同一块共享状态，而不是彼此的私聊历史。

```
┌──────────────── Group Blackboard ────────────────┐
│ topic / 目标                                      │
│ facts[]          # 已确认事实                      │
│ open_questions[] # 未决问题                        │
│ proposals[]      # 各角色方案（带 author）          │
│ decisions[]      # 已决议（不可轻易改）             │
│ artifacts[]      # 产出物引用（文件/diff/报告）     │
│ rolling_summary  # 滚动摘要（弱模型维护）           │
└──────────────────────────────────────────────────┘
         ▲ write（结构化更新）
         │
   各角色发言后 → 提炼器/记录员把"有价值的变化"写入黑板
         │
         ▼ read
   下一角色发言时：人设 + 黑板快照 +（可选）少量相关消息片段
```

### 3.2 读写规则

- **读**：每个角色发言前拿到同一份 blackboard 快照（可按角色权限裁剪字段，如记录员只看 summary/decisions）。
- **写**：角色**不直接改黑板**；发言结束后由记录员（弱模型）或规则引擎把新内容 merge 进黑板（去重、冲突标注）。
- **消息流**：仍保留完整 `GroupMessage[]` 供 UI 与审计，但模型侧主要看黑板。

### 3.3 进上下文的布局（配合缓存）

```
稳定前缀：系统 + 角色人设 + 工具定义 + 该角色 personal digest
半稳定：  黑板快照（仅在黑板变更时变化；按字段固定顺序序列化）
易变后缀：本轮被 @ 的原文 / 最近 1~2 条相关消息
```

黑板变更频率远低于消息频率 → 半稳定段仍有较高缓存命中率。

### 3.4 优缺点

| 优点 | 缺点 |
|------|------|
| Token 可控：上下文≈O(黑板大小)，与消息数解耦 | 提炼质量依赖记录员；提炼错会污染全群 |
| 天然结构化，便于投票/收敛/派单给 Forge | 丢失"语气/争论过程"等软信息（需偶尔回查消息） |
| 权限裁剪简单（按字段） | 实现要设计好 schema 与 merge 冲突策略 |
| 利于缓存 | 自由闲聊体验略弱于"人人看全文" |

适用：任务型群（定方案、评审、分工），以及比赛控成本场景。与 [`02-agent循环方案.md`](./02-agent循环方案.md) 的 **Supervisor / facilitated** 模式绝配。

## 4 方案 B：分角色视角记忆（Per-Member View + 共享摘要）

### 4.1 思路

不强制统一黑板，而是：**每个角色维护自己的"群视角记忆"**，再加一份**轻量共享摘要**。

```
Group
 ├─ shared_digest          # 群级滚动摘要 + 决议列表（短）
 ├─ memberViews[roleId]    # 每个角色自己的：关注点、笔记、待办、相关片段引用
 └─ messages[]             # 全量消息（检索用，不全进 prompt）
```

角色发言时：

```
召回 =
  personal 记忆
  + shared_digest（短）
  + 自己的 memberView
  + 向量/关键词检索到的少量群消息/群记忆（top-k，且可过滤 kind）
```

不同角色对同一群历史的"看见"不同：架构师多召回设计相关；测试多召回验收相关。

### 4.2 写入

- 每次发言后：异步更新该角色的 `memberView`（弱模型：从本轮对话抽"对我重要的点"）。
- 周期性/收敛时：记录员把跨角色共识写入 `shared_digest` / `group` scope 记忆。
- 用户显式"钉住"的决议 → 直接进 `group` 记忆与 `decisions` 表。

### 4.3 进上下文布局

```
稳定前缀：系统 + 人设 + 工具 + personal digest
半稳定：  shared_digest（短）+ 自己的 memberView
易变后缀：本轮检索到的群片段 + 最近对话
```

### 4.4 优缺点

| 优点 | 缺点 |
|------|------|
| 更像真人协作：各有视角，减少无关噪声 | 实现比黑板复杂（N 份视角要维护） |
| 个人偏好/私有笔记不泄漏 | 共享信息可能滞后（靠 digest/收敛补） |
| 仍可控 token（top-k + digest） | 缓存命中略弱于纯黑板（memberView 更常变） |
| 适合开放讨论、头脑风暴 | 需要防止视角漂移导致"各说各话" |

适用：开放式讨论、多视角评审、长期群。与 **free / @驱动** 模式更搭。

## 5 方案对比

| 维度 | A 共享黑板 | B 分角色视角 |
|------|-----------|-------------|
| Token | 更低、更稳 | 中低（依赖 top-k） |
| Prompt 缓存 | 更好（黑板变更才动前缀） | 中等 |
| 实现成本 | 中（schema + merge） | 中高（N 视角） |
| 协作一致性 | 高（单一事实源） | 中（靠 digest 对齐） |
| 自然度/多样性 | 中 | 高 |
| 失败模式 | 提炼污染全群 | 信息孤岛、重复争论 |
| 推荐场景 | 任务收敛、比赛 | 开放讨论、长期群 |

---

## 6 推荐落地（混合，一期可执行）

**默认采用 A 为主、B 为辅的混合架构**：

1. **P0**：上线 **共享黑板**（方案 A）作为群组记忆主通道 + 全量消息落盘可检索。
   - 群 `mode=facilitated|vote` 强制走黑板。
   - `mode=free` 也写黑板，但发言上下文可额外带最近 N 条消息（N 小，如 6）。
2. **P0+**：为每个角色加轻量 `memberView`（方案 B 的子集：只存"我的待办/我关注的问题"，不做完整私人副本），提升多样性且不显著抬 token。
3. **召回**：群相关检索一律走 [`04-向量存储架构.md`](./04-向量存储架构.md) 的 `scope='group' AND owner_id=groupId`，与 personal/global 隔离。
4. **收敛**：`decision` / 投票结果 → 写入黑板 `decisions[]` + `group` scope semantic 记忆（高 importance，难遗忘）。
5. **派单**：黑板里的 `decisions` / `artifacts` 可一键交给 Forge orchestrator 执行。

这样既满足"至少 2 个完整方案"的对比，又给出一条不打架的演进路径。

## 7 数据模型补充

```ts
interface GroupBlackboard {
  groupId: string
  topic: string
  facts: Array<{ id: string; text: string; sourceMessageIds: string[]; updatedAt: number }>
  openQuestions: Array<{ id: string; text: string; askedBy: string }>
  proposals: Array<{ id: string; authorId: string; text: string; score?: number }>
  decisions: Array<{ id: string; text: string; locked: boolean; sourceMessageIds: string[] }>
  artifacts: Array<{ id: string; kind: string; ref: string; summary: string }>
  rollingSummary: string
  version: number                 // 变更版本，用于缓存失效判定
  updatedAt: number
}

interface MemberView {
  groupId: string
  roleId: string
  notes: string[]                 // 对我重要的短笔记
  todos: string[]
  watchedQuestionIds: string[]
  updatedAt: number
}
```

持久化：黑板 / memberView 存 PGlite（JSONB 列即可）；其摘要与决议同时 upsert 进 `vectors` 表（`scope=group`）供语义召回。

## 8 运行时钩子（接 `@chatvein/groups`）

| 时机 | 动作 |
|------|------|
| 群创建 | 初始化空黑板（topic=议题） |
| 每条消息落库后 | 异步：是否更新黑板？是否更新发言者 memberView？ |
| 角色被选中发言前 | `assembleContext(role)` = 人设 + personal + 黑板(裁剪) + memberView + top-k 检索 |
| 出现 `decision` / 投票结束 | 锁定 decisions；写 group semantic；可选派单 |
| 群关闭 / 长间隔 | 巩固：rollingSummary 再压缩；低 importance 归档 |

预算：黑板体积有硬上限（如摘要 ≤ 800 tokens、facts ≤ 20 条）；超限触发 consolidate（弱模型归纳合并）。

---

## 9 验收要点

1. 同一群内连续 10 轮发言，单角色上下文中的"群相关"部分不随消息数线性暴涨（对照：纯全文方案会暴涨）。
2. 黑板 `version` 未变时，该角色稳定前缀 hash 不变（可测缓存友好性）。
3. `personal` 记忆不会出现在其他角色召回结果中；`group` 记忆仅群成员可见。
4. 收敛后 `decisions` 可被导出为 Forge 任务输入。
5. free / facilitated 两种 mode 都能跑通，且可切换。
