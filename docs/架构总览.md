## 1. 总体拓扑：三层 + 一个“消息层”定位

```text
┌─────────────────────────────────────────────────────────────┐
│  React (Vite + TS)  —— UI 层                                 │
│    • 会话列表 / 消息流 / 洞察面板 / 设置 / 追踪窗            │
│    • api.ts：统一封装，经 Tauri plugin-http 的 fetch 直连后端 │
└───────────────▲─────────────────────────────────────────────┘
                │  invoke("backend_url") 拿地址；之后 fetch 直连 Python
                │  （不走 Rust 代理，Rust 只在启动时推 URL + 转发日志）
┌───────────────┴─────────────────────────────────────────────┐
│  Rust / Tauri  —— 消息层（编排者，不是代理）                  │
│    • 启动 Python 侧车进程（spawn_backend）                    │
│    • 端口/数据目录决策（dev 8420；release 动态 ≥3000）         │
│    • 就绪探测 + emit("backend-ready", url)                    │
│    • 转发后端 stdout/stderr 为事件；退出时 kill_backend        │
└───────────────▲─────────────────────────────────────────────┘
                │ 子进程：Python 监听 127.0.0.1:port
┌───────────────┴─────────────────────────────────────────────┐
│  Python / FastAPI  —— 后端（真实业务）                        │
│    • /api/chat：LangGraph 编排（理解→路由→分档执行）          │
│    • /api/conversations|models|roles|mcps|skills|workspace    │
│    • SQLite（主库 SQLModel + 每会话 session.sqlite）+ 向量     │
└─────────────────────────────────────────────────────────────┘
```

## 2. 最关键的设计决策：Rust 是“消息层”而非请求代理

这是整个架构的“题眼”，面试务必先抛出来：

- **传统做法**：前端 → Rust 代理 → Python（每条请求都过 Rust 一次）。
- **ChatVein 做法**：Rust 在**启动时**把“真实后端 URL（含动态端口）”通过 `backend_url` 命令 + `backend-ready` 事件交给前端；之后 React 用 `fetch` **直连** Python。
- **Rust 的角色收敛为三件事**：
  1. **进程生命周期管理**：拉起 / 杀掉 Python 子进程；
  2. **URL 与路径提供者**：决定端口、数据目录，并推给前端；
  3. **日志/事件桥接层**：把 Python 的 stdout/stderr 转成前端可订阅的事件（`backend-stdout` / `backend-stderr` / `backend-error`）。

**为什么这样设计（要点）**
- 避免每请求多一跳 Rust 转发带来的延迟与复杂度（Agent 流式/长任务更敏感）。
- 让 Rust 专注它擅长且安全的“编排”，把 LLM/工具这类重业务逻辑交给 Python 生态（LangChain、SQLModel、sqlite-vec 都是 Python 一等公民）。
- 前端用 Tauri 的 `plugin-http` 的 `fetch`，请求实际在 Rust 的 reqwest 里发，**天然绕过浏览器 CORS / CSP**，所以直连没有跨域问题。

**面试话术**：
> “我们没有让 Rust 当逐请求的反向代理，而是让它做‘启动编排者’：负责把 Python 进程拉起来、探测就绪、把真实 URL 推给前端，之后前端直连 Python。Rust 只做进程管理、地址/路径决策和日志事件桥接。这样既保留了 Tauri 小体积、安全的优势，又让 Python 全权处理 LLM 编排这类重型逻辑，且前端直连没有 CORS 之扰。”

## 3. 进程与运行模型

### 3.1 启动顺序
1. Tauri（Rust）`Builder.setup` 中调用 `backend::spawn_backend(app)`。
2. Rust 解析端口（`OnceLock`，仅一次）：debug → 8420；release → `find_free_port(3000)`。
3. 决定数据目录：`app.path().app_data_dir()` → 经 `CHATVEIN_DATA_DIR` 注入；并建立目录。
4. 选定可执行文件：
   - **dev**：仓库根 `.venv` 的 python + `backend/main.py`，并设 `CHATVEIN_RELOAD=1`（uvicorn 热重载）。
   - **release**：资源目录 `backend-runtime/backend(.exe)`（PyInstaller 冻结产物）。
5. 启动子进程，`stdout`/`stderr` 各起一个线程 drain → `app.emit(event, text)`。
6. **不阻塞窗口**：`wait_for_backend` 在后台线程 TCP 探测（最多 20s）；成功 `emit("backend-ready", base_url)`，失败 `emit("backend-error", ...)`；setup 立即 `show` 主窗口。
7. 前端 `BackendGate` 先渲染 loading 壳（含 TitleBar），监听上述事件并并行轮询 `/api/health`；就绪后挂载 `App` 开始正常请求。

### 3.2 退出模型
- Rust `run()` 返回后调用 `kill_backend()`：杀掉 `BACKEND_CHILD` 中的 Python 子进程。

## 4. 后端模块架构（FastAPI + 分层）

每个业务域是“模块”，统一由 `module.py` 组装并暴露单例 `service` 与 `APIRouter`：

```text
请求 → APIRouter(controller.py 的路由)
        → Service（业务规则、编排）
        → Repository（SQLModel 持久化）
        → Entity（SQLModel 表模型）
```

- **`main.py` 装配**：`lifespan` 里 `init_db()` + 各模块 `on_module_init`（角色/向量模型等懒加载）；`include_router` 挂上 models/roles/embeddings/conversations/trace/skills。
- **`/api/chat` 主流程**（设计上最值得讲）：
  1. `conversations_service.open_for_chat` 确保会话 + `workspace_dir`；
  2. 读短期记忆、解析角色运行时、注入技能提示；
  3. `use_conversation_sandbox(workspace_dir)` 把“当前会话沙箱”绑到 contextvars；
  4. `run_pipeline` → LangGraph；
  5. `save_exchange`（主库消息） + `record_turn`（会话库记忆/工具轨迹/推理） + trace 落库；
  6. 返回 `reply / difficulty / tool_trace / workspace / tokens ...`。
- **横切**：CORS 全开（本地进程内通信，无外网暴露）、统一异常回落、schema 版本 `PRAGMA user_version`。

## 5. 核心流水线：理解 → 路由 → 分档执行 → 核对

### 核心是什么：**LangGraph 驱动的“理解→路由→分档执行→核对”流水线**

整个应用的能力心脏在 `backend/agents/`。一次 `/api/chat` 的本质是：把用户原文送进一张**总图**，先“理解并判难度”，再按难度进入 **simple / medium / hard** 三张子图之一。全程默认走**主模型**；角色可覆盖模型与生成参数。

```text
用户原文
   │
   ▼
┌──────────────────────────────────────────────┐
│ chat_pipeline（agents/graphs/pipeline.py）     │
│  START → understand（改写 + 难度路由）          │
│           ├─ simple  → simple 子图  → END       │
│           ├─ medium  → medium 子图  → END       │
│           └─ hard    → hard 子图    → END       │
└──────────────────────────────────────────────┘
   │
   ▼
run_pipeline 组装 reply / difficulty / tool_trace / trace
   │
   ▼
HTTP 落库（主库 + 会话库）+ 工作区洞察
```

| 模块 | 文件 | 职责 |
| --- | --- | --- |
| 入口 | `agents/graphs/pipeline.py` → `run_pipeline` | 对外唯一聊天入口 |
| 总图 | `agents/graphs/pipeline.py` | understand + 条件边分流 |
| 理解/路由 | `agents/router.py` | 主模型 structured：`rewritten` + `difficulty` |
| simple | `agents/graphs/simple.py` | 无工具单节点直答 |
| medium | `agents/graphs/medium.py` | 选型 → ReAct（`create_agent`） |
| hard | `agents/graphs/hard.py` | plan → 选型 → ReAct → verify（可回环） |
| 选型 | `agents/tool_selector.py` | 工具缩集 + 角色白名单展开（允许空集） |
| 状态 | `agents/graphs/state.py` | `ChatState` TypedDict |
| 记忆 | `agents/memory.py` | 历史 → LangChain messages |
| 共用 | `agents/graphs/common.py` | `last_text` / `build_react_graph` / `merge_tool_traces` |

---

### 共享状态 `ChatState`（图的“数据总线”）

`ChatState` 是 TypedDict，节点间通过它传值。关键字段：

```text
message          用户原文（HTTP 传入）
rewritten        改写后意图（下游只用这个，原文不替换用户气泡）
difficulty       simple | medium | hard
route_reason     路由理由
history          短期记忆（不含本轮用户句）
role             RolesService 运行时（可为空）
selected_tools / candidate_tools / tool_plan_reason
reply / used_llm / tool_trace
# hard 专用
plan / plan_text / verify_passed / verify_reason / verify_focus / verify_round
```

- **条件边只读 `difficulty`**：`hard → hard 子图`，`medium → medium`，否则 `simple`。
- **角色提示叠加**：`_merged_system(role, BASE)` 把角色 prompt 叠在“挡位 system”之上，避免丢掉工作区/工具约定。

---

### 三档子图详解

#### 3.1 simple（直答，无工具）
```text
START → chat → END
```
单次 `model.invoke([SystemMessage, …history, HumanMessage(rewritten)])`。闲聊/单句知识问答走这里，成本最低。

#### 3.2 medium（选型 → ReAct）
```text
START → select_tools → react → END
```
- `select_tools`：主模型从“已注册全量工具”里按改写文本选子集；`allowed` 经 `expand_allowlist`（分组 id 如 `mcp-web` 展开为组内工具名）；**允许空名单**（认为无需工具就直答，不强行塞默认工具）。
- `react`：`create_agent(model, tools, system)` 编译 agent⇄tools 循环，`recursion_limit = 2×n+10`（默认 34），抽最后文本为 `reply`，`extract_tool_trace` 记录工具调用。
- 适合“一两跳工具就能答”的任务；空转靠“工具/模型调用上限”收束。

#### 3.3 hard（plan → 选型 → ReAct → verify，可回环）
```text
START → plan → select_tools → react → verify
                      ▲                    │
                      └── 未通过且未达上限 ──┘
```
- `plan`：结构化 `TaskPlan`（goal / steps / success_criteria / risks），生成给人看的【执行计划】块。
- `select_tools`：查询串拼上 `plan_text`（若有 `verify_focus` 追加“上一轮未通过，请优先补…”）。
- `react`：`recursion_limit` 默认 42（`2×16+10`），便于“改代码→跑→看 stderr→再改”。
- `verify`：结构化 `VerifyDecision`（passed / reason / missing / next_focus），对照计划与 tool_trace 核对。
  - `passed` → 结束；
  - 未过且 `verify_round < 2` → 写 `verify_focus` 回 `select_tools` 再执行；
  - 达 2 轮仍不过 → **强制视为通过并收束**（防无限循环）；
  - 离线 → 有非空 reply 即通过。
- `tool_trace` **跨轮累计**，整轮追踪更完整。

## 6. 工具系统（进程内“MCP”，而非外置子进程）

工具是 Agent 能力的“手脚”。设计要点：

- **进程内 LangChain `@tool`**：不另起 `npx @playwright/mcp` 之类 Node 子进程，直接在当前 Python 进程里调用，体积小、启动快、与 `builtin://` 设计对齐。
- **注册表 + 按名 invoke**：`mcps/registry.py` 维护“工具名 → 实现”；`tool_selector` 只缩名字集，`resolve_tools(names)` 解析成可调用对象（名字无效回落全量）。
- **分组（MCP id）对齐前端**：`mcp-fs` / `mcp-web` / `mcp-sqlite` / `mcp-kb` / `mcp-codesandbox` / `mcp-bash` / `mcp-powershell` / `mcp-browser` / `mcp-ip` / `mcp-ocr` / `mcp-pdf` / `core` / `mcp-http`，与设置页 `MCP_SERVERS` 对齐。
- **能力探测（运行时决定注册与否）**：Bash（按需下 MinGit，失败则降级 PowerShell）、PowerShell（仅 Windows）、Browser（本机有 Chromium 才注册）、OCR/Web/IP 有各自降级链。**未探测到运行时不注册该分组**——避免在 Agent 里调用不存在的能力。
- **人工确认（HITL）不在图里**：Bash/PowerShell 的危险或写盘命令在“工具执行路径”上挂起，等前端 `BashApproval` 弹窗批准/拒绝（`/api/bash/{approve,deny}`）。这是把“不确定的人审”放在图节点之外，避免把对话阻塞在图状态机里。

工具矩阵（节选，详见 [`Agent流水线.md`](./Agent流水线.md)）：

| 分组 | 代表工具 | 说明 |
| --- | --- | --- |
| `core` | `get_current_time` / `calculator` / `get_system_info` | 时间/时区/计算/本机概况 |
| `mcp-fs` | `read_file` / `write_file` / `edit_file` / `list_directory` | 工作区文件读写（范围受限） |
| `mcp-web` | `web_search` / `web_fetch` | 多级降级搜索/抓取 |
| `mcp-sqlite` | `sqlite_tables` / `sqlite_query` | **只读**查主库 |
| `mcp-kb` | `kb_add_note` / `kb_search` | 笔记沉淀 + 向量/关键词召回 |
| `mcp-codesandbox` | `sandbox_run_python` | 会话 `runs/` 内 venv + 跑 Python |
| `mcp-bash` / `mcp-powershell` | `bash_run` / `powershell_run` | 限会话目录 + 危险拦截 + 确认 |
| `mcp-browser` | `browser_navigate` / `browser_click` / … | 进程内 Playwright |
| `mcp-ip` / `mcp-ocr` | `lookup_ip_region` / `ocr_image` | 免费降级链 |
| `mcp-pdf` | `pdf_read` / `pdf_merge` / `pdf_split` / `pdf_split_files` / `pdf_generate` | 读取 / 合并 / 拆分 / 逐页拆分 / 生成 / 加解密 |

## 7. 工作区沙箱（两层工作区，安全隔离的核心）

这是核心架构里最容易讲错、也最容易出彩的点。

```text
<主工作区 workspace_root>                （用户配置/容器，非真正沙箱）
  └─ <YYYYMMDD-HHMMSS-xxxxx>/             （会话工作区 = 真正的沙箱）
       output/       产物（用户需要的文件）
       logs/
         session.sqlite   本会话：短期记忆 / 工具返回 / 推理 / 追踪
       runs/        代码沙箱 .venv 与脚本（与产物隔离）
       uploads/     用户输入框拖入/选择的文件落盘处
       ocr_input/   OCR 图片落点
```

- **主工作区**：用户在设置页配置（或 `CHATVEIN_WORKSPACE`），落到 `CHATVEIN_DATA_DIR/workspace`。它是“容器”，Agent 不直接把它当沙箱。
- **会话工作区**：在主工作区下为每个会话生成 `YYYYMMDD-HHMMSS-xxxxx` 目录，才是 Agent 真正读写文件的**真正工作区**。
- **沙箱上下文**：`use_conversation_sandbox(workspace_dir)` 用 `contextvars` 把“当前会话目录”绑到线程上下文；此后 `current_sandbox()` / `resolve_in_sandbox()` 都相对会话目录。所以**工具实现无需知道会话 id**，只问“当前沙箱在哪”。
- **硬规则**：给 Agent 用的文件（上传图片/附件）必须落进**当前会话工作区**（带 `conversation_id` 调用 `/api/uploads`），否则新会话沙箱找不到它——“找不到图片”类报错的常见根源。
- **删除会话级联清工作区**：删除会话时一并删该 `YYYYMMDD-...` 目录，天然隔离、易清理。

## 8. 前端架构（React 视图 + 单一 API 层）

- **单一出口 `api.ts`**：所有领域请求都走 `backendRequest(endpoint, method, body, signal)`；它内部 `await waitForBackend()` 保证后端就绪，再用 Tauri `fetch` 直连。这把“等后端 + 直连 + 错误归一”收敛到一处。
- **视图切换**：`App` 用 `view` state 在 ChatView/ModelsView/RolesView/... 间切换；Sidebar 负责导航与计数。
- **核心状态在 `ChatView`**：会话列表、消息流、洞察（轨迹/产物）、发送/停止/撤回。关键设计：
  - 用 `AbortController` + `abortRef` 实现“停止生成”；
  - 乐观插入用户/助手气泡（`pendingRef` 记录 id 原文），便于精确撤回；
  - 后端是同步落库，停止 HTTP 后可能仍在生成 → 前端 `cleanupLastTurn` 轮询删除最近一轮（最多 ~6.4s），处理“异步落库 vs 同步请求”的不一致。
- **Trace 独立窗口**：`?view=trace&conversation=&turn=` 打开 `TraceShell`，与主界面解耦。

## 9. 双层持久化

| 库 | 位置 | 内容 | 技术 |
| --- | --- | --- | --- |
| 主库 | `CHATVEIN_DATA_DIR/chatvein.db` | 会话、消息、模型、角色 | SQLModel（SQLAlchemy2 + Pydantic） |
| 向量 | 同主库 `vec0` 虚拟表 | embedding 检索 | sqlite-vec（逐连接加载） |
| 会话库 | `<会话工作区>/logs/session.sqlite` | 短期记忆、工具返回、推理、整轮 trace | 轻量手写 DDL（可控增量加列） |

- **主库**：`db.py` 单例引擎 + `session_scope()` 事务；`Conversation` 与 `Message` 用 `Relationship(cascade_delete)` 关联；`Message.route` 记难度档位；schema 版本 `PRAGMA user_version`（当前 v4），`_migrate` 用 `create_all` + 增量 `ALTER` 兼容旧库（幂等）。
- **向量同库**：不用 lancedb（省 ~380MB），`sqlite-vec` 加载失败只诊断不阻断——聊天主流程不依赖向量。
- **会话库即短期记忆**：`short_term_memory` 先读 `logs/session.sqlite`（近 N 轮），空则回落主库消息；注入 simple/medium/hard 图。工具轨迹与推理也写这里，前端“洞察面板”与“追踪窗”直接读。

## 10. 可观测性（Agent 应用的刚需）

非确定性系统必须有“回放/追踪”能力：

- **`trace` 模块**：`recording(turn_id)` 上下文里记录 span 树、每次 LLM 请求/响应、工具调用、token 用量；按 `turn_id` 落会话库。
- **展示路径 `_path(difficulty)`**：把图节点映射成给人看的 path——understand → route →（simple | plan→select_tools→react→verify）。
- **接口**：`GET /api/conversations/{id}/traces`（每轮摘要）、`GET /api/conversations/{id}/traces/{turnId}`（完整步骤：图路径、LLM 入参/出参、工具、token）。前端 `TraceWindow` 独立窗可视化。
- **价值（面试话术）**：Agent 行为非确定性、且会调工具改文件，没有逐轮追踪就“无法调试、无法向用户解释为什么这么做”。所以可观测是**一等公民**，不是事后补监控。

## 11. 构建与发布架构（为什么最终用户不用装 Python）

```text
dev:  tauri dev  → Rust 拉起 .venv + backend/main.py（--reload，端口 8420）
build: prepare:runtime (PyInstaller onedir) → dist-backend/
       tauri build → 把 dist-backend/ 作为资源 backend-runtime/ 打进安装包
       最终：backend-runtime/backend.exe + _internal/，用户机无需 Python
```

- **PyInstaller onedir**：把 Python 解释器 + 依赖冻结成 `backend.exe` + `_internal/`，Tauri 在 `bundle.resources` 里以 `backend-runtime/` 复制进去。
- **按需下载，不进包**：Chromium（Playwright）、MinGit、向量权重模型等体积大的资源**不进安装包**，首次使用时下载到 `CHATVEIN_DATA_DIR`。
- **端口策略**：dev 固定便于抓包调试；release 动态探测空闲端口避免与宿主机冲突——端口在进程内只解析一次并被启动/探测/前端共用。

## 12. 一次请求的完整编排（把核心串起来）

```text
POST /api/chat { message, conversation_id?, role_id?, skills? }
   │
   ├─ open_for_chat → 确保会话 + workspace_dir（分配或复用会话工作区）
   ├─ short_term_memory(limit ≈ role.memory×2)   ← 读会话库
   ├─ RolesService.resolve_for_chat → 角色运行时（prompt/模型/工具/记忆）
   ├─ skill_prompt_blocks(skills) → 并入 role.prompt（SKILL.md 文本）
   ├─ use_conversation_sandbox(workspace_dir)     ← contextvars 绑定沙箱
   │
   ├─ run_pipeline → run_pipeline → LangGraph
   │     understand(改写+难度) → simple|medium|hard
   │       medium/hard: tool_selector 缩集 → create_agent ReAct
   │       hard: plan→…→verify（可回环）
   │     工具在沙箱内执行；Bash/PowerShell 危险命令挂起等人审
   │
   ├─ save_exchange  → 主库：用户消息 + 助手回复（同事务，route=difficulty）
   ├─ record_turn    → 会话库：消息 + 工具轨迹 + 推理（route_reason/tool_plan）
   ├─ trace 按 turn_id 落会话库
   │
   └─ 返回 reply, difficulty, rewritten, tool_trace, selected_tools,
             tokens, duration_ms, conversation_id, user/assistant_message, workspace
```

**两个易踩的不一致点（面试加分）**
1. **原文入库，改写不入库**：`rewritten` 只进 Agent，用户气泡仍是原话（避免“AI 替我改了我说的话”的体验问题）。
2. **同步请求 vs 异步落库**：`/api/chat` 同步返回，但 Agent 可能还在生成；前端“停止/撤回”用 `AbortController` 中止 HTTP 后，还要轮询 `deleteLastTurn` 直到后端真正落库并被清掉——这是“前端乐观 UI + 后端同步落库”的协调细节。

## 13. 面试串讲（45 秒 / 30 秒两版）

### 核心架构“面试串讲”（45 秒版）

> 核心是一条 LangGraph 流水线：先 `understand` 用主模型把用户原话改写成清晰意图并判定难度（simple/medium/hard），再按难度进子图。simple 直接答；medium 先“工具选型缩集”再跑 ReAct；hard 还要先 plan、最后 verify，不通过可回环最多两轮。工具是进程内 LangChain @tool，按 MCP 分组注册、运行时能力探测决定注册与否，Bash/PowerShell 危险命令走人工确认（在图外挂起）。文件操作都在“会话工作区沙箱”里——主工作区下按日期生成的目录，用 contextvars 绑定当前会话，删会话级联清目录。持久化是双层 SQLite：主库存会话/消息/模型/角色（SQLModel，向量用 sqlite-vec 同库），每会话再有一份 session.sqlite 存短期记忆/工具轨迹/逐轮追踪。每轮都有 trace，前端有独立追踪窗——因为 Agent 非确定性，可观测是刚需。

---

### 设计架构“面试串讲”（30 秒版）

> ChatVein 是 Tauri2 桌面 Agent，三层架构：React 做界面，Rust 做消息层（不是代理，而是进程编排者——启动时把 Python 的真实 URL 推给前端，之后前端经 Tauri 的 fetch 直连 Python，绕开 CORS），Python/FastAPI 做真实业务（LangGraph 编排 + 工具 + SQLite）。Rust 还负责端口/数据目录决策和日志事件桥接。后端按领域分层（controller/service/repository/entity），前端有单一 API 封装层。持久化用主库 + 每会话库两份 SQLite，向量走 sqlite-vec。打包时把 Python 用 PyInstaller 冻结成侧车塞进安装包，用户无需装 Python，浏览器/MinGit/向量权重按需下载。

## 14. 常见追问与应答

### 常见追问与应答

- **Q：为什么 medium/hard 要先“选型”再跑 Agent？** → 全量工具进 prompt 既占 token 又易误调；先缩集能降成本、提准确率，也让角色“工具白名单”有用武之地。
- **Q：hard 的 verify 会不会无限循环？** → 不会，`_MAX_VERIFY_ROUNDS=2`，到上限强制收束并注明“已达核对上限”。
- **Q：工具为什么不做成外置 MCP 子进程？** → 体积/打包成本、启动延迟；进程内调用更简单且与 `builtin://` 设计一致。Browser 用进程内 Playwright 对齐上游工具面，不另起 Node。
- **Q：两层 SQLite 不麻烦吗？** → 主库是“跨会话的业务状态”，会话库是“单会话的短期记忆与轨迹”，天然按会话隔离、删除即清；向量同主库省一份重依赖。
- **Q：没有 API Key 时系统还能用吗？** → 能。`router`/`tool_selector` 走启发式，`simple` 回离线文案，`medium/hard` 直接 `invoke_tools`——离线降级是设计目标之一。

### 常见追问与应答

- **Q：前端直连 Python，安全吗？** → 都是本机 `127.0.0.1`，不暴露到外网；CORS 全开仅限本地进程内通信；Tauri 窗口与能力受 `capabilities` 约束。
- **Q：Rust 不做代理，那它还能管什么？** → 进程生命周期、端口/路径决策、把后端日志实时转成前端事件（可观测）、退出清理。
- **Q：为什么不直接用 Electron？** → Tauri 用系统 WebView + Rust，体积小、内存低、安全模型更现代；本项目的“Rust 只编排不代理”正好契合 Tauri 轻量定位。
- **Q：dev 与 release 后端差异怎么对齐？** → `cfg!(debug_assertions)` 在编译期区分：dev 用源码+热重载+固定端口，release 用冻结 exe+动态端口；同一份 `backend.rs` 逻辑覆盖两种形态。

## 15. 设计哲学：为什么这样实现

### 总纲：让每种语言做它最擅长的事（扬长避短）

```text
Rust   → 安全、轻量、系统级编排（进程/端口/路径/日志桥接）
Python → LLM / 数据 / 工具生态最丰富（LangChain、SQLModel、sqlite-vec）
TS     → 现代、易维护的桌面 UI（React + Vite + Tailwind）
```

**思想**：不为了“统一技术栈”而强行用一种语言扛全部。桌面 Agent 的瓶颈在 LLM 编排与工具，而这恰恰是 Python 的强项；Rust 只做它最稳的“编排外壳”；UI 用前端生态最快迭代。三者通过**本地 HTTP + 事件**协作，互不绑架。

---

### 把“消息层”做薄：Rust 编排，而非代理

- **原则**：中间层只做“必须的协调”，不做“逐请求转发”。
- **体现**：Rust 仅在启动时把后端 URL 推给前端，之后前端直连 Python。Rust 不解析业务请求、不持有业务状态。
- **收益**：少一跳延迟；Rust 代码极薄（`commands.rs` 只一个 `backend_url`）；业务演进完全在 Python，Rust 几乎不动。
- **衍生收益**：前端用 Tauri `plugin-http` 的 `fetch`，请求在 Rust 的 reqwest 发，**免 CORS/CSP**——这是“前端直连后端”能成立的前提。

> 面试话术：“我们把 Rust 定位成‘消息层/编排者’，而不是反向代理。这契合 Tauri 的轻量哲学：Rust 负责把 Python 进程拉起来并告诉前端地址，真正的请求由前端直连 Python，既少一跳又让 Rust 代码极薄、业务全在 Python 演进。”

---

### 分层与同构：用结构对抗复杂度

- **后端领域同构**（entity/controller/service/repository/module）：每加一个业务域就照模板来，新人可读、可测、可扩展。
- **连接层与业务表分离**（`db.py` 不写业务表）：横切关注点（引擎、事务、迁移、向量扩展）集中，避免巨型 `models.py`。
- **前端单一 API 出口**（`api.ts`）：把“等后端就绪 + 直连 + 错误归一 + AbortSignal”收敛到一处，视图层只调语义化函数（`sendChat`/`listModels`/...）。
- **思想**：复杂度不会消失，只能被“结构化”。用统一分层让每个文件职责单一，变更互不污染、易于单测。

---

### 按成本与风险“分流”，而不是一刀切

Agent 最贵的是 LLM 调用与工具执行。项目用“难度路由”把任务按成本分三档：

- simple（闲聊/单句问答）→ 不挂工具，最省；
- medium（一两跳工具）→ 选型后 ReAct；
- hard（多步/需规划核对）→ plan + 更高递归 + verify 回环。

**思想**：
- **能直答就不调工具**（省成本、降出错面）；
- **能少工具就先选型缩集**（降 token、提准确率）；
- **复杂任务给“规划+核对”闭环**，但用回环上限（2 轮）防失控。
这是“在能力、成本、可控性之间取平衡”的工程直觉，而非无脑上最强模型/最多工具。

---

### 优雅降级：没有模型/没有网络也能“活着”

- 无 API Key：`router`/`tool_selector` 走启发式（命中工具意图 → medium，否则 simple），`medium/hard` 直接 `invoke_tools`，不拖垮会话。
- 向量扩展加载失败：只诊断上报，**不阻断启动**，聊天主流程不依赖向量。
- 能力探测失败（无 Chromium / 无 Bash）：对应工具分组**不注册**，Agent 不会调用不存在的能力；Bash 不可用时自动降级到 PowerShell。
- LLM 调用异常：`understand` 等失败自动回落离线分支。

**思想**：本地 Agent 的运行环境千差万别（密钥、网络、浏览器、Git）。把“缺失即降级”做成默认行为，系统在任何环境下都**至少可用**，而不是“一缺就崩”。这是桌面软件区别于服务端的重要工程准则。

---

### 用“沙箱 + 人工确认”把能力开放与安全风险分开

桌面 Agent 能读写文件、跑命令、开浏览器——能力越强，风险越高。项目的解法：

- **会话级沙箱**：所有文件/代码操作限制在“会话工作区”内（`contextvars` 绑定当前会话目录），工具实现无需感知会话 id；删会话级联清目录，天然隔离。
- **范围约束**：文件工具只能在工作区；`delete_path` 不能删主空间根；`mcp-sqlite` 只读；通用 `cmd.exe` 刻意不做。
- **人审挂起（HITL）**：Bash/PowerShell 的危险或写盘命令在工具执行路径上**挂起**，等前端弹窗批准/拒绝——把“不确定的决策”交给人，而不是在图状态机里阻塞。
- **RCE 风险规避**：明确不暴露 `browser_run_code_unsafe`（Playwright 服务端执行任意 JS，等价于 RCE）。

**思想**：本地 Agent 的价值在于“能动手”，但动手必须“在笼子里”。沙箱解决“范围”，人审解决“不可逆/高风险动作”，两者正交、可叠加。

---

### 可观测是刚需，不是装饰

Agent 行为非确定性、且会改文件，没有追踪就无法调试也无法向用户解释“为什么这么做”。

- 每轮都记录 path（理解→路由→直答/规划/筛选/ReAct/核对）、LLM 入参出参、工具、token；
- 落会话库，前端独立追踪窗可视化；
- `span`/`note` 贯穿图节点与子步骤。

**思想**：对“会自己决策、会调工具”的系统，可观测性不是运维附属，而是**产品的一部分**——用户要看见推理路径，开发者要能复盘失败。所以 trace 从一开始就是一等公民。

---

### 轻依赖、小安装包：桌面端的硬约束

- **向量用 sqlite-vec 而非 lancedb**：同库、同事务、同备份，且避免引入 pyarrow 等重型依赖（省 ~380MB）。
- **工具进程内而非外置 MCP 子进程**：不另起 Node 进程，体积小、启动快。
- **大资源不进包，按需下载**：Chromium（Playwright）、MinGit、向量权重模型都不打进安装包，首次使用时下载到 `CHATVEIN_DATA_DIR`。
- **Python 冻结成侧车**：PyInstaller onedir 把后端冻成 `backend.exe`，用户机无需装 Python。

**思想**：桌面应用的分发成本取决于安装包体积与“是否要用户配环境”。能冻结就冻结、能按需下就按需下、能用轻量库就别引重工业库——这是“能装得上、装得快”的底层考量。

---

### 路径/端口决策权上收，配置下推

- **路径所有权在 Rust**：因为打包后后端在只读资源目录，不能自己决定写哪；Rust 用 `app_data_dir` 算好 `CHATVEIN_DATA_DIR` 注入，Python 只读。
- **端口内部解析一次**：dev 固定 8420（好调试），release 动态探测 ≥3000 空闲端口（避冲突）；`OnceLock` 保证启动/探测/前端共用同一端口。
- **配置可被环境变量覆盖**：`CHATVEIN_DB_PATH` / `CHATVEIN_WORKSPACE` / `CHATVEIN_DATA_DIR` / `CHATVEIN_RELOAD` 等，便于调试与部署。

**思想**：把“环境相关、易变、需要安全决策”的东西（写哪、用哪个端口）放在最知道平台规则的层（Rust/OS 集成），把“业务逻辑”留在 Python；同时保留环境变量逃生舱，兼顾“开箱即用”与“可调试”。

---

### 迁移与演进要“幂等、向后兼容”

- 主库 schema 版本用 `PRAGMA user_version`（当前 v4）；`create_all` 只建新表，`_migrate` 用增量 `ALTER` 给旧库补列（幂等，可重复跑）。
- v1 时间戳规范化（去掉 `+00:00` 文本）只影响旧库、幂等。
- 会话库 `session_store` 也做增量加列，旧版 `tool_calls.turn_id` 为 INTEGER 时直接重建该表（仅丢历史工具轨迹，会随对话重生）。

**思想**：本地 SQLite 没有 DBA，升级靠“用户自己跑起来的那一次”。迁移必须**能重复执行、不丢数据、不阻塞启动**——这是客户端软件的数据库演进铁律。

---

### 前端与后端“异步落库”的协调哲学

`/api/chat` 是同步 HTTP，但 Agent 生成可能慢、且后端是同步落库。前端处理：

- 乐观插入用户/助手气泡（`pendingRef` 记 id 原文），停止时精确移除；
- 用 `AbortController` 中止在途请求；
- 后端可能已落库 → 前端 `cleanupLastTurn` 轮询 `deleteLastTurn` 直到真正清掉（最多 ~6.4s）。

**思想**：UI 的“即时感”与存储的“一致性”冲突时，用“乐观更新 + 补偿清理”而非“等全部完成再显示”。同时承认“请求中止 ≠ 后端已停”，用轮询补偿最终的存储状态。

---

### 一句话工程价值观（面试收尾用）

> ChatVein 的实现思想可以概括为：**用对的语言做对的事；让中间层做薄、让业务层做厚；按成本与风险分流；任何环境都能降级可用；能力开放必有沙箱与人审；可观测是一等公民；一切为“小安装包、能装即用、升级不丢数据”服务。**

---

### 面试可能被深挖的“思想类”问题

- **为什么不用 Electron + Node 后端？** → 体积/内存/安全；Rust 编排更轻；Python 吃 LLM 生态。
- **为什么不把 Rust 当代理统一收口？** → 少一跳、Rust 更薄、业务演进不被中间层拖住；直连靠 Tauri http 插件免 CORS。
- **为什么工具要进程内而非 MCP 子进程？** → 打包体积、启动延迟、与 `builtin://` 设计一致。
- **为什么难度要分三档而不是都上 ReAct？** → 成本/准确率/可控性平衡；简单任务没必要调工具。
- **为什么可观测这么重？** → Agent 非确定性 + 会改文件，没有追踪就无法调试也无法解释。
- **本地 SQLite 怎么保证升级不炸？** → user_version + create_all + 增量 ALTER + 幂等迁移。

> 面向面试：本篇讲“为什么这样实现”的底层取舍与工程哲学——把设计决策背后的**原则**提炼出来，便于在面试中展现“有思考、不是堆功能”。
