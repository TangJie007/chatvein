# 决策笔记：band 默认 maxSteps 改为 8/16/64

状态：已落地

## 背景

接上工具后，原 simple=`maxSteps:2` 经 app 映射为 LangGraph `recursionLimit=2`，一次「调工具再答」就会触发 Recursion limit。需要按真实 ReAct hop 容量抬高各档默认步数。

## 决策

`policyForBand` 默认：

| band | maxSteps |
|------|----------|
| trivial | 0（当时与 L1 短路共用；**band 默认已由** [2026-09-07-trivial-maxsteps-4](./2026-09-07-trivial-maxsteps-4.md) **改为 4**） |
| simple | **8** |
| standard | **16** |
| complex | **64** |
| unknown | **16**（对齐 standard） |

L2 schema / prompt 上限改为 0–64。`recursionLimit = max(1, maxSteps)` 映射不变。实现：`routing/policy.ts`；文档：`docs/design/09` §7、`10`、`11`。

## 备选方案

**保持 2/8/16**：不足以支撑带工具的 ReAct，否决。

**complex=32 或 48**：更紧，但用户明确要 64 作重任务熔断顶，采纳用户档。

**有工具时另算 headroom、不动 band 表**：多一套隐式规则难调试；先统一抬表更清晰。

## 影响

- 收益：simple/standard 日常工具轮不易误杀；complex 给重任务留顶。
- 代价：失控循环的上限变高，更依赖后续 BudgetGuard / 超时。
- 后续注意：simple 仍默认 `tools:none`，8 步对纯答偏宽，主要为日后偶发工具或误绑留余量。
